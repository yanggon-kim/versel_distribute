Custom HBM (B200 + LPDDR5X) — Sequential vs Gather:
Finding the Best HBM:LPDDR Ratio

Cycle-level Ramulator 2 study on a B200-class custom-HBM base die: how a fixed 1 TB/s GPU link should split traffic between a 24 GiB HBM3E near tier and a 128 GiB LPDDR5X far tier — for streaming and for DeepSeek-V3.2’s sparse-KV gather — and why the answer is one law with workload-dependent constants.

0 · TL;DR

10 : 1
best HBM:LPDDR ratio for sequential streams (hardware interleave) — 1023 GB/s = 99.9% of the 1 TB/s link
4 : 1  (p* ≈ 0.20)
best ratio for the DSv3.2 gather — 322 GB/s aggregate, 17% faster than HBM-only
322.3 ≈ 321.7
hardware 32 B striping and software page placement are bandwidth-equivalent at the matched ratio
30 vs 152 GiB
but whole-space interleave destroys capacity — software placement keeps the full unified space at equal bandwidth

One bottleneck law explains every sweep: split traffic in proportion to each tier’s workload-achievable bandwidth, so both tiers finish together. The constants differ per workload — 1007:124 for sequential, 268.8:65.9 for the gather — so the best ratio is a workload property, not a platform property. And because the gather leaves the HBM link 74% idle (activate-bound), the far tier is genuinely additive there, while for sequential it only tops up the last ~2%.

1 · The platform under test

One base-die site of an NVIDIA B200-class custom HBM stack, modeled in Ramulator 2 (branch feature/hbm-lpddr-basedie-v4): the HBM base die is a logic die hosting the memory controllers for the stack above it and LPDDR controllers behind its off-chip I/O, exposing one unified address space to the GPU across a fixed-bandwidth D2D link.

Fig. 1 — the modeled system: one B200 cube (of 8 per GPU) whose base die also fronts an LPDDR5X capacity extension. The GPU link is deliberately kept at the HBM wire peak — extra processor-side PHY is not free — so the far tier must live within that budget.

Deep (128-entry) read queues model a GPU-class memory controller: by Little’s law a 32-entry queue holds only 16 ns of work at 64 GB/s — less than one ~45 ns row miss — and measurably starves the DRAM (88% of wire vs 99.4% at 128).

2 · The two workloads

2a · Sequential streaming

A plain contiguous read stream (LD 0, LD 32, LD 64, …). Row-buffer hit rate is ~97%, the data bus is the binding resource, and each tier runs at essentially its wire rate: HBM 1006.7 GB/s (98.3% of wire), LPDDR 124.5 GB/s (91%; the ~9% is 8-rank ODP bus turnaround). This is the workload for which the link itself can be filled.

2b · The DeepSeek-V3.2 sparse-KV gather — what it actually is

DeepSeek-V3.2 uses DSA (DeepSeek Sparse Attention): at every decode step, instead of reading the whole KV cache, a “lightning indexer” scores all past tokens and a top-k unit selects the 2,048 most relevant tokens (index_topk, context-invariant). The attention kernel then reads only those tokens’ KV latents — the gather. Per (session, layer, decode step):

2,048 reads × 656 B = 1.34 MB, token positions ~uniform over the L-token context, selections regenerated every layer (61 layers), one index set per query token shared by all 128 query heads. All indices are known before the gather starts — no pointer chasing, so arbitrarily deep prefetch is legal.

The 656-byte record and its paged layout were verified directly against the vLLM source (fp8_ds_mla cache format; page = 64 tokens × 656 B = 41,984 B, row-major uint8, identity stride):

Byte offsetSizeContent
0 – 511512 Bc_kv latent — 512 × fp8_e4m3 (4 tiles of 128)
512 – 52716 B4 × fp32 per-tile scales
528 – 655128 Bk_rope — 64 × bf16, unquantized

Fig. 2 — the gather address pattern. The indexer emits request-relative positions; a translation pass converts them through the block table into global page slots, and the kernel gathers directly from the paged cache — so the faithful DRAM-side model is a random page base + in-page offset 656·t.

Where the indices come from (the per-layer selection pipeline): each of the 61 layers runs, in order — (1) a key scan over a separate 132 B/token indexer cache (sequential, ~17 MB at 128K); (2) a logits write of one fp32 score per past token (~524 KB/session-layer); (3) a radix/histogram top-k that re-reads the logits and emits 2,048 sorted int32 indices (8 KB, padded with −1 for short contexts); then (4) the gather studied here. The index buffer has no head axis and is overwritten every layer — successive layers select independently. Steps 1–3 are sequential-ish streams; the gather is the only scattered primitive, which is why it is the far tier’s critical workload.

Per-GPU gather volumes at L = 128K (from the B200 profiling bundle). Note the sustained per-cube demand (~18 GB/s even at b = 172) is far below even the LPDDR-only gather bandwidth measured below — the far tier’s risk is per-layer burst hiding, not average bandwidth.

Scale note: the study models one cube (one base-die site) of the GPU’s eight, so all bandwidths are per-cube. Uniform selection is the conservative default (real selections have sinks/recency/step-overlap structure, which only adds locality). Headline runs use L = 128K — exactly one record per touched page, the maximally scattered regime — and 12,000 records per run (≈ 8.1 MB issued).

Model boundary that matters: this composite interleaves the address space across channels at 32 B granularity, which sprays a record’s 21 lines over 16 channels and erases its internal locality — the gather degrades to random-32B behavior (row-hit 1.5%). Real GPUs stripe channels coarser (~256 B class): the real B200’s naive gather ran at ~93% of sequential. All gather numbers here are therefore the pessimistic bound; a channel-interleave-granularity lever is the top queued follow-up.

The sweeps below tune R:L for sequential (sweep 1), p for the gather (sweep 2), and then run the gather under the interleave (sweep 3) — where p is no longer free but hardwired to L/(R+L), making the two mechanisms directly comparable.

4 · Sweep 1 — sequential streams: interleave ratio R:L

A naive sequential stream over the interleaved space, R:L swept. HBM alone (no interleave) already sustains 1006.7 GB/s = 98.3% of the link, so the far tier can only top up the last ~1.7% — and only at ratios near the tiers’ sequential bandwidth ratio 1007 : 124.5 ≈ 8.1 : 1.

Fig. 3 — sequential streams: a broad plateau at 8:1–16:1 reaching 99.6–99.9% of the link; best 10:1. Below ~9:1 the stream over-diverts to the ~8× slower far tier and falls under the HBM-only baseline. Hover any bar for exact values.

Ratio sensitivity was established on a smaller configuration too: the optimum tracked the tiers’ bandwidth ratio there as well (2.3:1 wire ratio → best 2:1–3:1), moving to 1:1 when the provisioning changed to a 1.1:1 ratio — and a too-far-heavy ratio was not merely suboptimal but fell below not interleaving at all (0.67× at 1:2). Fine (32 B–256 B) stripe granularity was required with shallow queues; with GPU-class deep queues even 4 KiB stripes work — the ping-pong penalty was largely a queue-starvation artifact.

Takeaway 1: for streaming, the far tier is not a bandwidth tier — a perfectly tuned ratio buys +1.6% because HBM alone nearly fills the link. The interleave’s value must come from elsewhere (see the gather).

6 · Sweep 3 — the gather under hardware interleave

Finally, the gather is run on the hardware-interleaved address space (sweep 1’s mechanism), sweeping R:L. Here every 656 B record is automatically split ~R:L across tiers at 32 B granularity — placement is no longer per-page but hardwired to p = L/(R+L). The family-2 law, with the same constants, predicts this sweep too:

Takeaway 3: the best ratio is workload-dependent — 4:1 for the gather vs 10:1 for sequential; running the gather on the sequential-tuned config forfeits 8%. And hardware interleave at 4:1 ties optimal software placement (322.3 ≈ 321.7 GB/s)…
…but at a capacity price software placement doesn’t pay. Whole-space 4:1 striping can address only near×5/4 = 30 GiB total (6 of the 128 GiB LPDDR reachable); by-page placement at p = 0.20 delivers the same bandwidth with the full 152 GiB. Software placement strictly dominates whole-space interleave for this workload. The one way hardware wins both: a carved interleaved sub-range — stripe a ~30 GiB hot-KV window at 4:1, keep the remaining ~122 GiB as plain far capacity. This elevates the carved sub-range from patent-faithfulness nicety to the actually required mechanism.

7 · The bottleneck law — and why 268.8, not 1 TB/s

All three sweeps obey one law. Send fraction p of the traffic to LPDDR and (1−p) to HBM; the tiers drain their shares concurrently; aggregate rate T is capped by whichever tier is overloaded relative to its capability: 

T(p) = min( BW_H / (1−p) ,  BW_L / p )          ← rate form
time(p) = max( (1−p)·B / BW_H ,  p·B / BW_L )   ← equivalent time form

optimum:  p* = BW_L / (BW_H + BW_L)   (both tiers finish together)
peak:     T(p*) = BW_H + BW_L         (both tiers flat-out, in parallel)

The constants are each tier’s workload-achievable bandwidth — measured at the sweep endpoints, not fitted, and not the wire peaks:

HBM tierLPDDR tier
Wire (pin) peak1024 GB/s136.5 GB/s
Sequential achievable1006.7 (98.3% of wire)124.5 (91%)
Gather achievable268.8 (26%) — activate-bound: random rows force one ACT per line and tFAW allows 4 ACT/15 ns/pseudochannel → 16·2·4/15 ns·32 B = 273 GB/s predicted65.9 (48%) — command-bus-bound: 4 slots per random read (2-cycle ACT1+ACT2, CAS+RD) → 8·32 B/3.75 ns = 68.3 predicted

Both gather ceilings match first-principles DRAM arithmetic within ~1% — the data pins are not the limit; the row-activation and command machinery are. That is why the same platform has two different best ratios: sequential constants 1007:124.5 → ~8:1; gather constants 268.8:65.9 → 4:1. Plug in nameplate bandwidths and every prediction fails; plug in workload-achievable bandwidths and every sweep point lands within ~3%.

8 · Concurrency: how much batch the gather needs

The sweeps above run at the concurrency plateau. Capping the number of gather records in flight (K — the memory-side meaning of “batch size”) reproduces the rising part of the curve, and Little’s law with one measured constant per tier fits every point: BW(K) = min(plateau, K · 672 B / trecord), trecord = 49 ns (HBM) / 66 ns (LPDDR).

HBM measured (dashed: Little’s-law prediction) LPDDR measured (dashed: prediction)

Fig. 6 — bandwidth vs records in flight. Knees at the bandwidth-delay product: K* ≈ 20 records (~13 KB) for HBM, ≈ 7 for LPDDR. A base-die gather engine needs only that much buffering per cube to saturate each tier. The real-GPU calibration curve has the same shape but t_record ≈ 290 ns end-to-end — the ~240 ns delta is SM/kernel pipeline overhead outside a DRAM model.
