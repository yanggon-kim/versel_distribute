Python & C++ Basics for Ramulator — the Language Concepts Behind the Component Framework

A prerequisite lesson for the Ramulator 2.1 Core Course, Lesson 3. It teaches only the seven language concepts needed to understand how a Python configuration becomes a tree of C++ objects — three Python ideas, four C++ ideas — each with the same rhythm: the problem → a tiny example → a line-by-line walk → where it appears in Ramulator. print(...) in examples means "show this on screen" (real C++ printing looks noisier, but that noise teaches nothing).

0Why are there even two languages?

The engine is C++ (fast), the control panel is Python (convenient).

  • C++ programs must be compiled: a tool translates the whole source code into machine code before anything runs. The result is very fast — and that matters, because Ramulator executes its tick loop hundreds of millions of times per simulation.
  • Python is interpreted: you write a text file and run it immediately, no compile step. It is slow but effortless to change — perfect for describing what you want to simulate today (8 channels? rank=2? which scheduler?).

So Ramulator splits the work. Everything time-critical (controllers, DRAM timing, the tick loop) is C++. Everything you touch daily (choosing components, setting parameters) is Python. This page is about the wiring between the panel and the engine.

1The Python you need — 3 ideas

Everything you will ever write in Ramulator-Python is "make me one of these, with these ingredients."

Idea 1 — calling with named ingredients

FRFCFS() means "make me a FRFCFS thing." You can pass ingredients by name:

ctrl = ramulator.controller.HBM34(scheduler=FRFCFS(), read_buffer_size=32)

Read it aloud: "make an HBM34, whose scheduler ingredient is a fresh FRFCFS, and whose read_buffer_size ingredient is 32." Notice ingredients can themselves be freshly-made things — the calls nest.

Idea 2 — the dictionary: a labeled box of values

{"impl": "HBM34", "read_buffer_size": 32, "scheduler": {"impl": "FRFCFS"}}

Curly braces, label: value pairs — and a value can itself be another dictionary (boxes inside boxes). Keep this picture in mind: this is the hand-off format between the two languages.

Idea 3 — every Ramulator thing can describe itself as a dictionary

Each Python object carries a function to_config() that flattens the pretty nested calls of Idea 1 into the nested dictionary of Idea 2. That is all Python contributes: building a description. No simulation ever happens in Python.

2C++ idea 1 — class, object, constructor

The problem

You want to describe a kind of thing once, then make many of them.

The tiny example — a click counter

class Counter {            // "class" = a BLUEPRINT for a kind of thing
  int count;               // every Counter will have its own number called count

public:
  Counter(int start) {     // the CONSTRUCTOR: assembly instructions,
    count = start;         // runs automatically when a Counter is built
  }

  void increment() {       // a function every Counter carries with it
    count = count + 1;
  }
};

Line-by-line walk

  1. class Counter { ... }; — nothing is built yet! This is only the blueprint: "if someone makes a Counter, it will contain an int count and know how to increment()."
  2. Counter(int start) — the constructor. Its name always matches the class. It runs exactly once, at the moment of creation, to set the newborn object up.
  3. Now build objects — real things stamped from the blueprint:
Counter a(0);      // build one Counter; constructor runs with start=0 → a.count is 0
Counter b(100);    // build ANOTHER, totally separate one → b.count is 100
a.increment();     // a.count becomes 1.  b.count is still 100 — they don't share!

Where it appears in Ramulator

HBM34Controller is a class. Configuring 8 HBM channels builds 8 separate objects from that one blueprint. And Ramulator's constructors end by calling init() — the setup ritual where parameters are read and children are built (§6).

3C++ idea 2 — inheritance ("is a kind of")

The problem

Two blueprints share 90% of their content. Copy-pasting the shared 90% would be a maintenance nightmare.

The tiny example

class Animal {
public:
  void breathe() { print("inhale, exhale"); }
};

class Dog : public Animal {      // read ":" as "is a kind of"
public:
  void bark() { print("woof!"); }
};

Line-by-line walk

  1. class Dog : public Animal — Dog inherits Animal. That one line copies, invisibly, everything Animal has into Dog.
  2. So a Dog object has two abilities — its own and the inherited one:
Dog rex;
rex.bark();      // works — Dog's own
rex.breathe();   // ALSO works — came free from Animal (we never wrote it in Dog)
  1. Rule of thumb: write the shared stuff once in the parent; each child adds only its differences.

Where it appears in Ramulator — and it is load-bearing

The class ControllerBase contains the ~90% every memory controller shares: the four queues, send() with forwarding/coalescing, the write-mode watermarks, the pending-reads deque, all the stats. Then each standard adds only its delta:

class HBM34Controller  : public HBMControllerBase   { /* adds: dual command bus + edge pairing */ }
class LPDDR5Controller : public LPDDRControllerBase { /* adds: two-part ACT, WCK sync */ }
When the Core Course studied set_write_mode() (Lesson 4), it studied it once, in ControllerBase — and the conclusion applied to both the HBM tier and the LPDDR tier of the v1 model automatically. That is inheritance paying rent.

4C++ idea 3 — the interface (a contract with empty slots) + the pointer that makes it useful

The big one — built in three small steps.

Step 4a — the problem

The controller needs to ask some scheduler "pick the best request." We want to freely swap which scheduler (FRFCFS today, your custom one tomorrow) without editing the controller's code. How can the controller call a function on a thing whose exact type it doesn't know?

Step 4b — the contract

Declare a class that is deliberately hollow:

class ISpeaker {
public:
  virtual string sound() = 0;   // "every kind of ISpeaker MUST have sound() —
};                              //  but I'm not telling you how it works"

Two new marks, both doing exactly what they look like:

  • virtual = "children are allowed to replace this function with their own version, and the replacement wins."
  • = 0 = "this slot is EMPTY here. You cannot build a plain ISpeaker (it's incomplete!) — only children who fill the slot can be built."

Two children fill the slot differently:

class Dog : public ISpeaker {
public:
  string sound() { return "woof"; }    // Dog's way of fulfilling the contract
};

class Cat : public ISpeaker {
public:
  string sound() { return "meow"; }    // Cat's way
};

Step 4c — the pointer (a sticky note with an address)

A pointer is a variable that holds the location of an object rather than the object itself — a sticky note with an address written on it. Written with a *:

ISpeaker* pet;        // a sticky note that can point at ANY kind-of-ISpeaker
pet = new Dog();      // today it points at a Dog...
print(pet->sound());  // → "woof"    (-> means: follow the note, call the function)
pet = new Cat();      // ...tomorrow, at a Cat. Same variable!
print(pet->sound());  // → "meow"

Stare at the magic line: print(pet->sound()) — that line never changes, yet it produced "woof" and then "meow." The code was written against the contract (ISpeaker); the behavior came from whatever object the note pointed at. This is the mechanism that lets one line of code work with things invented years later.

Where it appears in Ramulator — verbatim

The controller holds IScheduler* m_scheduler; — a sticky note typed "some scheduler." Its tick does m_scheduler->get_best_request(buffer), written purely against the contract in i_scheduler.h. Whether the note points at an FRFCFS object or at a scheduler you write next month, the controller's code is untouched. Every i_*.h file in the repo — IController, IMemorySystem, v1's IDMAEngine — is one of these contracts. Even the whole v1 composite works this way: the simulation loop holds an IMemorySystem* note; pointing it at GenericDRAM or at HBMLPDDRBaseDie requires zero changes to the loop.

5C++ idea 4 — the macro (a rubber stamp on text)

The problem

Some code patterns are pure boilerplate — 10 identical-shaped lines that every class needs, with only names changed. Typing them repeatedly invites errors.

The tiny example — start with the smallest possible macro

#define SQUARE(x) ((x) * (x))

int y = SQUARE(7);

Walk through what the compiler actually sees

  1. #define SQUARE(x) ... teaches a pre-processing tool a find-and-replace rule. This happens before compilation, on raw text.
  2. Everywhere SQUARE(7) appears, the text is literally rewritten to ((7) * (7)).
  3. The compiler never sees the word SQUARE at all — only the expanded text, as if you had typed it yourself.

A macro is not a function — it is a stamp. And a stamp can expand to many lines:

#define REGISTER(name)                       \
  static bool registered_##name =            \
      factory_table.add(#name, build_##name);
// (don't worry about the ##/# glue syntax — it just pastes the name into the generated text)
// one short line, REGISTER(FRFCFS), expands into the whole
// "add me to the factory table at program start" ritual of §6.

Where it appears in Ramulator

RAMULATOR_REGISTER_IMPLEMENTATION(IScheduler, FRFCFS, "FRFCFS")  // expands to: factory self-registration
RAMULATOR_PARSE_PARAM(m_size, int, "read_buffer_size")           // expands to: read this label from my config dict
RAMULATOR_CREATE_CHILD(m_scheduler, IScheduler)                  // expands to: build my child via the factory

Each stamped line hides 5–15 lines of ritual.

The beautiful side effect: because macros are plain text with a fixed shape, the Python code generator can find every one of them with simple text search — that is literally how the Python "menu" gets generated from the C++ source. The stamps serve two masters at once: the compiler (expanded code) and the codegen (searchable markers).

6The journey of one config — all seven ideas composed

The factory is a recipe book indexed by name; each class pins its own recipe in; codegen prints the menu.

The central question: the C++ engine receives the dictionary {"impl": "HBM34", ...} — a string! How do you go from the text "HBM34" to constructing an HBM34 object? Answer: a factory — a lookup table inside the C++ program:

"FRFCFS"      →  how to build an FRFCFS
"HBM34"       →  how to build an HBM34Controller
"RoBaRaCoCh"  →  how to build a RoBaRaCoCh
...

…and each class adds itself to the table (that's what the REGISTER stamp expands into). No central list anyone maintains: write a new class with the stamp → the table gains a row at program start; delete the file → the row disappears.

The journey, step by step

  1. You write Python (§1 idea 1): HBM34(read_buffer_size=32, scheduler=FRFCFS(), ...)
  2. Python flattens it into the dictionary via to_config() (§1 ideas 2–3).
  3. The dictionary crosses the border into C++ (as a tree structure called ConfigNode — same shape, C++ flavored).
  4. C++ asks the factory: "build me the thing named HBM34." The factory finds the row and runs HBM34's constructor (§2).
  5. The constructor ends by running init() — where the stamps live: 
    void init() {
  RAMULATOR_PARSE_PARAM(m_read_buffer_size, int, "read_buffer_size");  // reads 32 from the dict
  RAMULATOR_CREATE_CHILD(m_scheduler, IScheduler);    // sees {"impl":"FRFCFS"} → factory builds FRFCFS
  RAMULATOR_CREATE_CHILD(m_addr_mapper, IAddrMapper); // sees {"impl":"RoBaRaCoCh"} → factory builds it
}
    Notice the recursion: building the controller triggers building its children, and if a child had children, the same happens inside its init(). One factory call at the top unfolds the entire dictionary into a full tree of live C++ objects — mirroring the nesting of your Python calls.
  6. One last pass: after the whole tree exists, every object gets a setup() call — the moment for wiring that needs other objects to already exist. (v1's MigrationEngine finds its host memory-system here — during its own init() the parent was still half-built, like asking for your manager's signature while HR is still typing the manager's contract.)
The restaurant, in one paragraph. Each chef (C++ class) pins their own recipe card into the kitchen's book (the factory, via the stamp). A clerk (codegen) walks the kitchen reading recipe cards and prints the customer menu (the Python classes). You tick boxes on the menu; your order ticket (the dictionary) goes to the kitchen; the kitchen builds the dish by following recipes, ordering sub-dishes recursively. Add a new chef → the menu updates itself.

And v1's extension, in one sentence

The stock CREATE_CHILD_LIST stamp hard-codes its dictionary label from the interface name (IController → "controllers"), so a parent could own only one list of controllers; the base die needs two (HBM pool, LPDDR pool) — so v1 added a stamp variant where you choose the label, and taught the menu-printing clerk to recognize it:

RAMULATOR_CREATE_NAMED_CHILD_LIST(m_hbm_controllers,   IController, "hbm_controllers");
RAMULATOR_CREATE_NAMED_CHILD_LIST(m_lpddr_controllers, IController, "lpddr_controllers");

…which is precisely why your Python config has hbm_controllers=[...] and lpddr_controllers=[...] as ingredients.

Composed: classes share machinery via inheritance, plug into each other through interface pointers, and self-register/self-describe via macros — which the factory uses to build them from your Python dictionary, and codegen uses to write the Python menu.

Q1 — Counter a(0); Counter b(100); a.increment(); — what are a.count and b.count now, and why doesn't b change?
a.count = 1, b.count = 100. Each object stamped from the blueprint carries its own copy of the data — incrementing one object touches nothing in the other.
Q2 — In IScheduler* m_scheduler; — is m_scheduler a scheduler?
No — it is a pointer: a sticky note holding the address of some scheduler object that lives elsewhere. The note's type (IScheduler*) only promises that whatever it points at fulfills the IScheduler contract, so m_scheduler->get_best_request(...) is always a legal call.
Q3 — Why can't you build a plain ISpeaker object directly?
It has an unfilled slot (virtual ... = 0) — the blueprint is deliberately incomplete. Only children that fill every empty slot are buildable. That is what makes it a pure contract rather than a thing.
Q4 — A developer reads a config value by hand instead of using RAMULATOR_PARSE_PARAM. The code compiles and runs. What still breaks?
The Python side. Codegen discovers parameters by text-searching for the macro; hand-written parsing is invisible to it, so the parameter never appears as a keyword argument in the generated Python class — users cannot set it from the menu. The stamps serve two masters: skipping one (the codegen) breaks the wiring even when the other (the compiler) is satisfied.
