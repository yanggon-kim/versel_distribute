1The big picture: what Ramulator actually is

Ramulator simulates when, never what — and all of time is one loop.

Ramulator answers a single question, millions of times: "a memory request arrived at time T — at what time does it finish?" It stores no data. There are no real bytes anywhere. It only tracks timing, obeying the DRAM standard's rules (how long a row activation takes, how long after a write a read may start…). A read request goes in, waits in queues, obeys DRAM timing, and comes out with a timestamp. The timestamp is the product. This is enough, because an architect's questions are all timing questions: sustained bandwidth? latency under load? how much does stream A slow down stream B?

Every simulation has exactly two top-level actors, and time advances only because a loop calls tick() on them, alternately, forever:

pseudo-code of the real main loop — src/ramulator/python/bindings.cpp, Simulation::run()

fe_ratio  = frontend.clock_ratio          // e.g. 1
mem_ratio = memory_system.clock_ratio     // e.g. 8
loop forever:
  every mem_ratio iterations:  frontend.tick()        // maybe sends one request
  if frontend.is_finished():   break                    // trace done → SIMULATION OVER
  every fe_ratio iterations:   memory_system.tick()   // DRAM advances one cycle

Two facts hiding in this loop explain real behavior of the v1 model:

  • The gear ratio is the offered-load knob. LoadStoreTrace sends at most one request per frontend tick, so "frontend ticks per memory tick" is the request rate. Bandwidth experiments use fe:mem = 2:1 (saturating); latency probes use 1:16 (nearly idle).
  • The frontend ends the world. The loop exits when the frontend finishes; the memory system gets no vote. The v1 migration DMA lives inside the memory system — when the trace runs out, the simulation stops mid-flight, in-flight DMA blocks and all. DMA experiments must pad the trace.

A tick is dimensionless. Physical time appears only when you multiply by the tick period from the DRAM spec: HBM4-8000 → 0.25 ns/tick; LPDDR5-6400 → 1.25 ns/tick. A real trap from our experiments: HBM reported 196 ticks average read latency and LPDDR 74 ticks — LPDDR "looks" faster until you convert: 49 ns vs 93 ns.

RECAP

  • Two actors — frontend → memory system — ticked alternately by one loop at a configurable gear ratio.
  • The frontend finishing is the only thing that ends a simulation.
  • Ticks are dimensionless; multiply by the tier's tick period (0.25 / 1.25 ns) to get real time.
Q1 — Your DMA engine still has 3 blocks in flight when the frontend's trace runs out. What happens?
The simulation ends immediately — the loop breaks on is_finished() before the memory system ticks again. The in-flight blocks simply never complete (stats would show e.g. blocks_completed=3 with reads issued for a fourth). This is why DMA experiments pad the frontend trace with filler requests.
Q2 — 100 ticks avg latency on HBM4-8000 vs 30 ticks on LPDDR5-6400: which answered faster in real time?
HBM: 100 × 0.25 = 25 ns, vs LPDDR: 30 × 1.25 = 37.5 ns. The larger tick count is the faster memory.

2The life of one request

One struct, one bool, one callback — and the read/write asymmetry that shaped the whole v1 project.

the core object (fields that matter) — src/ramulator/base/request.h

struct Request:
  addr        // flat byte address, e.g. 0x1000
  addr_vec    // same address decoded: [channel, rank, bank, row, column]  (Lesson 6)
  type_id     // Read = 0 or Write = 1 — nothing else enters through send()
  source_id   // which core sent it; -1 = "internal traffic" (crucial for v1, Lesson 8)
  size_bytes  // must be set, ≤ one DRAM transaction (32 B for HBM4/LPDDR5)
  arrive, depart              // timestamps: entered / finished  ← THE PRODUCT
  callback(Request&)          // "call me when it's done"
  // note what is ABSENT: no data pointer, no payload, no value.

how a frontend sends — src/ramulator/frontend/impl/memory_trace/loadstore_trace.cpp, tick()

tick():
  line = trace[cursor]                          // e.g. "LD 4096"
  req  = Request(line.addr, line.is_write ? Write : Read)
  req.size_bytes = memory_system.get_tx_bytes() // 32 B
  sent = memory_system.send(req)
  if sent: cursor += 1                          // advance ONLY on success ← backpressure!

Three idioms in those six lines appear everywhere in Ramulator, including the v1 DMA engine:

  • ① send() returns a bool — backpressure. Full queues ⇒ false ⇒ nothing happened; retry the same request next tick. Queues never overflow; senders stall. The MigrationEngine's read_stalls / write_stalls stats are literally counters of send()==false.
  • ② The request is copied in — the sender forgets it, except through…
  • ③ The callback. Completion is event-driven: when a read finishes, the controller invokes your lambda with depart filled in. latency = depart − arrive is where every latency statistic is born. In v1, a read's callback is what issues the matching write to the other tier — reads chain into writes with no other coordination.

Reads and writes are asymmetric — the most consequential fact in this course

The two v1 war stories, both born here. (1) The first MigrationEngine waited for its writes to really retire before declaring a block done — and deadlocked: under a steady GPU read stream, "whenever convenient" is never (0 blocks in 40,000 ticks). Fix: count writes done at accept — posted, like real DMA hardware. (2) In the ping-pong study, GPU-vs-DMA interference was dominated by write-drain batching, not bank conflicts; enlarging the write buffer 4× recovered most of the GPU's latency (1.50× → 1.18×) at zero migration cost.

One more door exists: priority_send(), for internal DRAM maintenance commands (refresh, forced precharges — type_id = −1). v1's DMA does not use it: the DMA sends ordinary reads/writes so it experiences ordinary queueing.

TRY IT — run the example again; connect Avg read latency = mean(depart − arrive) over every read whose callback fired, and Read requests = accepted send() calls.
RECAP
  • Request = address + type + size + arrive/depart + callback. No data.
  • send() == false means "queue full, retry next tick". Senders own the retry.
  • Reads complete later via callback (real latency); writes complete at accept and drain lazily in batches.
  • priority_send() is a separate door for maintenance commands.
Q3 — Why must LoadStoreTrace NOT advance its cursor when send() returns false?
The rejected request was not accepted — nothing holds it. Advancing would silently drop a memory access from the workload; retrying preserves it.
Q4 — A write's callback fired. Has the data reached the DRAM cells? Where is the request?
No (and no data exists anyway). The request sits in the controller's write buffer awaiting a write-mode drain. The callback fired at accept because writes are posted.
Q5 — Why did "wait until my writes retire" deadlock the first MigrationEngine?
Its 16-write blocks never filled the 32-entry write buffer past the 80% watermark, and the steady GPU read stream meant the "read queue empty" condition never triggered either — so write mode never engaged, the writes never retired, and the engine waited forever.

3The component framework: Python config → C++ objects

How ramulator.controller.HBM34(...) becomes a live C++ object tree with zero binding code — the machinery v1 extended.

Interfaces and implementations. Every component type has an abstract interface (IController, IScheduler, IMemorySystem, … and in v1 our new IDMAEngine) declaring what others may ask of it. Every concrete component inherits the interface plus a common Implementation base, and wires itself in with macros — which do double duty as runtime code and codegen markers:

the three magic macros — src/ramulator/base/base.h (usage pattern)

class FRFCFS : public IScheduler, public Implementation {
  RAMULATOR_REGISTER_IMPLEMENTATION(IScheduler, FRFCFS, "FRFCFS")
      // → self-registers in the factory → becomes ramulator.scheduler.FRFCFS(...) in Python
  void init() {
    RAMULATOR_PARSE_PARAM(m_knob, int, "knob").default_val(4)
      // → config parameter, auto-exposed as a Python keyword argument
  }
}
// inside a parent's init(): build children from the config subtree
RAMULATOR_CREATE_CHILD(m_scheduler, IScheduler)
RAMULATOR_CREATE_CHILD_LIST(m_controllers, IController)     // key = "controllers"

// ── the v1 extension: one component, TWO lists of the same interface ──
RAMULATOR_CREATE_NAMED_CHILD_LIST(m_hbm_controllers,   IController, "hbm_controllers")
RAMULATOR_CREATE_NAMED_CHILD_LIST(m_lpddr_controllers, IController, "lpddr_controllers")

There is no registry file and no binding code. A new scheduler is one .cpp file with these macros plus one line in a CMakeLists.txt (source lists are explicit — forget the CMake line and your component silently doesn't exist). The stock CREATE_CHILD_LIST hard-wires its config key to "interface name + s", so a component could own only one list per interface; the base die needs two lists of IController — hence the named variant, which is why the Python API has first-class hbm_controllers=[…] / lpddr_controllers=[…] arguments.

Lifecycle rules that bite (they bit us)

  • init() runs at the end of the constructor — parse params, create children. A child is fully initialized right after its CREATE_CHILD line.
  • setup() runs once after the whole tree exists — cross-component wiring only, and it must not recurse into children. v1's MigrationEngine finds its host here (in init() the parent is still mid-construction).
  • Codegen gotcha: a brand-new interface must land together with at least one implementation, or the generated Python package imports a subpackage that doesn't exist — and codegen itself imports ramulator. Chicken, meet egg.

Stats ride the same tree. m_stats.add("name", counter) in init(); collection walks the component tree and nests each child under its interface name. Same-interface siblings become a list distinguished by id — which is why v1 labels controllers "HBM Channel 0" / "LPDDR Channel 1" and experiment scripts filter stats["memory_system"]["controller"] by prefix.

TRY IT — open python/ramulator/dma_engine/migration_engine.py. Every Param(...) line corresponds 1:1 to a RAMULATOR_PARSE_PARAM in the C++. Nobody wrote that file by hand.
RECAP
  • Interface = contract; implementation = macro-registered class; factory + config tree builds everything recursively.
  • The macros are simultaneously runtime code and codegen markers. New component = one .cpp + one CMake line.
  • init(): params & children (in constructor). setup(): cross-wiring (after tree exists).
  • v1 added named child lists; stats auto-nest, same-interface siblings become an id-tagged list.
Q6 — New scheduler .cpp with all the right macros, rebuilt, but ramulator.scheduler.MyScheduler doesn't exist. Most likely cause?
The .cpp was never added to the relevant CMakeLists.txt — source lists are explicit, so the file was never compiled and its self-registration never ran. (Second guess: codegen didn't rerun — rebuild.)
Q7 — Why does MigrationEngine locate its IDMAHost in setup() rather than init()?
Children are created during the parent's own init(), so at the child's init() the parent is still mid-construction — casting it is not yet safe. setup() runs after the whole tree exists.

4Inside a memory controller

One controller = one DRAM channel: four queues, a scheduler, the write-mode watermarks, and one command per tick.

the watermark machinery, near-verbatim — src/ramulator/controller/controller_base.cpp, set_write_mode()

if not write_mode:
  if write_buf.size > 0.8 * write_buf.max  or  read_buf.size == 0:
    write_mode = true          // writes piled up, or nothing better to do
else:
  if write_buf.size < 0.2 * write_buf.max  and  read_buf.size != 0:
    write_mode = false         // mostly drained AND reads are waiting
// while in write mode: writes drain back-to-back, ARRIVING READS WAIT.

On send() the controller also implements two address-keyed shortcuts: read-after-write forwarding (a read hitting a buffered write's address is answered next cycle — the buffer is the freshest copy) and write coalescing (a second write to a buffered address merges). v1 consequence: the composite keeps req.addr global for both GPU and DMA traffic so these shortcuts behave consistently across the two streams.

one tick, seven steps — src/ramulator/controller/impl/generic_ddr_controller.cpp, tick()

tick():
  1  m_clk += 1;  serve_completed_reads()   // any pending read with depart ≤ now → fire its callback
  2  refresh_manager.tick()                  // may inject maintenance via the priority buffer
  3  pre_schedule hooks (row policy, plugins)
  4  candidate = pick from: active > priority > (write_mode ? write_buf : read_buf)
       within a buffer, the scheduler chooses (FRFCFS: ready-now beats older)
  5  cmd = device.get_preq_command(candidate)    // "what does it need next?"  (Lesson 5)
       if not device.check_timing(cmd): try another candidate
  6  device.issue_command(cmd)               // AT MOST ONE DRAM COMMAND PER TICK
  7  if cmd was final (RD/WR): retire — reads get depart = now + read_latency
     if cmd was ACT: promote request to the active buffer;  update stats; on_issue hooks

So a single read on a closed bank takes multiple trips through this loop: tick k issues ACT, ticks later RD issues, and read_latency ticks after that a future tick's step 1 fires your callback. (HBM's HBM34 controller is the one exception to "one command per tick": HBM has two command buses — row and column — so it can issue one of each per cycle, with half-cycle pairing rules.)

RECAP
  • One controller = one channel = 4 queues + scheduler + device; one command per tick (two for HBM's dual bus).
  • Write mode (0.8 / 0.2 watermarks) batches write drains; reads wait during drains — deadlock source and dominant interference mechanism.
  • Forwarding/coalescing key on req.addr. Read completion happens in a later tick's prologue.
Q8 — Saturating read stream + a 5% trickle of writes: when do the writes actually reach DRAM?
Only when the read queue momentarily empties (a trickle never reaches the 80% watermark). Under a truly gapless read stream they can starve for a long time — which is exactly the risk the high watermark bounds: once writes pile past it, a drain is forced regardless.
Q9 — Why does the active buffer outrank even the priority buffer?
An active request already spent an ACT — its row is open. Not finishing it risks the row being closed by other activity, wasting the activation and paying it twice. Finish what you started.
Q10 — avg_read_latency = 74 (LPDDR5) vs 196 (HBM4) in the same simulation. Real-time comparison?
74 × 1.25 = 92.5 ns vs 196 × 0.25 = 49 ns — the HBM controller is ~1.9× faster in real time.

5The DRAM device model

The device answers two questions every tick: "what command does this request need next?" and "may it issue this cycle?"

The model is authored in Python, not C++. Each standard (python/ramulator/dram/hbm4.py, lpddr5.py, …) declares, as data: the hierarchy (levels), the command set, the timing rules (e.g. TimingConstraint(level="Bank", preceding=[ACT], following=[RD], latency=nRCD) — "a RD must wait nRCD after an ACT, at bank scope"), and presets: org presets fix capacity, timing presets fix speed. You configure by picking presets and overriding — LPDDR5(org_preset="LPDDR5_16Gb_x16", timing_preset="LPDDR5_6400", rank=2): that one rank=2 doubled v1's far-pool capacity per channel. (channel= is deliberately forbidden: channel count = how many controllers you instantiate — the convention that made v1's "LPDDR channels = list length" natural.) At build time the code generator resolves everything to integer ticks and bakes it into C++; at runtime there are no JEDEC lookups, just integer comparisons.

What does "preq" mean, and does it return only ACT/PRE? preq = prerequisite, better read as "the next required command on the path to my goal." Crucially, it can and often does return RD/WR themselves — when nothing stands in the way, the next required command is the goal. So the return is always an issuable command, never "nothing to do": hit → RD, closed → ACT, wrong row → PREpb. That makes the controller's tick uniform: it issues whatever preq returns, then checks preq == final_command — that equality is the signal the request can retire.

Naming trap: preq (prerequisite — a question/answer) is not a command. PRE (as in PREpb/PREab) is precharge — a real command that closes a row. A precharge can be the answer to the preq question, which is exactly where they're easiest to confuse.
Reading the hierarchy — what is "Sid"? Sid = Stack IDentifier: HBM's version of DDR's "rank." An HBM device is a vertical tower of DRAM dies (4-Hi, 8-Hi…), and the channel wires are fixed by the standard no matter how tall the tower gets. So stacking higher forces more dies to share each channel's wires — and SID is the bit that selects which shared die responds.

That's why sid grows with height: 4-Hi → sid=1, 8-Hi → sid=2, 16-Hi → sid=4. sid=1 does NOT mean "one die" — it means "one choice, i.e. no choice": each channel reaches exactly one die, so no selector bit is needed. Doubling the dies (8-Hi) makes two dies share each channel → a real 2-way choice → 1 SID bit → capacity doubles with zero added wires. (A level with count 1 is Ramulator's way of saying "this dimension is trivial here" — same as rank=1 in the LPDDR preset. And note: SID counts dies-per-channel, not floors — don't let the word "Stack" mislead you.)

talking to the spec from C++ — the pattern every extension uses

init():
  m_cmd_rd  = spec.get_command_id("RD")      // throws if the standard lacks it
  m_nCL     = spec.get_timing_value("nCL")   // resolved integer, in ticks
  m_has_rda = spec.has_command("RDA")        // optional features: check with has_* first
// rule: string lookups ONCE in init(), cached as integers — never on the hot path.

Q11 — Two back-to-back reads, same row of same bank: what commands issue? Same bank, different rows?
Same row: ACT, RD, RD (second read is a hit — one command). Different rows: ACT, RD, PREpb, ACT, RD (conflict — close, reopen).
Q12 — Why is the row map lazy instead of an array over all 2^14 rows?
Only a handful of rows are ever open at once; an array would waste memory and time. The map holds only opened rows — a closed bank is an empty map.
Q13 — Where would "at most N activates per window per rank" live, and what extra state does it need?
At the Rank level of the node tree (it spans all banks of the rank), with a rolling window of the last N ACT issue times — exactly how nFAW (N=4) is implemented.
Q14 — goal = WR, and the correct row is already open. What does get_preq_command() return, and what does the controller do right after issuing it?
WR itself (a hit — no prerequisite remains). Since the issued command equals final_command, the controller retires the request; for a write that means firing its callback immediately, because writes are posted.

6Address mapping: one integer becomes coordinates

Two mappers slice the address bits in sequence — and the bit layout is a first-order performance decision.

Reading the alphabetical name — and its trap

The name is a recipe spelled MSB→LSB: Row-Bank-Rank-Column-Channel. But here is the catch that confuses everyone: the name has only 5 syllables, while HBM4 has 7 levels (Channel, PseudoChannel, Sid, BankGroup, Bank, Row, Column). So the name cannot list them all — it is a legacy DDR3-era mnemonic. The code ignores the name and instead places every sub-channel level in the standard's declared hierarchy order. So "BaRa" is not two specific fields — it is shorthand for "all the bank-ish/rank-ish middle levels, whatever they are." For HBM that middle zone expands to {PseudoChannel, Sid, BankGroup, Bank}.

Never trust the name for bit positions. No DDR-era name mentions BankGroup (postdates DDR3) or Sid/PseudoChannel (HBM-only). The authoritative source is m_addr_bits — the spec's levels list — not the syllables. The name reliably tells you only the two endpoints: Row on top, Column+Channel at the bottom; everything bank-ish lives in the middle in hierarchy order.

exact bit layout, HBM4_32Gb_8Hi, 30-bit intra-channel address (verified against the real mappers)

Same 30 bits, two lenses. The only field both schemes agree on is Column (both park it at [5:10)). Everything above it is reinterpreted — which is why the identical address 357,664 decodes to PC1/BG1/Bank3/Row5 under RoBaRaCoCh but PC0/BG0/Bank0/Row349 under ChRaBaRoCo. Read each column of the table with the odometer rule (low bits change fastest): RoBaRaCoCh keeps the bank-ish levels low (fast interleave, Row rarely ticks → row hits); ChRaBaRoCo shoves them to the top and drops Row low (a stream crawls through rows of one bank).

v1's steering + per-pool interleave — src/ramulator/memory_system/impl/hbm_lpddr_basedie_system.cpp, send()

send(req):
  if req.addr < near_size:                 pool = HBM;   pool_addr = req.addr
  else if req.addr < near_size + far_size: pool = LPDDR; pool_addr = req.addr - near_size
  else: throw "address outside the unified address space"

  // interleave within the pool (same math as CacheLineInterleave)
  ch    = (pool_addr >> log2(tx)) & (pool_channels - 1)
  intra = pool_addr with the channel bits spliced out
  req.intra_channel_addr = intra
  return pool[ch].send(req)      // controller's addr_mapper decodes intra → bank/row/col
The v1 subtlety worth internalizing: because both pools interleave at 32 B granularity, address-range separation is not resource separation — any large region spans ALL channels of its pool, and under RoBaRaCoCh two distant regions share the same banks. That is physically faithful, and it is why GPU-vs-DMA isolation had to come from the write-path levers (Lesson 4), not from address placement.

RECAP
  • Stage 1: channel bits just above the tx offset (interleave). Stage 2: the controller's mapper slices bank/row/column.
  • RoBaRaCoCh: streams rotate banks (good), distant regions share banks. ChRaBaRoCo: the reverse trade.
  • v1 steers near/far by boundary, then interleaves per pool. Address separation ≠ channel/bank separation.
Q14 — Under RoBaRaCoCh, a 64 B-strided read stream on a 2-channel 32 B-tx system hits how many channels?
One. The channel bit is address bit 5; a 64 B stride holds bit 5 constant. (Our first mini-test hit exactly this: "HBM Channel 1 reads = 0".)
Q15 — You want the GPU to stream fast AND the DMA in disjoint banks. Why does neither stock mapper deliver both with contiguous regions?
Fast streaming needs bank bits low (rotate banks within a small span — RoBaRaCoCh); disjoint-bank regions need bank bits high (ChRaBaRoCo). One bit position can't be both. You'd need a custom/hashed mapper or channel-level partitioning — a v2 topic.

v1's per-tier ticking — src/ramulator/memory_system/impl/hbm_lpddr_basedie_system.cpp, tick()

tick():
  tick_count += 1
  if dma: dma.tick()                          // DMA decides at the HBM rate
  for c in hbm_controllers:   c.tick()        // every tick        (0.25 ns domain)
  if tick_count % lpddr_tick_divider == 0:    // auto-derived: round(1.25 / 0.25) = 5
    for c in lpddr_controllers: c.tick()      // every 5th tick    (1.25 ns domain)

Because every controller counts time in its own ticks, per-controller stats stay internally consistent — but you must convert to nanoseconds before comparing across tiers (Lesson 1's 196-vs-74 trap).

RECAP
  • tick period = tCK / tick_multiplier: 0.25 ns (HBM4-8000) vs 1.25 ns (LPDDR5-6400).
  • The fe:mem ratio is both "CPU speed vs memory speed" and the experimenter's offered-load knob.
  • v1 nests a second gear inside the memory system: LPDDR ticks every 5th composite tick, auto-derived and overridable.
Q16 — What offered bandwidth does fe:mem = 1:8 produce on a 4 GHz-tick, 32 B-tx system?
One 32 B request per 8 memory ticks = 0.5 G req/s × 32 B = 16 GB/s.
Q17 — HBM4-16000 has tCK 250 ps (tick 0.125 ns). What LPDDR5-6400 divider would v1 auto-derive?
1.25 / 0.125 = 10.

8The v1 design, guided — everything composed

Open hbm_lpddr_basedie_system.cpp and migration_engine.cpp and read along: nothing left is mysterious.

the MigrationEngine, whole logic — src/ramulator/memory_system/dma_engine/impl/migration_engine.cpp

tick():                                       // called by the composite, HBM rate
  retry stalled writes                        // send()==false queue — L2① backpressure
  if idle and gap elapsed and blocks remain:  open_next_block()   // cursor or seeded random
  while inflight_reads < cap and block not fully read:
    req = Request(src_pool_addr, Read, source_id = -1, callback = on_read_complete)
    host.dma_send(src_tier, req)              // false → read_stall, try next tick

on_read_complete(req):                        // L2③ — fired by the src controller
  write = Request(dst_pool_addr, Write, source_id = -1)
  host.dma_send(dst_tier, write)              // accepted = DONE (posted, L2.3/L4)
  if all writes of the block accepted: block complete → stats, arm gap

That pseudo-code, step by step — the moving-company picture

Picture a moving company relocating books from an old apartment (LPDDR) to a new one (HBM) — but, per Lesson 1, no real books exist; we simulate only the timing. Three rules force the whole design:

  • The truck is tiny — one 32 B box per trip. So a 512 B block = 16 boxes = 16 reads + 16 writes. Never "move the block at once."
  • Pick up before you deliver — you cannot write box i to HBM until its read from LPDDR has completed. That is why the write is issued inside the read's callback (on_read_complete), not in a loop.
  • Doors lock — a loading dock may be full → dma_send() returns false → try that trip again later. (Backpressure, Lesson 2.)

So the two functions are the two halves of one trip: tick() is the dispatcher that launches pickups; on_read_complete() is what happens when a pickup finishes — it launches that box's delivery.

Watch the three rules: 4 separate reads + 4 separate writes (tiny truck); write 0 only after read 0 completes (pick-up-before-deliver); ticks 2–3 the dispatcher wants to issue more but holds at 2 — the max_inflight_reads cap, not the block size, is the brake. And block completion is decided in the write path (tick 8): the instant the 4th write is accepted, writes_done == reads_per_block → done. Not when reads finish — when the last write is accepted (posted-write rule).

Two details the code adds around this core: tick() drains any stalled writes first (a stuck delivery blocks the block from closing — finish in-flight work before starting more), and after a block completes it may rest inter_block_gap ticks before the next (the migration-rate throttle from the ping-pong study).

Q — In the trace, why is read 2 issued on tick 4 and not tick 2?
On ticks 2–3 the in-flight count is already 2, hitting max_inflight_reads. A slot frees only when read 0 completes on tick 4 (on_read_complete does inflight−−), so tick 4's dispatcher loop can finally launch read 2. The cap, not the block size, was the limit.

The three design decisions, each traceable to a lesson:

  • Posted writes (block done at write-accept): forced by Lesson 4's watermarks — waiting for retirement deadlocks under foreground reads. Matches real DMA hardware, and the accepted writes still exert genuine write-buffer pressure (the real interference).
  • source_id = −1: controllers keep per-core stat arrays sized by the frontend's core count and index them by source_id — a DMA "fake core id" would corrupt them. −1 marks internal traffic; dma_send() enforces it.
  • DMA bypasses send(): migration must consume zero GPU-link bandwidth (the patent's requirement). Entering through dma_send(), DMA traffic shares only the DRAM controllers with the GPU — the physically real contention point, and exactly what the ping-pong study measured.
