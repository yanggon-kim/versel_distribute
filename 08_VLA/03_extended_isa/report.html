Our ISA Extensions: 28.55 ms → 8.15 ms per Step, and How They Differ from Prior Designs

Part III measured why stock LPDDR5-AiM loses on the π0 Action Expert: every in-bank fetch feeds one vector, one accumulator, one register mode. This page turns that breakdown into eight problem statements and implements the fixes on a simulator branch (vla-aim-ext) under an AF-free LPDDR-PIM premise (no in-DRAM activation function — the GEMV-only scope of every disclosed LPDDR-PIM, incl. Samsung’s LP5X-PIM Sim): three ISA/controller extensions (P1, P4, P7) + two software fixes, measured: 28.55 → 8.15 ms per step at Orin memory parity (3.5×), and 5.26 ms at 32 channels (1.7× the XPU’s theoretical bandwidth floor). P2 (in-memory softmax) and P8 (in-bank write-back), which require AF-class hardware, are documented as GDDR-AiM-only alternatives, excluded from the headline. With hybrid stale/fresh pipelining, all but the final fresh-KV denoising steps leave the robot’s critical path (378 ms cycle, 2.65 Hz).

2P1 — MAC_ABK_MV: teaching one fetch to feed a whole token tile

The core insight from Part III’s crossover: the XPU wins because its cache lets one weight read serve all 51 tokens. P1 gives AiM the same amortization, in-bank.

Depth note. The shipped design sweeps V = 26 token vectors per fetch — the tokens one channel group owns (§Why 26, below). The toy machine, the three-frame figure and the “running the clock” walkthrough use a 16-token tile because it fits on a screen and matches the 16-wide GPR word that stock RD_MAC already produces. Every mechanism is identical at either depth; only the slot count changes.

The idea, without any hardware

Strip away channels, banks, commands and buffers. A projection is just this: Y[t][j] = Σk X[t][k] · W[j][k], with S = 51 tokens, N = 2,048 outputs and K = 1,024 inputs. Three loops, and the only thing that separates stock from P1 is where the token loop sits relative to the read of W.

(a) STOCK ORDER — token loop outermost
for t in 0 .. S-1:                 # 51 tokens
    for j in 0 .. N-1:             # 2,048 outputs
        acc = 0                    # ONE accumulator
        for k in 0 .. K-1:         # 1,024 inputs
            acc += W[j][k] * X[t][k]      # W[j][k] is read HERE
        Y[t][j] = acc
# every W[j][k] is read S = 51 times: the weight loop is inside the token loop
(b) P1 ORDER — tile the token loop by V and sink it BELOW the read of W
for t0 in 0 .. S-1 step V:         # V = 26 → 2 tiles cover 51 tokens
    for j in 0 .. N-1:
        acc[0 .. V-1] = 0          # V accumulators, one per token in the tile
        for k in 0 .. K-1:
            w = W[j][k]            # read ONCE …
            for i in 0 .. V-1:     # … and reused V times
                acc[i] += w * X[t0+i][k]
        Y[t0 .. t0+V-1][j] = acc[0 .. V-1]
# every W[j][k] is read ceil(S/V) = 2 times instead of 51

This is an ordinary register-tiling transform, and it is legal because the token dimension is a reduction-free outer product: token t’s result never depends on token t’s neighbours. What it costs is exactly two things: V partial sums must stay live while k advances, and V input vectors must be readable while w is held. A CPU or GPU does this in registers and cache without anyone noticing. Stock AiM cannot, because it has one accumulator per bank and one vector in the Global Buffer — so the inner i loop has nowhere to live, and the token loop is forced back to the outside. P1 is that storage, and nothing else.

The problem in miniature: a toy machine, cycle by cycle

Everything above compresses into one question: which dimension of the GEMM does each piece of hardware parallelize, and which dimension is left to the command stream? To make that visible, shrink the machine until every operand fits on screen. Toy machine: 2 banks, each PU has 2 multipliers (one fetch = one 2-element k-chunk); the command bus issues one ISR per 4-cycle slot (nCCD). Toy workload: Y = X·Wᵀ with a 4×4 weight matrix (output rows r1–r4, K=4) and 3 tokens x1, x2, x3 — the miniature of the AE’s 12,800×1024-class projections against S=51 tokens.

Seen this way, P1 is simply the GEMV → GEMM upgrade at the ISA level: stock computes W_chunk[16×16] × x[16] → y[16] per command; P1 computes W_chunk[16×16] × X[16×16 tokens] → Y[16×16] — with the M dimension realized as 16 beats in time on the existing multipliers rather than new silicon. Reuse per fetched byte goes from 1 to 16 FLOPs, which is exactly the command-count reduction; the remaining 4× re-fetch (4 tile passes) and the once-per-pass fills are what the software fixes of §7 attack next.

  • The new loop is the i loop, innermost, inside each column fetch, run by the PU — not by the host and not by the DMA. The row-group loop already existed in stock. At V = 26 the tile is one slice, so the slice loop that a 16-deep file needed (16 + 10) is gone.
  • The column stays outside the beats. Fetch once, then sweep the 26 resident tokens. Reversed, every beat would need its own fetch and nothing would be saved.
  • Row-groups double from 8 to 16 because token-parallel ×2 leaves 8 channels per group: one sweep covers 16 banks × 8 channels = 128 outputs instead of 256. Each group holds a full weight replica and computes all 2,048 outputs for its own tokens.
  • Deeper nesting, far less work. Loop depth costs nothing; trip count × per-iteration cost does. Per channel for q_proj: stock 51 × 8 = 408 sweeps → 26,112 column fetches, 408 drains, 408 row switches; P1 1 × 16 = 16 sweeps → 1,024 fetches, 16 drains, 16 row switches. That is 4 fetches per output produced versus 0.16. The i loop added one level and removed a factor of 26 from an outer one.
  • Token-parallel is fetch-neutral per channel. Halving the tokens per group halves the slice count and halving the channels doubles g, so with or without the split each channel issues 16 sweeps (the no-split trace: G = 1, rgroups = 8, 2 slices of 26 → 16). Its gain is the fill stream: each group pushes 26 vectors through its own pins instead of 51, and the two groups do it concurrently (§6).

Charged honestly. The simulator issues MAC_ABK_MV at MAC16 timing (4 cycles) and the composition adds the PU occupancy analytically: 16 beats of 16 lanes at AiM’s fabbed 1 GHz = 256 MACs = 16 ns = 25.6 DRAM cycles per column, i.e. +21.6 cycles per MAC_ABK_MV column on top of the simulated stream. That is why the 16-channel layer is 0.486 ms and not the simulator’s raw 0.219 ms at V = 16. At the shipped V = 26 the same charge is 26 beats = 416 MACs = 26 ns = 41.6 cycles per column (+37.6), and the layer is 0.396 ms on a raw 0.156 ms. No multiplier is added; the PU is simply kept busy.
What the beats assume. A beat is 1 ns (1.6 cycles) vs a column slot’s 2.5 ns (4 cycles) because it never touches the DRAM column path: the weights stay latched in the PU and only the activation operand changes, read from the Global Buffer. That requires the GB and its broadcast bus to deliver a fresh 32 B slice to all 16 PUs every PU cycle. The fabbed GDDR6-AiM already needs this rate — at its rated 1 TFLOPS every 1 ns column command needs a new 32 B GB slice — but from a 2 KB buffer read sequentially; ours is 52 KB read at a fixed stride. If the GB sustained only the column rate, the design would behave as D = 1 (15.4 ms, 1.9× over stock instead of 3.5×). Derivation and caveats: Part III §7, “A third clock”.

Why 26, when there are 51 tokens? (measured)

Two knobs. The command depth V — how many token vectors one MAC_ABK_MV sweeps, and therefore how many slots the accumulator file needs — was first set to 16 for hardware fit (one RD_MACB burst = one 32 B GPR word), then swept. The GB tile capacity is separate and matters little: 32 KB (16 vectors) measures 9.87 ms/step vs 9.77 with 128 KB (+1%); depth V = 26 then takes it to 8.15. Depth is what matters.

The generator takes V as a parameter (default 16, so every earlier trace is byte-identical) and each depth was simulated at 16 channels; the composition charges the PU honestly, since one command asks a bank for V × 16 MAC and a 16-lane PU at 1 GHz needs V ns for it. The sweep reproduces the earlier 9.77 ms V = 16 point exactly, and V = 26 is the 8.15 ms headline.

  • Most of the gain arrives by V = 8–13. 1 → 8 is 3.0×; 8 → 13 another 1.26×; everything past 13 is worth at most 1.09× more.
  • Above V = 8 the binding term is padding, not amortisation. Mode switches, row switches and drains are already ~20× down at V = 13. What separates 9.77 from 8.15 ms is that 26/16 = 1.23 of the MAC work at V = 16 multiplies padded slots.
  • The measured optimum is V = 26 — the tokens each channel group owns — at 8.15 ms/step, 1.20× better than the original V = 16, for 52 B of accumulator file per bank instead of 32 and no extra GB. Without token-parallel the same rule gives V = 51 and 8.68 ms (1.36×).
  • Depth must match the group, not the token count. V = 51 with token-parallel ×2 is the worst configuration above V = 4 (12.14 ms): half of every 51-slot file sits idle.
  • So V = 16 is defensible, not optimal. It is what the hardware likes — power-of-two slot index, and one RD_MACB burst is exactly one 32 B GPR word, the format stock RD_MAC already produces — and it leaves 1.20× on the table. A V-matched design pays a wider slot index and a burst count that no longer equals the GPR width.

A non-power-of-two depth instead costs decode tidiness: a 5-bit slot index and a RD_MACB that no longer bursts exactly one 32 B GPR word per slot.

Why the multiplier width matters at all. One MAC_ABK_MV asks a bank for 16 lanes × 26 vectors = 416 MAC. Pipelining does not help: a pipelined PU already sustains one 16-lane dot-product per cycle, so the 416 MACs are a throughput requirement, not a latency one. At AiM’s fabbed 1 GHz a 16-lane PU needs 26 ns — 10.4× the 2.5 ns column slot — so the controller throttles and the command occupies 41.6 cycles. Widening the array shortens that linearly; nCCD becomes the limiter again only at ~166 lanes (416 MAC in one 2.5 ns slot), so even 128 lanes are still PU-bound at this depth.

The arithmetic needs far less depth than the bookkeeping. With a 16-lane PU, any V ≥ 3 vectors per command saturates it at 1.6 cycles/vector (vs stock’s 4.0) — so the free 2.5× on the MAC term needs only V = 3. We use V = 26 not for arithmetic but because it divides the WR_BIAS/RD_MACB drains, GB refills and row activations by 26 — the overhead terms that were 54% of the stock layer (Part III §8) — and because 26 is exactly the tokens one channel group owns, so no slot is ever padded.

Two costs, priced separately — and the cheap one carries most of the win. The storage additions (32 B accumulator file per bank + RD_MACB + the GB tile, ~1% of die) eliminate the WR_BIAS/RD_MAC/TMOD/row-thrash storm all by themselves: 3.5× over stock with zero added multipliers, and 16.7× over today’s measured stack. Widening the array is an option, not part of the design: 2× already clears the realistic XPU bound (1.10×) and 4× reaches 1.38×, but §8 shows the end-to-end gap between 16 and 64 lanes is only 1.02× — once the expert is overlapped it is off the critical path, so paying 4× the multiplier area for 2% of system throughput is a poor trade. Feasibility: P3-LLM’s synthesis takes the same 16→64 multiplier step for +9% of PCU area (7.7→8.4 mm²) — the multiplier array is not the dominant PCU term; their larger +17.5% total comes from format decoders and register files that we do not add. Samsung’s Aquabolt-XL fabbed a far heavier per-bank programmable PCU (CRF/GRF/SRF) in HBM2 at only +5.4% device power. Our deltas keep AiM’s philosophy: no cell-array or sense-amp changes, no programmable control, no numeric-format change, ISR-only interface extension. LPDDR-specific risk: mobile thermal may cap the PU clock — at 500 MHz the 64-lane point degrades to the 32-lane row above.

Why it is efficient, in the terms of Part III §1. LPDDR5 is a one-column-per-4-cycles machine, and AiM turns each column slot into 16 banks’ worth of work. 3P4 — LOOP n … ENDLOOP: the host issues a layer once — plus the supporting cast (P3, P7, P8)

P1 fixed what happens inside the DRAM. Someone still has to send the commands, and that is the host. P4 takes the host out of the loop.

The problem P4 solves

Every time the host hands the memory controller a batch of ISRs it pays a kernel launch — the driver/dispatch handshake that gets a piece of work started. We charge it at 20 µs [assumption, swept 5–50 µs in Part III]. A layer of the Action Expert alternates between AiM work and small host-side kernels (norms, RoPE, softmax, GeLU⊙, residuals), and every host kernel is a SYNC point at which the ISR stream stops and a new launch is needed to restart it:

one layer, as the trace is laid out (the six SYNC points are the six host segments)
SYNC  # HOST: rmsnorm1          → AiM: q_proj, kv_proj
SYNC  # HOST: rope              → AiM: attention (scores, context)
SYNC  # HOST: softmax           → AiM: o_proj
SYNC  # HOST: residual_rmsnorm2 → AiM: mlp_gate, mlp_up
SYNC  # HOST: gelu_gate_mul_up  → AiM: mlp_down
SYNC  # HOST: residual
# 6 launches x 20 us = 120 us per layer; x 18 layers = 2.16 ms per step -- 26 % of an 8.15 ms step spent starting things

Even with P1, the AiM segments are now so short that this fixed cost stops being noise. It is the second-largest term left after P1 (the ablation in §5: 12.36 → 10.52 ms when P4 is added).

The concept

LOOP n … ENDLOOP marks a block of ISRs that the memory controller buffers in a small macro buffer and replays n times by itself. The host issues the block once — one launch — and the controller paces everything after that, including the SYNC points: at each one the DMA blocks, the host’s own kernel runs, and the controller resumes the block without the host re-issuing anything. Samsung’s HBM-PIM stores micro-kernels in a command register file and replays them with a zero-cycle JUMP; P4 is the trace-level equivalent, but with one difference that matters: Samsung’s CRF amortizes instruction storage while every non-JUMP instruction still costs one host column command, whereas P4 removes the host from the loop entirely (Part III-2 §2).

Fig. 3a — Where P4 lives. Nothing on the DRAM die changes; the macro buffer is KB-scale SRAM in the SoC’s memory controller. The channels cannot tell whether the stream came from the host or from the buffer.

Step by step: one layer under P4

  1. Issue once. The host writes LOOP n, the layer’s ISR body and ENDLOOP into the controller — one launch, 20 µs.
  2. Capture. The controller frontend copies every line between LOOP and ENDLOOP into the macro buffer (in the simulator: load-time expansion in the trace frontend, m_lines). Nesting is rejected; an EOC inside a body is rejected.
  3. Replay. For each of the n iterations the DMA reads the body line by line at one ISR per cycle — exactly the pace a host-fed FIFO had. Column unrolling, preconditions (ACT/PRE), TMOD guards: all unchanged.
  4. SYNC inside the body. The DMA blocks, the host’s kernel (norm, RoPE, softmax, GeLU⊙) runs on its own data, then the controller continues from the next buffered line. The host does not re-issue the stream; it only signals completion.
  5. Done. After the n-th ENDLOOP the frontend falls through to the lines after the block (EOC).
Fig. 3b — The same layer, issued two ways. P4 does not shorten any AiM segment; it removes five of the six launches per layer.

What it costs, what it buys

  • Hardware: a macro buffer sized for the largest loop body — KB-scale SRAM in the SoC’s memory controller, nothing on the DRAM die. Two decode rules: no nesting; EOC inside a body is rejected at load.
  • Timing-neutral in the memory system. The DMA still decodes one ISR per cycle; the channels see a byte-identical stream. Verified: a 10×-unrolled body and its LOOP form simulate to the identical 6,644 cycles.
  • Host stream: a layer shrinks from 17.7 k host ISRs to ~2.5 k (7×) — 17,717 → 2,475 lines. Most of that shrink is P1 issuing fewer commands; P4 is what lets one launch carry them.
  • Measured: 12.36 → 10.52 ms per step at 16 channels when P4 is added on top of P1 (§5) — 1.17×, for zero DRAM change and no arithmetic. Sensitivity to the launch assumption is in Part III (5 → 50 µs).
  • Opens a door: with the host out of the issue loop, a self-running denoising step (an Euler update at the DMA) becomes plausible — not evaluated here.

The supporting cast

P3 — per-channel mode partition (CFR 3)

A 32-bit mask CFR marks each channel AiM-mode or conventional-mode, scoping Part III’s mutual exclusion to within a partition. Its value is not layer latency — it is the enabler for §8: streaming next-observation KV into masked channels while the others denoise, and letting the XPU use idle AiM capacity as ordinary memory.

P7 — WR_TILE descriptors

Stock activation loads issue one ISR per 32 B column (8.2 k/layer). WR_TILE opsize GPR mask bank row lets the DMA unroll a whole tile write from one descriptor — the write stream itself already paces at bus rate (unit trace: 286 = 286 cycles), so the win is command-stream compression (64×) and freeing the decode slot the P1-improved layer now notices.

P8 — COPY_MACBK write-back (GDDR-AiM alternative — excluded from the headline)

Excluded under the LPDDR-PIM premise: the in-bank gate⊙up chain consumes a post-AF gate. Without an AF unit the gate tile must exit to the host for GeLU regardless, so the write-back path saves nothing — the AF-free headline computes GeLU·gate⊙up on the host and re-uploads h (priced in §6). Design kept for AF-equipped substrates: stock PIM results can only exit through GPRs toward the host, so gate⊙up ran on the host and the h tile (the layer’s largest load, 4.1 k writes) was re-uploaded for down-proj. COPY_MACBK writes the (post-AF) accumulator file into a bank row (WRCP timing class): gate and up results land in adjacent banks, EWMUL multiplies them in place, and down-proj consumes h without the host ever seeing it.

P2 — softmax without leaving the memory (GDDR-AiM alternative — excluded from the headline)

Excluded under the LPDDR-PIM premise. Everything below relies on the AF block (LUT + interpolation + scalar multiplier) that GDDR6-AiM carries and no disclosed LPDDR-PIM does — Samsung’s LP5X-PIM Sim (arXiv:2606.00636) models a GEMV-only device. We keep the design and its measurements as a documented alternative for AF-equipped substrates: on the old GDDR-style chain it bought 0.25 ms/step at 16 ch. The AF-free headline instead keeps softmax on the host, which costs one host segment + SYNC per layer and is priced into every §6 number.

6The last bottleneck: activation broadcast — and its sweet spot

After P1+P4+P7, the layer profile flips: WR_GB activation streaming dominates at 61% of the AiM layer — and it does not scale with channel count, because the same token tile is broadcast serially into every channel’s GB through its 12.8 GB/s port. The bound is physical: you can only (a) send fewer bytes, (b) send different bytes to different channels, or (c) add GB write ports (hardware).

SW — the two fixes, as a block diagram

“SW” means software: no hardware is added or changed. Both fixes are decisions about which command stream the trace generator emits. They attack the same physical fact — the activation tile enters each channel’s GB through that channel’s own 12.8 GB/s pins, one 32 B vector per WR_GB column — from two sides: dedup sends the tile fewer times, token-parallel sends each channel a smaller tile.

Fig. 6a — The broadcast fix. Token-parallel makes each channel’s tile half as long; dedup makes it arrive half as often. Weight replication is the price: memory capacity, which the 64 GB LPDDR pool has to spare.

Step by step: q_proj then kv_proj, one layer

  1. Split the tokens, not the outputs. Group 0 (channels 0–7) owns tokens 0–25; group 1 (channels 8–15) owns tokens 26–50. Each group holds a complete copy of every weight matrix, so each computes all N outputs for its own tokens — no cross-group reduction is ever needed.
  2. Fill both GBs at once. The generator builds the two groups’ command lists separately and round-robin merges them (merge_groups), so the stream alternates 0xff, 0xff00, 0xff, … The single in-order DMA still issues one ISR per cycle, but consecutive ISRs land on different channel buses, so the two fills proceed concurrently instead of back to back.
  3. Sweep q_proj in both groups, interleaved the same way: WR_BIAS / MAC_ABK_MV / RD_MACB per row-group, each group against its own replica.
  4. Do not refill. kv_proj consumes the identical normalized tile. It is still resident in every GB, so its fill is skipped (skip_fill=True → fill=False) and the sweep starts immediately. The same holds for mlp_gate → mlp_up.
  5. Host reassembles by token index. Group 0’s results are rows 0–25 of Y, group 1’s are rows 26–50 — a placement, not a computation.
Fig. 6b — The fill stream before and after. Token-parallel shortens each fill and overlaps the two; dedup removes the second one entirely.

  • Why replicate the weights rather than split them? Splitting outputs across groups would leave every group needing every token (the fill problem unchanged).   • Dual-use memory: the AiM channels ARE the platform LPDDR. With P3 partitioning the XPU keeps full-bandwidth access for the 95% of the cycle the AE is idle — the difference between “adding a PIM accelerator” and “the memory you already have can denoise.”
  • Micro-pipelining: host post-processing of layer ℓ overlaps AiM’s layer ℓ+1 (disjoint data) — a further −10% if wanted.
Bottom line of the series. A flow-matching VLA’s Action Expert is mis-matched to both a GPU (too little reuse) and to GEMV-era PIM (too much). Three AF-free ISA extensions sized for S=51 — a multi-vector MAC with an accumulator file, controller macros, and tile descriptors — plus two software scheduling fixes make LPDDR-PIM 2.9× faster than its stock self and 16.7× faster than the stack robots run today, with zero added arithmetic, and, with pipelining, remove action generation from the robot’s critical path entirely.

8Energy, and what a fair baseline looks like

Latency is half the deployment story on a battery-powered robot. Per-command energy follows the CENT power calculator shipped with the simulator (GDDR6-AiM constants, conservative for LPDDR5): array/activate/MAC energies from command counts, DQ at 5.5 pJ/bit, controller and standby power, and an AE-phase GPU power of 20 W [ASSUMPTION; the paper measures 20–40% SM utilization; swept 15–30 W].

Energy per step

  • Why stock AiM loses on energy too: 35.5 ms of standby burn (127 mJ) plus per-command overhead traffic. Slowness is itself an energy cost.
  • Honest caveat: against the theoretical-floor XPU, extended AiM is ≈1.21× worse on energy — in-DRAM fp16 MACs cost more per op than tensor cores (3.5 pJ/MAC here), and MV still re-fetches weights per tile pass. A 64-slot accumulator file (future work) would cut the dominant MAC term further. Combined figure of merit today: 0.77× latency × 1.36× energy ≈ 1.05× energy-delay product against that hypothetical rung (269× against the measured stack) — plus the freed XPU.

What makes a baseline fair

  • What a fair baseline is NOT: more LPDDR. The XPU shares the memory system, and its floor scales perfectly with channels (32 ch ⇒ 1.57 ms) while the AiM curve scales sub-linearly — adding channels helps the baseline more than the design. The legitimate framings are the three-tier baseline (vs measured 543 ms stack ⇒ 14×; vs realistic 2× ⇒ 0.77×; vs theoretical floor ⇒ 0.32× at 16 ch, 0.26× at 32 ch — rung definitions in Part II §3), energy & EDP (above), and iso-platform (same channels, plain vs AiM LPDDR; marginal cost = PIM die area).
  • Iso-cost scale-down (Orin NX, 102.4 GB/s = 8 channels): NX AE floor 6.30 ms, realistic 2× 12.61 ms. Our 8-channel config (14.01 ms — the same tier as at 16 ch) sits at 0.90× the NX realistic bound, so a cheaper module with AiM lands where an NX-class GPU would at its hypothetical best.

9How this differs from prior in-DRAM designs

Several published designs also reuse an in-bank fetch across more than one activation vector. To claim novelty honestly we did not argue from their papers — we re-implemented each mechanism on our own substrate and measured it: same machine (LPDDR5-AiM, 16 channels), same workload (π0 action expert, S = 51), same weight layout, the same stock attention path, and none of our software or controller work (no LOOP, no dedup, no token-parallel). What is left is the ISA mechanism alone. Each model lives on its own branch (prior/cent, prior/dots, prior/p3-llm, prior/lp-spec).

The four designs, and what each one actually does

Each block below gives the paper’s own datapath, how we modelled it here, what we deliberately did not credit, and the one-line difference from ours.

CENT — PIM Is All You Need, ASPLOS’25. Datapath: the same GDDR6-AiM substrate we extend, driven from a CXL controller with no GPU. Its PU carries 32 addressable accumulation registers, selected by a Regid field in MAC_ABK/RD_MAC — the register file our design needs. Modelled as: one register per output row-group, so a token’s whole projection drains once instead of once per row-group; MAC commands and GB fills unchanged. Not credited: nothing — this is a pure ISA feature and it transplants exactly. Measured: 27.09 ms, 1.05×. Difference: CENT has the accumulator file and spends it on one vector at a time; it explicitly declines batching inside a pipeline stage because “batching requires a significantly larger Global Buffer”. Enlarging that buffer is precisely the step we take.
DOTS — DRAM-PIM Optimization for Tall and Skinny GEMM, DATE’25. Datapath: switches the FC-layer dataflow so the activated weight row stays open while several input vectors stream past it, adding 8 result latches per PU and splitting the Global Buffer into two halves on separate read/write I/O buses so the next vector is written while the current one computes. Modelled as: the weight row held open across a block of 8 tokens, one drain per block — but still one MAC command per token, because DOTS never makes a single command serve several vectors. Not credited / credited separately: the split I/O bus is not free on our substrate, so we report both: charged (31.77 ms, 0.90× — slower than stock, because its row-major order re-fills the GB per row-group per token) and with the writes hidden as DOTS claims (20.52 ms, 1.39×). Difference: DOTS reuses the row activation and the drain; we reuse the fetch. Its 16× internal bandwidth is still spent 8 times on the same 32 B.
P3-LLM — NPU-PIM accelerator for edge LLM inference, arXiv’25/26. Datapath: an HBM-PIM PCU rebuilt for 4-bit weights and 8-bit activations, which closes timing at twice the clock; it therefore issues one command per tCCDS instead of tCCDL, letting the 256-bit weight slice already in the row buffer be consumed by two different input vectors in consecutive windows. Modelled as: depth 2 — one fetch, two accumulators. Not credited: the doubled command rate and the W4A8 numeric formats, both excluded by our fp16 and JEDEC-timing premise; their published speedup rests on all three together. Measured: 18.63 ms, 1.53×. Difference: depth 2 comes from a faster clock, and the paper states the reason it stops there — a deeper spatial tile “will increase the number of multipliers by n×”. We get depth 26 by time-multiplexing instead, so no multiplier and no clock change is needed.
LP-Spec — LPDDR5-PIM for mobile speculative decoding, ICCAD’25. Datapath: the closest platform match (LPDDR5, mobile SoC, a skinny GEMM of draft tokens against re-read weights). It replaces the per-bank-pair vector unit with a matrix processing unit of four 32-wide INT8 ALUs plus matrix register files, so one bank burst is broadcast to four ALUs — one fetch, four token rows — and adds a near-data controller so the NPU can use DRAM while PIM computes. Modelled as: depth 4 with a 4×-wide PU (64 lanes in the occupancy term). Not credited: its INT8 datapath and the NPU co-processing split. Measured: 14.81 ms, 1.93× — the only row that beats us. Difference: it buys depth with arithmetic, at 16.9 % of the die and a 26.5 % density loss in the original; we reach 2× the depth on the fabbed 16-lane MAC and end up 2 % behind on latency with 6 % less energy.

What the measurements say

  • Accumulators alone are nearly worthless (CENT, 1.05×). More result registers remove drains and mode switches, but every weight column is still fetched once per token. CENT has the register file our design needs and spends it on one vector at a time.
  • Latches without fetch reuse are worth little, and can lose (DOTS, 0.91–1.45×). Holding the row open across 8 tokens removes row activations (5,113 → 2,030 per channel) and blocking drains, but each token still costs its own MAC command — the same 32 B column is re-read from the open row buffer through the column path once per token, so the 16× internal bandwidth is spent 8 times on the same data and the MAC command count is exactly stock’s (263,976 vs our 57,000). The column path delivers one 32 B per 4 cycles whether one command or eight asks for it: 26 tokens against one column cost DOTS 26 fetches = 104 cycles, and cost P1 one fetch plus 26 PU beats = 41.6 cycles at 1 GHz. The weight-stationary order DOTS needs also re-fills the Global Buffer per (row-group, token): charged, that is slower than stock; only its split read/write bus rescues it.
  • Where P1’s edge over DOTS comes from — and where it stops (D = 1). The MAC-path advantage is exactly the PU’s headroom over the column rate. With a beat as slow as a column access (PU at 400 MHz, or a GB that can deliver only one slice per 2.5 ns), 26 beats cost the same 104 cycles as DOTS’s 26 column accesses and the two mechanisms tie: ours 21.08 ms vs DOTS 19.65 ms with its split bus credited (19.61 vs 19.65 if our fills are credited the same way), and 1.49× ahead of DOTS with its GB writes charged (31.47 ms). What P1 keeps at D = 1 is bookkeeping: one fill per projection instead of one per row-group (8× less GB traffic), and one drain per 26 tokens instead of per 8. At the fabbed 1 GHz (D = 2.5) the same comparison is 15.15 vs 19.65 ms (1.30×) and 2.08× vs DOTS charged. Regenerate: run_prior_art.py --d1.
  • Depth bought with arithmetic works — it is the only row that beats us (LP-Spec, 1.93×). Four ALUs per bank pair give depth 4 with a short command, so the PU never throttles. It costs 4× the multipliers: 16.9 % of the die and 26.5 % of the density in the original paper.
  • Depth bought with clock works too, and less (P3-LLM, 1.53×). Depth 2 from a PCU clocked at tCCDS. Its published speedups also need INT4/INT8 operands and a doubled command rate; our fp16, JEDEC-timing premise credits neither.
  • Depth bought with storage matches all of them at zero arithmetic (ours, 1.88×). Within 2 % of the 4×-multiplier design on latency, with 4.6× fewer MAC commands than any stock-depth design, the fewest mode switches, and the lowest energy of any row (261 mJ: 6 % under LP-Spec, 12 % under DOTS’s best case).

The novelty claim, in one paragraph. No prior design holds a multi-vector activation tile resident in the DRAM-die buffer and sweeps it with a single command.
