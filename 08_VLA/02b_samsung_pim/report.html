The Same Offload on Samsung’s PIM — a Smaller Problem, and Why

Part III showed the π0 action expert losing on SK hynix AiM for an ISA reason: one in-bank fetch serves one activation vector and one accumulator. Is that SK hynix’s mistake or a property of GEMV-only PIM? This page runs the identical workload on Samsung’s own simulator, retimed to the same LPDDR5 timing, and finds the same disease with a much smaller magnitude. The reason is not a better ISA. It is that Samsung sized its compute unit to the command bus, so there is far less idle throughput for a fix to harvest — and the machine is 1.9× slower to begin with.

SAITPublic/PIMSimulator @ 3703d1f (DRAMSim2) HBM-PIM retimed to LPDDR5-6400, 16 ch stock Samsung: 52.3 ms/step same workload, same timing, same host model

Overview

A second vendor, held to the same test. Everything except the PIM ISA is identical to Part III: tCK = 0.625 ns, 32 B column, 12.8 GB/s per channel, 16 channels at Jetson AGX Orin parity, the same 51-token layer, the same host segments. What changes is the machine underneath. One caveat on the column period: this page runs at the 2.5 ns column (tCCD = 4), which Parts III–IV now treat as their optimistic sensitivity; their primary point is the 5 ns all-bank column (stock AiM 40.24 ms, full design 9.31 ms), at which the Samsung model has not been re-run. Every AiM number quoted on this page is therefore the 2.5 ns one, labelled so.

The one-line answer. The diagnosis transfers exactly, the fix transfers exactly, and the payoff does not — because the payoff is gated by how much MAC throughput each vendor put behind the bank, not by the ISA. Samsung’s problem is smaller because Samsung left less on the table.

1Samsung’s PIM: the machine

Same idea as AiM, three structural differences: one compute unit per two banks, a register-file programming model instead of a broadcast buffer, and a unit clocked at the column rate rather than 1 GHz.

Fig. 1 — The Samsung channel. The programming model is a small register file per unit, not a per-channel broadcast buffer: GRF_A holds the input vector, GRF_B holds the accumulators, and the CRF holds a micro-kernel of up to 32 instructions.

2The ISA, and the one rule that matters

Nine 32-bit instructions: NOP, ADD, MUL, MAC, MAD, MOV, FILL, JUMP, EXIT. The interesting part is not the list but how instructions are issued.

The execution rule

// PIMRank::doPIM -- invoked once per incoming DRAM bus packet
do {
    cCmd = crf.data[pimPC_];
    ... EXIT / JUMP / execute ...
    pimPC_++;
} while (cCmd.type_ == JUMP);

A JUMP is free: it is folded into the same packet as the instruction it branches to. Every non-JUMP instruction consumes exactly one host DRAM column command. So the 32-entry command register file amortises instruction storage, not host issue: a 4,096-long GEMV runs from a six-instruction program written once by four writes, and the host still issues one column command per MAC.

This is the fact that decides the AiM comparison. Samsung’s CRF plus JUMP looks like a controller macro, and it is not one. Part IV’s P4 — a loop the memory controller replays without host involvement — is unsolved on this machine too.

Address-aligned mode: eight columns per instruction

The second half of the story is the isAuto_ bit. In address-aligned mode the register indices come from the address itself:

GRF_A index = column & 0x7
GRF_B index = ((row & 1) << 2) | ((column >> 3) & 0x3)

One auto-indexed instruction therefore serves eight consecutive column commands, and a 64-column sweep walks every (input burst, output burst) pair. Samsung’s stated motive is tolerance of memory-controller reordering; the side effect is code compression, and it is why Samsung’s host-command count per layer (12.5 M) is far below its MAC-burst count (86.9 M) — roughly seven bursts per command.

What address-aligned mode does not do is share a fetch. Each MAC still reads one bank burst, applies it to one GRF_A entry and accumulates into one GRF_B entry. The reuse factor is one, exactly as on AiM.

3The simulator, retimed to LPDDR5

There is no open-source simulator for Samsung LPDDR-PIM. Samsung’s own LP5X-PIM Sim is a four-page tech note with no code. The only runnable Samsung-authored PIM simulator is SAITPublic/PIMSimulator (DRAMSim2, modelling HBM-PIM / Aquabolt-XL), so we take it and retime it.

  • What is held identical to Part III: tCK = 0.625 ns, 32 B column, BL = 4, tCCD = 4 (Part III’s 2.5 ns column — its optimistic sensitivity, not its 5 ns primary point), 12.8 GB/s per channel, 16 channels = 204.8 GB/s, the same π0 layer at S = 51, the same host segments and the same 18-layer × N-step composition. Only the PIM ISA differs.
  • What is assumed, and tagged: LPDDR5 bank timings mirrored from the AiM study’s preset (A15-2); the compute unit clocked at the column rate (A15-3); fp16 kept, no quantisation (A15-4); one unit per two banks as the HBM-PIM baseline, with the one-unit-per-bank organisation measured separately (A15-5); and the headline framing that this is a retimed HBM part, not a native LPDDR-PIM product (A15-6).
  • Validation: the stock kernels are bit-identical to the pristine upstream branch after our patch (PIMKernelFixture.gemv 4096 passed / 0 failed; PIMBenchFixture.gemv 36,082 → 13,166 cycles, 2.74×).
  • Licence: the simulator is Samsung proprietary, academic use only, no redistribution. Nothing Samsung-authored is committed or published; our changes live as a patch script that applies to a local clone.

4How a GEMV runs, step by step

Samsung’s own reference kernel, PIMKernel::executeGemv. The shape of the loop nest is the whole story.

for (output tile j)
    for (b = 0; b < num_batch; b++)          <-- the batch loop is OUTSIDE the weight sweep
        changePIMMode(HAB, HAB_PIM)           // per output tile, per batch element
        for (input tile)
            8 × WRITE GRF_A                  // this token's input burst
            64 × MAC  (address-aligned)      // one bank burst each, one GRF_A, one GRF_B
        8 × GRFB_TO_BANK                     // drain the accumulators

With the batch loop outside the weight sweep, every weight is fetched once per batch element. For the action expert the batch is the token count, S = 51. Samsung’s own balance figures say what that costs: peak compute 1.229 TFLOPS divided by peak weight fetch 1.229 TB/s is 1.00 FLOP per byte — the machine is balanced for, and only for, a single-vector GEMV.

Samsung said this in print, in 2021. From the ISCA paper describing the silicon: “PIM-HBM improves the performance of GEMV by 11.2× and 3.2× for batch size of 1 and 2… for batch size of 4, the processor with HBM begins to outperform one with PIM-HBM… PIM-HBM does not improve performance if the batch size is 4 or larger.” The π0 action expert runs at batch 51.

Same disease. One fetch, one vector, one accumulator slot. At S = 51 both machines re-read the entire weight set once per token, and neither ISA has any way to express “apply this fetch to the next token too”. Samsung’s source says it plainly: readOpd(EVEN_BANK) performs one bank read per MAC, address-aligned mode picks one GRF_A entry and one GRF_B entry, and the batch loop sits outside the weight sweep.

6Why the problem is smaller here

Samsung is slower in absolute terms and yet has less of the problem this series is about. Both facts come from one design decision: how much MAC throughput each vendor put behind the bank.

 SK hynix AiMSamsung
lanes per channel16 banks × 16 = 2568 units × 16 = 128
unit clock1 GHz400 MHz (column rate)
MAC throughput per channel256 GMAC/s51.2 GMAC/s
one 16-MAC burst vs the 2.5 ns column slot1 ns → 40 % utilised2.5 ns → 100 % utilised
stock layer vs its own compute floor5.4× off1.62× off
layer after the ISA fix, vs that floor1.65× off1.32× off

AiM over-provisioned its compute unit by about 2.5× relative to its own command bus; Samsung sized its unit exactly to the column rate. That single choice explains both observations. On AiM the stock ISA leaves 5.4× of latent MAC throughput on the floor, and an ISA fix that stops re-fetching harvests it. On Samsung there is almost nothing latent: the unit is already busy every column slot, so removing redundant fetches converts a command-bound design into a compute-bound one and then stops.

The useful way to say it. The bug is identical on both machines — an ISA that cannot express token reuse. The bug’s cost is proportional to the throughput the machine cannot reach because of it. Samsung has a smaller problem because Samsung built a smaller engine: 5× less MAC throughput per channel, and correspondingly less of it stranded. Being harder to improve is not the same as being better — Samsung is 1.92× slower than AiM on the identical layer, before and after the fix.

7What the fix is worth, and the Samsung-specific ceiling

We implemented the Part IV fix in Samsung’s idiom — a new opcode MACV in the first reserved ALU slot, plus the two storage additions it needs — and measured it.

A correction to our own prior expectation, worth stating: we assumed Samsung’s GRF_A/GRF_B already provided the storage the fix needs. They do not. In the stock mapping GRF_A holds eight reduction bursts of one token and GRF_B holds eight output bursts of that same token. Token amortisation needs V tokens resident and V × 8 accumulators — new storage on both machines. The requirement is structural, not vendor-specific.

The ceiling Samsung hits instead: output-tile granularity

Samsung’s GEMV mapping computes num_output_tiles = ceil((out / total_PIM_blocks) / 8). The output dimension therefore quantises to a multiple of (units × 8), and the expert’s projections are small relative to that quantum — 4,096 down to 256 for the MQA KV path and attention. The waste is measured, not derived:

configuration8 ch16 ch32 ch
arithmetic padding, stock (1 unit / 2 banks)1.12×1.32×2.13×
arithmetic padding, 1 unit / bank—2.13×—
AiM, for comparison≈1.03× at every channel count

Padding grows with parallelism. Spreading a narrow GEMV across more units makes it worse, and this is what absorbs added compute. Giving every bank its own unit — the organisation Samsung announced for LPDDR-PIM — doubles the units, but num_output_tiles then saturates at 1 for six of the eight operations. Measured: the two widest projections speed up exactly 2.00×, the other six gain nothing and do twice the redundant arithmetic, so the layer improves 1.38× rather than the 1.79× we had projected before running it.

Where this leaves the cross-vendor claim. The diagnosis (a GEMV-only ISA cannot amortise a fetch across tokens) and the fix (storage, not arithmetic) are properties of the ISA class, not of one vendor — they transfer intact. The payoff is a property of the microarchitecture behind the bank, and it is large only where compute was left idle.
