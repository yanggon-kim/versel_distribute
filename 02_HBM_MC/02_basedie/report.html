Custom HBM Base Die + LPDDR Extension — Ramulator v1 Design

How the HBM4-era "custom HBM" architecture — a logic base die hosting the HBM controllers, off-chip LPDDR controllers, unified-address-space steering, and a tier-to-tier migration engine — was modeled in Ramulator 2.1, why each design decision was made, and what the model measures.

1Why: the design purposes

Stock Ramulator models a flat GPU+HBM system. The research target is the base die as a three-way memory hub — and the questions that only a simulator can answer quantitatively.

From HBM4 onward the HBM base die can be a logic die (KAIST TERALAB roadmap; NVIDIA patents US 11,789,649 / US 12,001,725; Samsung cHBM; Intel–AMD UCIe-Memory). Once it hosts customer logic, two things happen at once: the HBM memory controller moves off the GPU into the base die, and the base die grows external off-chip I/O of its own — serial channels to LPDDR devices. Each HBM site becomes the head of a small memory network: a high-bandwidth near tier (the stack above) fused with a high-capacity far tier (the LPDDR beside), presented to the GPU as one unified memory.

The v1 model exists to make three first-order research questions measurable:

QuestionWhat the model provides
What are the bandwidth/latency characteristics of each tier as seen through one base die? Per-tier controllers with correct clock domains and wall-clock stats (§7, tier characterization)
How much does background tier-to-tier migration interfere with foreground GPU traffic — and which mechanisms control it? A DMA engine that bypasses the GPU link but contends inside the DRAM controllers (§7, isolation levers)
What does a capacity-tier usage model (KV-cache / weight warming) look like at the memory-system level? Configurable block migration with regions, patterns, rate control (§5)

Intent statements that shaped every decision

  • Reuse, don't fork, the device models. Upstream's validated HBM34 and LPDDR5 controllers and their generated DRAM models are used unchanged; all new behavior lives above them (memory-system level) or beside them (DMA engine). Upstream's latency/throughput validation suites keep passing untouched.
  • Model traffic, not data. The DMA generates request patterns; no bytes move — matching the fidelity level of the rest of Ramulator (requests + timing).
  • Everything configurable from Python with zero hand-written binding code, via Ramulator's macro-scanning code generator.
  • Every commit builds green; the branch is regression-clean against upstream's four test suites.

2Architecture

One new composite memory system is the base die; the tiers are plain upstream controllers; the DMA is an optional child reaching the tiers through an internal port.

Why a new memory system instead of extending GenericDRAM: the stock implementation bakes in homogeneity — one clock ratio forced on all controllers, transaction size taken from controller 0, a single flat channel list. Heterogeneous tiers break all three. A separate implementation carries zero regression risk for upstream configurations.

3Unified address space & steering

Pool sizes are derived, not configured — the address map follows the DRAM organization automatically.

// per-channel capacity comes from the controller itself (new IController::get_addressable_bytes)
per_channel_bytes = (Π level_sizes[1..N-1] / internal_prefetch_size) × tx_bytes
near_size = per_HBM_channel × |hbm_controllers|     // HBM4_32Gb_8Hi → 1 GiB/ch
far_size  = per_LPDDR_channel × |lpddr_controllers| // LPDDR5_16Gb_x16 → 2 GiB/ch (rank=2 → 4 GiB)

// steering (the MML), on every GPU request
addr < near_size            → HBM pool,   pool_addr = addr
addr < near_size + far_size → LPDDR pool, pool_addr = addr - near_size
else                        → error "outside the unified address space"

// per-pool interleave at transaction (32 B) granularity
channel = (pool_addr >> log2(tx)) & (pool_channels - 1)
intra_channel_addr = pool_addr with the channel bits spliced out
// the controller's own addr_mapper (RoBaRaCoCh, …) decodes intra → bank/row/column

The LPDDR extension is fully configurable from Python: channel count = list length, capacity = org preset + overrides (e.g. rank=2), bandwidth = timing preset. The GPU never observes which tier served a request except through its latency.

Deliberate consequence: interleaving at 32 B granularity means address-range separation is not channel separation — any large region spans all channels of its pool, exactly like real systems. Resource partitioning therefore requires the levers measured in §7.

4Per-tier clocking

Two real clock domains behind one composite tick.

The composite ticks in the HBM tick domain (HBM4-8000: tCK 500 ps, 2 ticks/CK → 0.25 ns). LPDDR controllers tick once every lpddr_tick_divider composite ticks. The divider is auto-derived from the controllers' actual per-tick periods (1.25 / 0.25 = 5 for the default pairing), accepted within 1% of an integer, and overridable — otherwise initialization throws with instructions. Because every controller measures time in its own tick domain, upstream's per-controller stats (avg_read_latency in ticks, *_throughput_MBps) remain wall-clock correct per tier with no changes; experiment scripts convert ticks → ns with the per-tier period.

5Migration engine (the base-die DMA)

"Read a block from LPDDR, put it into HBM" (or the reverse) as a request-level state machine — only the traffic pattern is modeled.

ParameterDefaultMeaning
directionlpddr_to_hbmor hbm_to_lpddr
block_size4096bytes per transfer block (multiple of 32 B tx)
num_blocks0total blocks; 0 = migrate continuously
pattern / seedsequentialor random (block-aligned, seeded — deterministic runs)
inter_block_gap0composite ticks between blocks — the rate throttle
max_inflight_reads8outstanding-read window
src/dst_region_offset/size0 / rest of poolpool-relative windows — enables ping-pong / double-buffer placement

Block lifecycle: open block (cursor or random base within regions) → issue 32 B reads to the source tier up to the in-flight cap → each read's completion callback immediately posts the mirrored write to the destination tier → block completes when all writes are accepted → gap countdown → next block. Backpressure is honored everywhere (rejected sends retry; counted as read_stalls/write_stalls).

Design decision — posted writes (learned the hard way). The first implementation waited for writes to retire to DRAM and deadlocked under foreground load: controllers drain writes only in write mode (write queue > 80% watermark, or read queue empty), and a steady GPU read stream keeps the read queue non-empty while a 16-write block never reaches the watermark — 0 blocks completed in 40k ticks. Posted completion (done at buffer accept) matches real fire-and-forget DMA engines, while the accepted writes still occupy the destination write buffer and exert fully realistic drain-mode interference — the very mechanism §7 quantifies.
Design decision — source_id = -1. Controllers index per-core stat arrays (sized by the frontend's core count) for any request with a real source id; a DMA "fake core id" would corrupt them. All DMA requests are maintenance-style (-1), enforced in dma_send() — with the side benefit that frontend-visible per-core stats are provably unpolluted by migration traffic.

6Framework infrastructure it required

Two small, generic extensions to Ramulator's component framework — plus one upstream bug fix.

ChangeWhy
Named child lists
RAMULATOR_CREATE_NAMED_CHILD_LIST		 The config system could attach only one list per interface to a component; the base die needs two lists of IController (hbm_controllers, lpddr_controllers). Added a keyed C++ overload + macro and taught the regex-based codegen to emit ChildList("controller", key="hbm_controllers") — so the Python API gained first-class keyword arguments with zero hand-written bindings. Regenerating all existing wrappers is byte-identical.
IController::get_addressable_bytes() Pool sizes must be derived from the DRAM organization. The formula is exactly the address space upstream's flat address mappers decode, so derived pools and the mappers agree by construction.
Python Component.to_config() fix The DMA engine is the repo's first optional single-child slot; unset optional slots serialized the class-level descriptor object itself and crashed config conversion. Latent upstream bug, surfaced by this design, fixed by keying on instance-dict membership.

7.2 Migration interference & the isolation levers (ping-pong study)

GPU streams reads into HBM region A at fixed 32 GB/s while the DMA fills region B from LPDDR (double-buffering placement). Default RoBaRaCoCh mapper:

DMA modeGPU latency vs offGPU BWMigration rate
off1.00× (46.1 ns)32.0 GB/s—
unthrottled1.50×26.0 GB/s9.0 GB/s
write buffer 1281.18×29.2 GB/s9.0 GB/s
throttle (gap4k)1.14×30.2 GB/s2.8 GB/s
gap4k + wbuf1281.06×31.1 GB/s2.8 GB/s
heavy throttle (gap16k)1.05×31.4 GB/s0.9 GB/s
Findings. (1) Interference is dominated by the controller's read/write turnaround (write-drain mode blocking reads), not bank/row conflicts — row-conflict counters barely move while write-path levers recover most of the loss. (2) Write-buffer batching is the "free" lever: 1.50×→1.18× at the full migration rate. (3) Throttling is dose-dependent — pace migration to the ping-pong deadline (region_size / phase_time), no slower and no faster. (4) Contiguous-region bank partitioning via ChRaBaRoCo is an anti-lever: it collapses the GPU's own bank parallelism (baseline capacity 19.6 < 32 GB/s offered) and degrades 2.57× under load.

8v1 limits & v2 roadmap

Deliberate constraints (enforced with explicit errors) and the extensions they motivate.

v1 limitationv2 direction (ordered by research value)
No GPU-vs-migration QoS — write-drain policy treats DMA and GPU writes identically 1. QoS arbitration: GPU reads preempt migration writes unless the buffer is critical — targets the unreached operating point (full 9 GB/s and <1.1×)
Static near/far partition 2. Interleaved near pool (patent Fig. 3A): carve part of LPDDR into the near range at a programmable ratio — far-tier bandwidth becomes additive
Pattern/rate-driven DMA only 3. Access-driven migration: frequency counters / stream inference as triggers — a new IDMAEngine impl, not a rewrite
Single base-die site per simulation 4. Multi-site scaling: N base dies + GPU-side site decode (named child lists already support grouping)
Equal 32 B tx across tiers; pow-2 channels per pool; DMA lifetime = frontend lifetime Constraint lifting: per-pool tx validation, modulo interleave, run-until-drained
