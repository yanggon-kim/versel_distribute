DeepSeek-V3.2 — Part IX: Custom-HBM Capacity Design Evaluation on B200

The custom memory design under study — each GPU's 8 HBM cubes extended with 128 GB of LPDDR behind the base die, 192 GB + 1,024 GB = 1,216 GB per GPU at unchanged bandwidth — evaluated end-to-end with LLMServingSim replaying B200-measured V3.2 kernels (Part VIII). Three systems, each pushed to its no-eviction maximum batch, across 64K–1M context.

Simulated from measured B200 kernels LLMServingSim DeepSeek-V3.2-Exp 1,216 GB/GPU custom tier 15-run matrix, all steady-state validated

§0Overview — capacity alone is worth 2.9× at 64K and 8.7× at 1M

Same GPU, same 8 TB/s, same measured kernels — only the memory pool grows. The custom 8-GPU system serves 12.6–22× more concurrent sessions than stock, which converts to 2.9–8.7× cluster throughput and identically 2.9–8.7× better energy per token. And six custom GPUs beat eight stock GPUs at every context length.

The claim this part establishes: on Blackwell, exactly as on Hopper (Part VII), DeepSeek-V3.2 decode is power-flat and capacity-bound, not bandwidth-bound. Extending each GPU's memory 6.3× at fixed bandwidth converts almost losslessly into batch, throughput, and tokens/joule — and the longer the context, the larger the win, because stock capacity collapses faster (28 → 1 sessions/GPU from 64K → 1M) than the per-token decode cost grows.

§2Method & memory accounting — measured kernels, audited units

Same pipeline as Part VII, re-anchored on the B200 profile bundle from Part VIII: every latency is a lookup into measured tp1 kernel data; the scheduler, KV block allocator, and admission control are LLMServingSim's vLLM-style replay.

  • EP-rank proxy: the DP ranks are symmetric, so one rank is simulated as a single tp1 instance of an expert-slice model; cluster batch/throughput = N×rank. A cluster batch B runs as b = B/N requests on the rank.
  • Steady-state measurement: staggered-output workloads (request i gets output = (b−1−i)×(L/65536) + 64) make all b requests decode their final 64 tokens at full concurrency; steady TPOT is the last-prefilled (max-TTFT) request's TPOT, and every cell is checked for n_eff = b at the steady-window midpoint. All 15 cells passed.
  • GB vs GiB, audited: a real B200 exposes 179.06 GiB, not 192 — back-derived from our own B200 profiling logs via vLLM's memory accounting (0.94×T = 21.0 model + 142.08 KV + 5.24 overhead GiB), matching the standard nvidia-smi total of 183,359 MiB. The marketed "192 GB" is decimal and already post-ECC (physical 192 GiB minus the ~1/16 inline-ECC carve). Likewise the custom pool is 1,216 GB = 1,133 GiB, the value the simulator (which reads GiB) is given.
  • KV cost: 48,068 B/token (656 B fp8_ds_mla latent + 132 B indexer key, ×61 layers) → 2.93 / 5.87 / 11.7 / 23.5 / 46.9 GiB per session at 64K / 128K / 256K / 512K / 1M.
  • A capacity-planning lesson (64K): filling memory to the last session backfires. At b = floor(free/KV) the pool hit 99.97% occupancy and the last request could not allocate KV until others finished (output tokens grow each session by 1–7 extra 64-token blocks), breaking full-batch steady state. The final matrix backs off two sessions of headroom at 64K (b = 351/342 instead of 353/344).

§5Analysis — five observations

  • 1 · The capacity advantage grows with context length: 2.89× → 8.70×. Stock capacity collapses geometrically (28 → 1 sessions/GPU from 64K to 1M) while the custom system's TPOT falls with context at max batch (118.8 → 58.4 ms — fewer, longer sessions cost less per token than many short ones, since MoE/dense token count shrinks while total KV bytes stay pinned at the pool size). The gap therefore widens exactly where long-context serving lives.
  • 2 · Six custom GPUs beat eight stock GPUs everywhere — 2.14–6.38× — with 25% less silicon, and B's per-GPU throughput matches A's within 1–2% at every context. With a ~1 TiB pool, weights-per-GPU stop mattering and GPU count becomes a nearly linear throughput knob; on stock memory the same 8→6 move would be a weights-vs-KV tug-of-war (an EP6 stock rank would keep only ~58 GiB for KV — worse per GPU than EP8).
  • 3 · The price is per-user latency. Custom runs at 57–119 ms TPOT (8–17 tok/s per stream) vs stock's 23–27 ms (37–43 tok/s). This is the batch-throughput frontier, not a free lunch: the design converts capacity into aggregate tokens and joules, while an individual user reads slower. Interactive SLOs pick the operating point; these tables are the frontier's end-points.
  • 4 · Energy gains equal throughput gains, exactly. Steady decode power is ~1,268 W per rank-node at every batch size (the model is utilization-binary: the GPU is equally "on" serving 1 or 351 streams), so J/token is throughput's mirror — 0.43 vs 29.3 J/token across the whole table, a 68× spread. This is the Blackwell restatement of Part VII's power-flat finding on Hopper.
  • 5 · B200 vs H200 at the same story-point: the stock-B200 128K ceiling (112 sessions, 4,277 tok/s) already beats stock-H200's (64 sessions, 3,120 tok/s) on both capacity and speed — but both are dwarfed by the capacity tier, and the shape of the win (growing with context, flat power) is generation-invariant.

§6Caveats — what these numbers assume

Uniform-bandwidth idealization. Systems A/B model the 1,216 GB pool as flat 8 TB/s. In the real design the 1,024 GB LPDDR tier sits behind UCIe at 128 GB/s per cube (1.024 TB/s aggregate), so KV resident in LPDDR pays a gather cost these tables do not charge. This is the same optimistic convention as Part VII's H200 tiers; the tiered-bandwidth reality — and what the base die can do about it — is quantified in Part VIII §15 (G-ladder) and Part VI §12. Read A/B as the capacity ceiling the memory-system design must then defend.
  • EP6 approximation: System B uses the heavy 43-expert rank for all 6 ranks (≤2% conservative on weights) with MoE latency interpolated between measured 32- and 64-expert rows.
  • EP all-to-all: as in Part VII, the decode-time expert all-to-all (~1 MB/direction/iteration) is not separately charged; at 8 TB/s-class links this is sub-percent.
  • Prefill excluded from the headline: TPOT/throughput/J-token are steady decode-phase numbers; the serial 64K–1M prefill ramp is simulated (chunked at 65,536 tokens/iteration) but reported separately in the run logs.
  • Simulator fidelity anchors: the same pipeline reproduced real-vLLM behavior across Parts VI–VIII; every attention/MoE latency here is a measured-grid lookup (batch points up to n=1024, KV to 1M — no extrapolation was needed at any cell).
