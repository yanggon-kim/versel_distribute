Two runs with identical work and identical FLOPs, differing only in where the 2048 indices point, produce a DRAM footprint difference of four orders of magnitude — 331,539 distinct 64-token pages versus exactly 32 — yet the fused kernel time changes by only 0.5–1.6 % at b=256. At b=1024 the gather moves 1.376 GB, about 172 µs of ideal 8 TB/s DRAM time, of which only 11.1–11.8 µs per launch is exposed — roughly 86 % is hidden behind the attend compute. (Convention, discovered during the in-situ PCIe run below and applied throughout: the split-KV kernel launches twice per decode step, so every per-kernel column on this page is per-launch; per-step kernel time is 2× it. Layer-level columns were always per-step.)

For a custom HBM whose base die fronts an LPDDR extension this is the load-bearing result: because the HBM-tier gather is nearly free as currently overlapped, a slower tier's cost is almost entirely additive. The pessimistic serial bound is close to the truth for far tiers, and the optimistic bound can credit at most ~1–24 µs of hiding per step.

2Why this run existed

The previous rental measured the DSA (DeepSeek Sparse Attention — V3.2's top-2048 sparse attention mechanism) only at fused-kernel granularity. Its gather column was the whole flash_fwd_splitkv_mla_fp8_sparse kernel — the top-2048 gather and the sparse attention over those entries. At b=1 the math is under a microsecond so 12 µs was close to a true gather floor, but at b≥256 a large share of the fused time is attend compute, so there was no gather-only latency from the production path and every quoted “gather bandwidth” was bytes ÷ fused latency — a mixed lower bound.

4Method: index-controlled A/B

The fused kernel gathers whatever the int32 index buffer holds; it has no opinion about where those slots point. Run (A) scatters them across the whole context (a real DRAM gather); run (B) confines them to 32 L2-resident pages (~1.34 MB). Both execute identical work otherwise — same 2048 indices per token, same 128-head attend over 2048 entries, same launches, softmax and output writes, and an identical scan/top-k/projection prologue. In t(A) − t(B) everything common cancels and what survives is the cost of fetching 656-B records from scattered DRAM instead of from L2. t(B) is itself the measured t_layer_no_gather.

Set (B) cannot be built the obvious way. The natural reading is to overwrite the index buffer before slot translation, using request-local positions [0, 2048). But every request owns disjoint KV blocks, so request-local [0,2048) lands on a different 32 pages per request — B × 1.34 MB, not 1.34 MB: 21 MB at b=16 but 344 MB at b=256 and 1.37 GB at b=1024. Set (B) would then be doing its own full DRAM gather at large batch, and t(A)−t(B) would understate the exposed gather, with the error growing in batch — worst exactly where the downstream GPU-count study needs tight interpolation. So Set (A) is applied before translation (real block-table indirection, the production pattern) and Set (B) is applied to the translation output, giving one shared hot set. Measured: Set (B) touches exactly 32 pages, independent of batch.

How we know the override really reaches the kernel, given that the fused time barely moves. Three independent checks, not timing: path instrumentation shows the translation function, the fp8 decode path and the fused-kernel wrapper each called exactly once per forward; index validity is 100.00 % (0 of 524,288 translated slots are −1, so nothing is skipped); and the distinct-page count differs 10,361×. The small latency delta is the physics, not a failed override.

5Inside flash_fwd_splitkv_mla_fp8_sparse: why the gather hides

Read directly from FlashMLA's sm100 decode kernel (the 69-line diff of our consumer-stub fork proves the reading). The kernel is warp-specialized: one CTA per (request, split), and within a CTA the warps hold fixed roles connected by mbarrier-guarded double buffers:

GPU terms used in this section — CTA: cooperative thread array, one kernel work-block resident on one SM; warp / warpgroup: 32 / 128 threads scheduled together; SMEM: the SM's fast on-chip shared memory; TMA: the Tensor Memory Accelerator, Hopper/Blackwell's DMA engine that copies global↔shared memory asynchronously (here via tma_gather4, which fetches 4 records per instruction); mbarrier: a hardware barrier that TMA transfers signal on completion, letting consumer warps sleep until bytes arrive; tcgen05 / UMMA: Blackwell's 5th-gen tensor-core instructions; tensor memory (tmem): the per-SM accumulator storage UMMA writes, read back by the softmax warps; NoPE / RoPE: the two pieces of each 656 B record — the 512 B fp8 compressed-latent part (no positional encoding) + 16 B of e8m0 power-of-two scale factors, and the 128 B bf16 rotary-position part; fp8 e4m3 / e8m0: 8-bit float formats for the payload and its scales.

warp(s) role what it does per 64-record chunk
7index transformturns 64 top-k token ids into TMA coordinates, e8m0 scale bytes and a validity mask; arrives coord_ready
5NoPE gather (producer)issues tma_gather4 bulk fetches of the 512-B fp8 latents into SMEM; arrives raw_ready with an expected-byte count

The chunk pipeline: while the consumers (dequant → MMA → softmax) process chunk i, warps 5–7 are already fetching chunk i+1 into the other buffer. Per launch there are 16 chunks (1024 records of the 2048, the other half in the second split launch). The gather is exposed only at the fill (first chunk, nothing to overlap yet) and wherever a chunk's fetch outlasts a chunk's compute.

Measured ratios at (64, 128K), per launch: consumer chunk = fusedk_B/16 = 2.58 µs; producer chunk = (N/2/16) / 2.81 TB/s = 0.96 µs — the fetch takes only 37% of its slot, so it finishes early every time. Exposed: ~0.33 µs fill at the head plus residual leaks, totalling the measured 1.51 µs. From the consumer-stub fork: the consumer lane is ~90% ingestion/staging and ~10% MMA+softmax.

The two-lane chunk pipeline at measured ratios. Top: on HBM the fetch uses ~37% of each slot, so the gather rides invisibly under the compute — only the fill and per-chunk residuals are exposed. Bottom: in-situ over PCIe the same machinery runs with roles inverted — each fetch chunk takes ~100 compute-chunks of time, the compute hides completely, and the kernel time becomes the gather time (which is why tlayer = layer_B + t_gather − W held to 0.28%).

Three readings. (1) The attend kernel uses only 7–18% of HBM peak (0.58 TB/s at b=16 up to 1.48 TB/s at b=1024), rising with batch and flattening around 1.2–1.5 TB/s; at the (64, 128K) reference cell it is 1.00 TB/s (12.5%). (2) It is context-independent — the rows are identical within noise because the kernel touches exactly 2048 latents per token whatever L is; context only changes the separate scan. (3) It is not bandwidth-bound. Sections 7 and 12 triangulate why: removing the math (D7 stub) shortens the kernel only ~10% and removing gather locality (D2) moves it 1–2%, so the critical path is the per-CTA TMA-gather → dequant → SMEM staging pipeline, with the producer fetch using only ~37% of its chunk slot. That is why ~80% of HBM bandwidth sits idle under this kernel, why an HBM-resident gather hides inside the window, and why the break-even bandwidth for any other tier is the kernel’s own ~1–1.5 TB/s ingestion rate (section 13), not the 8 TB/s peak. A standalone torch.gather of the same records on HBM (Part VIII memtiers table) reaches 0.93–0.99 TB/s — the same class — so random 656-B-granularity access simply does not approach the sequential peak at this in-flight depth.

Bound: the table counts only the gathered latents. Adding the query read and output write (bf16, b × 128 × (576+512) × 2 B) raises every cell by ~20% relative (e.g. 12.5% → 15.1% at (64, 128K)); the true figure lies between. Timings are torch.profiler kernel durations inside the real vLLM decode (no ncu / DRAM counters were available on the rental), and the byte count is analytic from the model config.

Two honest caveats. First, delta_layer (the layer-level subtraction) is noise-dominated: it is ≤ 0 in 19 of 34 cells, because it inherits the variance of the whole decoder layer while the signal is only ~1–12 µs. Since the gather lives in a single kernel, delta_kernel is the same quantity measured with far less noise, and it is positive in 34/34 cells. Second, b=256 dips below b=192 (0.75–2.30 vs 3.16–3.34 µs). b=256 is a protected interpolation point, so this is flagged rather than smoothed; it looks like a tiling/occupancy effect and the fit near b=256 should be read with care.

Reading it per GPU count

Under the serving layout each rank runs attention for its own per-rank batch b = B_cluster / N, and gather time is a function of (b, L) only. So the batch axis is the GPU-count axis: fewer GPUs means larger b per rank and proportionally more gather. The planned comparison's per-rank operating points (137, 163, 172, 176) all fall inside 128–512, where the exposed gather runs 2.05 → 8.06 µs — though the b=256 dip noted above sits inside that interval.

11Co-run interference (D6, complete on the subset grid)

Why this section exists. The tier-substitution model credits an overlap window: exposedtier = max(0, t_gather − W) — up to W of a slow tier's gather is assumed to hide for free under the layer's other work. That “for free” is an assumption worth attacking: the gather and the compute kernels share one GPU and could fight over the same HBM bandwidth, in which case “hidden” gather would silently slow everything else and the credit would be partly an illusion. This experiment runs a gather concurrently with the layer and measures whether either side slows down.

The vocabulary, term by term:

  • Stream: a CUDA stream is an ordered queue of GPU work. Kernels within one stream run in order; kernels in different streams may run concurrently on the same GPU, sharing its SMs, copy engines and memory system. vLLM normally issues everything into one stream (the primary stream), so nothing ever overlaps with the layer — a second stream is the only way to make two workloads genuinely execute at the same time.
  • Partner = the full layer-B forward: the decoder layer run with the HOT index set (Set B of the A/B experiment), i.e. the layer with its own gather made ~free — t_layer_no_gather, the “everything else” a tier gather would hide under. Layer-A is not used because its own DRAM gather would double-count.
  • CUDA context: the per-process GPU state container (address space, allocations, loaded kernels, streams). Both sides must share one context — i.e. run inside the same worker process — or the GPU time-slices between two processes instead of overlapping them (no MPS on this box).
  • Co-runner: the synthetic gather injected on the second stream — a torch gather over an HBM pool (src=hbm) or a pinned-host→device copy sized to the gather bytes (src=pcie). It is not the TMA microbench kernel, so its absolute times are not comparable to D3; only the solo→co-run change (the interference) is the measurement.
  • Makespan: wall-clock from the first launch to the last completion of the pair (in the CSV, with W_eff = partner_solo + (makespan − partner_corun)).

How to read a row: at (64, 128K) hbm, the gather alone takes 76.2 µs but 90.5 µs beside the layer (+19% — the gather got slower), while the layer goes 8275.9 → 8246.5 µs (−0.4% — it did not notice). The interference exists but lands entirely on the gather — exactly what a design that hides gather under compute wants. 13How to charge a different memory tier: the max-overlap-window recipe

This section is self-contained: it defines every term, gives the lookup table, and shows how to predict one decoder layer's time when the KV gather is served from some other memory tier (LPDDR behind a base die, CXL, PCIe, host DRAM …) characterised by just three numbers (a, b, N).

Definitions

termmeaning
decoder layerone full transformer layer of DeepSeek-V3.2 in decode: input layernorm → sparse attention (indexer scan → top-k → the fused kernel) → output projection → MoE FFN. Everything here is per layer, per decode step; the model has 61 such layers.
fused kernelflash_fwd_splitkv_mla_fp8_sparse — the single GPU kernel that BOTH fetches the selected 2048 KV records from DRAM (the gather) AND computes the 128-head attention over them. Because both jobs live in one kernel, the gather cost cannot be read off a profiler directly — hence this page.
recordthe per-token KV entry the kernel fetches: 656 bytes = 512 B fp8 compressed latent + 16 B scale factors + 128 B bf16 RoPE part.
top-k / top-2048the sparse-attention selection: for every query token, an indexer scores all cached tokens and picks the 2048 highest; only those records are fetched and attended to.
KV block (page)the paged-KV allocation unit: 64 tokens × 656 B = 41,984 B. A per-request block table maps logical token positions to physical blocks; requests own disjoint blocks.
processing blockdistinct from the KV block: the kernel's main loop consumes the 2048 selected records in chunks of 64 records per iteration. Overlap happens at this granularity — while the math works on chunk i, the producer warps fetch chunk i+1.
gatherfetching the B × 2048 randomly-scattered 656 B records from memory. Its byte volume is N = B × 2048 × 656 (B = per-GPU decode batch); note N does not depend on context length L.
Set (A) / Set (B)the two runs of the isolation experiment. (A): indices point at scattered DRAM (real pattern). (B): indices point at one shared, L2-resident 1.3 MB hot set, making the gather ~free. Identical instruction stream otherwise.
layer_A / layer_Bmeasured time of the WHOLE decoder layer under Set (A) / Set (B). layer_B is the layer with a free gather — the t_layer_no_gather that tier substitution starts from.
fusedk_A / fusedk_Bmeasured time of the fused kernel under Set (A) / Set (B), per launch — the split-KV kernel launches twice per decode step (torch.profiler: count=2), so per-step kernel time is 2×fusedk. fusedk_B is the per-launch compute-side critical path: how long a launch runs when fetching costs nothing.
delta_kernelfusedk_A − fusedk_B = the exposed gather on the HBM tier — the part the pipeline fails to hide (small: 0.5–12 µs).
window Wthe maximum gather time that can hide inside the kernel per decode step = W = 2 × fusedk_B (two sequential split launches, each hiding its half of the gather). A gather faster than W is (at best) invisible; anything beyond W has nothing left to hide behind.
a, b, Nthe tier model t_gather = a + N/b: a = one-time setup / initial latency (µs), b = achieved gather bandwidth for scattered 656 B records (GB/s), N = bytes (above). The N/b term is the bandwidth cost; a captures fixed overheads.

The rule

Inside the kernel, fetching chunk i+1 overlaps computing chunk i, so to first order

t_kernel(tier) ≈ max( t_gather(tier), W ) with W = 2 × fusedk_B — the fused kernel runs as two sequential split launches per step, and fusedk_B is per-launch.

and therefore, at the layer level,

t_layer(tier) ≈ layer_B + max( 0, t_gather(tier) − 2·fusedk_B )   (window-credited, optimistic)
t_layer(tier) ≈ layer_B + t_gather(tier)   (serial, pessimistic)

If t_gather ≤ W = 2·fusedk_B the tier change is (near) free. If t_gather > W, the excess is purely additive — there is nothing left to hide it behind. On this hardware the truth sits close to the serial bound for slow tiers (see caveat 1).

The recipe

  1. Pick the operating cell (B, L). For an Ngpu-GPU cluster at total batch Bcluster, use B = Bcluster / Ngpu (gather is per-rank).
  2. Read layer_B and fusedk_B for that cell from the lookup table below (or from d2_gather_ab.csv).
  3. Compute N = B × 2048 × 656 bytes.
  4. Compute the tier's t_gather = a + N/b — with measured a and b for scattered 656 B reads (see caveat 1), like the tier fits above.
  5. Bound the layer: serial = layer_B + t_gather; window-credited = layer_B + max(0, t_gather − 2·fusedk_B). Quote both; the truth is between, near serial for slow tiers.
  6. Model-level: multiply the per-layer delta by the layer count (61) and add to the decode-step time; TPOT then follows from the serving stack as usual.

Caveats that keep this honest

  • Use measured (a, b), not datasheet numbers. b must be the achieved bandwidth for scattered 656 B records, which is far below pin rate, and sustaining it requires enough requests in flight: by Little's law, in-flight bytes ≈ b × round-trip latency. The kernel's own buffering (~2 × 42 KB per CTA, sized for HBM) cannot supply that for a high-latency tier — the tier's gather engine must bring its own parallelism, or the real cost exceeds a + N/b and the serial bound is the right one.
  • Overlap is per-processing-block (64 records at a time), not lump-sum: window time from early chunks cannot be banked against a slow tail.
  • The window can be architecturally widened. Indices exist only after top-k, so today W = fusedk_B. But the co-run measurement above showed the rest of the layer leaves HBM bandwidth essentially idle, so a base die that prefetches on the previous step's indices could stretch the window toward the whole layer (~layer_B) for the recurring-index fraction.
  • layer_B is a 1-layer dummy-weight measurement at TP1; it carries the profiling harness's per-forward overheads. For simulator use, apply the delta (the max-window rule) on top of your calibrated layer time rather than treating layer_B as gospel.

The calculation, spelled out (no black box)

  1. N = B × 2048 × 656 bytes: every query token fetches its top-2048 records of 656 B each; context length L does not enter N.
  2. Your tier model: tgather = a + N/b, with a = per-step intercept in µs (setup + exposed round-trips: a ≈ tsetup + keff·tRT, keff=1 for a deep pipeline, ~8–15 for a shallow one) and b = achieved scattered-656 B bandwidth in GB/s (never the pin rate). tgather[µs] = a + N[bytes]/(b·10³).
  3. Window credit: the kernel overlaps fetch and compute, so up to W = (d) of the gather hides. Exposed gather on the new tier: (c)tier = max( 0.67 + N/44.6 TB/s , tgather − W ). The first argument is the fast-tier floor fitted on HBM: a 0.67 µs head plus a leak of N/44.6 TB/s — about 18% of the bytes' ideal 8-TB/s time, or 2–3% of the window (state the denominator; an earlier revision ambiguously said “~2% leak”). It only matters for tiers within ~2× of HBM-class.
  4. New layer time: tlayer(tier) = layer_B + (c)tier, where layer_B is the measured layer with a free gather (≈ (a) − (c), but measured directly, which also absorbs a small out-of-kernel exposure at large batch).
  5. LLMServingSim patch rule: t_att(tier, B, L) = t_att_HBM(B, L) + (c)tier − (c)HBM with (c)HBM = column (c) of Table A — the subtraction removes HBM's own exposed gather so it is not counted twice.

16Using it: the 8-GPU-stock vs 6-GPU-custom trade study

The concrete downstream question this series serves: does a 6-GPU cluster whose GPUs carry a large-capacity custom memory tier beat an 8-GPU stock-B200 cluster, once the custom tier's gather is charged honestly? The whole machinery above collapses into a one-file change to the simulator's profile database.

The rule: patch only the pure-decode rows of attention.csv: t_att(tier, n, kv) = t_att_HBM(n, kv) + max( floor(N), a + N/b − W(n) ) − exposed_HBM(n) — the window-credited exposed gather added as a difference, so HBM's own exposure is not double-counted. Everything else in the layer (scan, top-k, projections, MoE) is tier-invariant — that is exactly what the in-situ substitution identity validated to 0.28%.

Why the GPU count itself needs no patch: the simulator looks attention up at the per-rank batch, n = Bcluster / Ngpu, so an 8→6-GPU move simply lands on larger-n rows of the same table (measured to n=1024). The patch models only the tier's access cost. Sanity built in: a tier with truly HBM-equal achieved (a, b) patches to ≈0, and the 6-GPU case then differs only through capacity and batch.

What the patch does at a=5 µs, b=400 GB/s (per decode attention row, per layer): n=8: +1.4 µs · n=16: +21.8 µs · n=32: +59.3 µs · n=64: +134.6 µs · n=176: +397.3 µs — small batches fit under the window, large ones pay the overflow; n=176 is the EP8 per-rank operating point from the capacity study.

Recipe: (1) patch_attention_csv.py --a <µs> --b <GB/s> --tag <t> emits a full profile variant (example committed: bf16-kvfp8-lpddr400). (2) 8-GPU stock: EP8Rank model slice + default variant; 6-GPU custom: EP6Rank + enlarged npu_mem capacity + --variant bf16-kvfp8-<t>. (3) Run python -m serving per config and compare TPOT at equal cluster batch. Scope caveats: decode rows only (prefill sparse attention unpatched), and the 132 B/token indexer cache is assumed to stay in HBM, matching the in-situ experiment.
