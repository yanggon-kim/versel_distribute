DeepSeek-V3.2 on B200 — Part X: Isolating the Top-2048 Gather (Exposed vs Hidden, and Four Memory Tiers)

Measured on a rented single NVIDIA B200 (SM100, 179 GiB exposed, driver 580.126.20 / CUDA 13.0), vLLM 0.25.1, DeepSeek-V3.2-Exp with dummy weights. Container allocation: 28 vCPU, 283 GB RAM, 50 GB disk — enforced as 23.8 cores of CFS quota and a 263.6 GiB memory limit. All figures on this page are generated from the committed CSVs in agent/analysis-b200-gather/.

The fused kernel already hides almost all of the gather

Two runs with identical work and identical FLOPs, differing only in where the 2048 indices point, produce a DRAM footprint difference of four orders of magnitude — 331,539 distinct 64-token pages versus exactly 32 — yet the fused kernel time changes by only 1.2–1.7 % at b=256. At b=1024 the gather moves 1.376 GB, about 172 µs of ideal 8 TB/s DRAM time, of which only 11.1–11.8 µs is exposed — roughly 93 % is hidden behind the attend compute.

For a custom HBM whose base die fronts an LPDDR extension this is the load-bearing result: because the HBM-tier gather is nearly free as currently overlapped, a slower tier's cost is almost entirely additive. The pessimistic serial bound is close to the truth for far tiers, and the optimistic bound can credit at most ~1–12 µs of hiding.

Why this run existed

The previous rental measured the DSA attention only at fused-kernel granularity. Its gather column was the whole flash_fwd_splitkv_mla_fp8_sparse kernel — the top-2048 gather and the sparse attention over those entries. At b=1 the math is under a microsecond so 12 µs was close to a true gather floor, but at b≥256 a large share of the fused time is attend compute, so there was no gather-only latency from the production path and every quoted “gather bandwidth” was bytes ÷ fused latency — a mixed lower bound.

Method: index-controlled A/B

The fused kernel gathers whatever the int32 index buffer holds; it has no opinion about where those slots point. Run (A) scatters them across the whole context (a real DRAM gather); run (B) confines them to 32 L2-resident pages (~1.34 MB). Both execute identical work otherwise — same 2048 indices per token, same 128-head attend over 2048 entries, same launches, softmax and output writes, and an identical scan/top-k/projection prologue. In t(A) − t(B) everything common cancels and what survives is the cost of fetching 656-B records from scattered DRAM instead of from L2. t(B) is itself the measured t_layer_no_gather.

Set (B) cannot be built the obvious way. The natural reading is to overwrite the index buffer before slot translation, using request-local positions [0, 2048). But every request owns disjoint KV blocks, so request-local [0,2048) lands on a different 32 pages per request — B × 1.34 MB, not 1.34 MB: 21 MB at b=16 but 344 MB at b=256 and 1.37 GB at b=1024. Set (B) would then be doing its own full DRAM gather at large batch, and t(A)−t(B) would understate the exposed gather, with the error growing in batch — worst exactly where the downstream GPU-count study needs tight interpolation. So Set (A) is applied before translation (real block-table indirection, the production pattern) and Set (B) is applied to the translation output, giving one shared hot set. Measured: Set (B) touches exactly 32 pages, independent of batch.

How we know the override really reaches the kernel, given that the fused time barely moves. Three independent checks, not timing: path instrumentation shows the translation function, the fp8 decode path and the fused-kernel wrapper each called exactly once per forward; index validity is 100.00 % (0 of 524,288 translated slots are −1, so nothing is skipped); and the distinct-page count differs 10,361×. The small latency delta is the physics, not a failed override.

Reading it per GPU count

Under the serving layout each rank runs attention for its own per-rank batch b = B_cluster / N, and gather time is a function of (b, L) only. So the batch axis is the GPU-count axis: fewer GPUs means larger b per rank and proportionally more gather. The planned comparison's per-rank operating points (137, 163, 172, 176) all fall inside 128–512, where the exposed gather runs 2.05 → 8.06 µs — though the b=256 dip noted above sits inside that interval.

Co-run interference (D6, complete on the subset grid)

Both sides must share one CUDA context or they time-slice instead of overlapping, so the co-runner runs on a second stream inside the same worker process. It is a torch gather (HBM) or a pinned-host stream (PCIe), not the TMA kernel — absolute gather times are not comparable to the microbench, but the interference is exactly the quantity of interest. The superseded row is kept in the table for traceability.

Also re-verified in the same session: the b=256 dip is real — two independent re-measurements give δ_kernel = 2.03/1.78 µs at b=256 against 3.24/3.48 at b=192 and 8.52/8.95 at b=512, so it is a genuine tiling/occupancy effect, not sweep noise. The pure-transfer tier fits at a ≈ 4–7 µs, b ≈ 5100–5900 GB/s (64–74 % of the pin rate), and hidden-gather figures are now a nosink-to-copy range rather than a single upper bound.

The consumer-stub fork (stretch goal): what is the kernel actually waiting for?

FlashMLA at the pinned commit, built twice: unmodified, and with the consumer warps keeping every barrier arrival but skipping the UMMA issues, the softmax, S writes and O rescale. The producer warps (index transform + the tma_gather4 KV fetches) and the fp8→bf16 dequant stage are untouched, so the stub time is the production KV-ingestion pipeline with the math removed. Combined with the A/B result this completes a triangulation: removing the DRAM locality cost moves the kernel 1–2 %; removing all the math moves it only ~10 %. The critical path is the KV ingestion pipeline itself — TMA issue rate at 656 B granularity, dequant staging, and per-64-token-block barrier round-trips — not DRAM bandwidth and not tensor-core math. What a base-die gather engine must beat is this pipeline's ~1.7 TB/s effective ingestion rate, not the 8 TB/s pin rate.

Caveat: the standalone harness's absolute baseline is ~2.5× the in-situ vLLM kernel at the same shape (scheduling and combine-kernel differences), so the ratio and the difference are the robust quantities; the stub's absolute time is an upper bound on the in-situ production gather.

How to charge a different memory tier: the max-overlap-window recipe

This section is self-contained: it defines every term, gives the lookup table, and shows how to predict one decoder layer's time when the KV gather is served from some other memory tier (LPDDR behind a base die, CXL, PCIe, host DRAM …) characterised by just three numbers (a, b, N).

Definitions

termmeaning
decoder layerone full transformer layer of DeepSeek-V3.2 in decode: input layernorm → sparse attention (indexer scan → top-k → the fused kernel) → output projection → MoE FFN. Everything here is per layer, per decode step; the model has 61 such layers.
fused kernelflash_fwd_splitkv_mla_fp8_sparse — the single GPU kernel that BOTH fetches the selected 2048 KV records from DRAM (the gather) AND computes the 128-head attention over them. Because both jobs live in one kernel, the gather cost cannot be read off a profiler directly — hence this page.
recordthe per-token KV entry the kernel fetches: 656 bytes = 512 B fp8 compressed latent + 16 B scale factors + 128 B bf16 RoPE part.
top-k / top-2048the sparse-attention selection: for every query token, an indexer scores all cached tokens and picks the 2048 highest; only those records are fetched and attended to.
KV block (page)the paged-KV allocation unit: 64 tokens × 656 B = 41,984 B. A per-request block table maps logical token positions to physical blocks; requests own disjoint blocks.
processing blockdistinct from the KV block: the kernel's main loop consumes the 2048 selected records in chunks of 64 records per iteration. Overlap happens at this granularity — while the math works on chunk i, the producer warps fetch chunk i+1.
gatherfetching the B × 2048 randomly-scattered 656 B records from memory. Its byte volume is N = B × 2048 × 656 (B = per-GPU decode batch); note N does not depend on context length L.
Set (A) / Set (B)the two runs of the isolation experiment. (A): indices point at scattered DRAM (real pattern). (B): indices point at one shared, L2-resident 1.3 MB hot set, making the gather ~free. Identical instruction stream otherwise.
layer_A / layer_Bmeasured time of the WHOLE decoder layer under Set (A) / Set (B). layer_B is the layer with a free gather — the t_layer_no_gather that tier substitution starts from.
fusedk_A / fusedk_Bmeasured time of just the fused kernel under Set (A) / Set (B). fusedk_B is the kernel's compute-side critical path: how long the kernel runs when fetching costs nothing.
delta_kernelfusedk_A − fusedk_B = the exposed gather on the HBM tier — the part the pipeline fails to hide (small: 0.5–12 µs).
window Wthe maximum gather time that can hide inside the kernel = W = fusedk_B. A gather faster than W is (at best) invisible; anything beyond W has nothing left to hide behind.
a, b, Nthe tier model t_gather = a + N/b: a = one-time setup / initial latency (µs), b = achieved gather bandwidth for scattered 656 B records (GB/s), N = bytes (above). The N/b term is the bandwidth cost; a captures fixed overheads.

The rule

Inside the kernel, fetching chunk i+1 overlaps computing chunk i, so to first order

t_kernel(tier) ≈ max( t_gather(tier), fusedk_B )

and therefore, at the layer level,

t_layer(tier) ≈ layer_B + max( 0, t_gather(tier) − fusedk_B )   (window-credited, optimistic)
t_layer(tier) ≈ layer_B + t_gather(tier)   (serial, pessimistic)

If t_gather ≤ W = fusedk_B the tier change is (near) free. If t_gather > W, the excess is purely additive — there is nothing left to hide it behind. On this hardware the truth sits close to the serial bound for slow tiers (see caveat 1).

The recipe

  1. Pick the operating cell (B, L). For an Ngpu-GPU cluster at total batch Bcluster, use B = Bcluster / Ngpu (gather is per-rank).
  2. Read layer_B and fusedk_B for that cell from the lookup table below (or from d2_gather_ab.csv).
  3. Compute N = B × 2048 × 656 bytes.
  4. Compute the tier's t_gather = a + N/b — with measured a and b for scattered 656 B reads (see caveat 1), like the tier fits above.
  5. Bound the layer: serial = layer_B + t_gather; window-credited = layer_B + max(0, t_gather − fusedk_B). Quote both; the truth is between, near serial for slow tiers.
  6. Model-level: multiply the per-layer delta by the layer count (61) and add to the decode-step time; TPOT then follows from the serving stack as usual.

Break-even tier bandwidth b* = N / W (GB/s)

Read the b* table before assuming anything can hide. Break-even sits at roughly 2–3 TB/s of achieved scatter bandwidth across the whole grid — approximately the fused kernel's own ingestion rate, which is no coincidence: the window is set by that same pipeline. HBM (≈2.8 TB/s achieved on 656 B records, 8 TB/s pin) clears it; no LPDDR-, CXL-, DDR- or PCIe-class tier comes close (400, ~200, 219, 36 GB/s), so for every far tier essentially the whole N/b term lands on the layer. The judgement is usually not “how much hides” but “accept N/b, or widen the window architecturally” (previous-step prefetch, above).

Caveats that keep this honest

  • Use measured (a, b), not datasheet numbers. b must be the achieved bandwidth for scattered 656 B records, which is far below pin rate, and sustaining it requires enough requests in flight: by Little's law, in-flight bytes ≈ b × round-trip latency. The kernel's own buffering (~2 × 42 KB per CTA, sized for HBM) cannot supply that for a high-latency tier — the tier's gather engine must bring its own parallelism, or the real cost exceeds a + N/b and the serial bound is the right one.
  • Overlap is per-processing-block (64 records at a time), not lump-sum: window time from early chunks cannot be banked against a slow tail.
  • The window can be architecturally widened. Indices exist only after top-k, so today W = fusedk_B. But the co-run measurement above showed the rest of the layer leaves HBM bandwidth essentially idle, so a base die that prefetches on the previous step's indices could stretch the window toward the whole layer (~layer_B) for the recurring-index fraction.
  • layer_B is a 1-layer dummy-weight measurement at TP1; it carries the profiling harness's per-forward overheads. For simulator use, apply the delta (the max-window rule) on top of your calibrated layer time rather than treating layer_B as gospel.

Honesty box

  • D6 is complete on the subset grid, but its co-runner is a torch gather rather than the TMA kernel, so absolute gather times are not comparable to the microbench, and the (64,128K) PCIe row from the first attempt is superseded (unmatched copy size).
  • D7 (consumer-stub fork) done; its standalone harness runs ~2.5× slower in absolute terms than the in-situ kernel, so quote its ratio/difference, not its absolute latencies.
  • Six masked cells, recorded rather than skipped: (512, 512K), (1024, 512K), (192, 1M), (256, 1M), (512, 1M), (1024, 1M) — each exceeds the 193.6 M-token KV budget.
  • Dummy weights. The indexer's natural top-k comes from random weights, so its distribution is not a real workload's. That is exactly why Set (A) is index-controlled, and the uncontrolled selections are recorded separately.
  • delta_layer is noise-dominated (≤0 in 19/34 cells); the kernel-level estimator is used throughout.
  • b=256 dip verified reproducible (2.03/1.78 vs 3.24/3.48 µs at b=192) — a real effect inside the protected interpolation interval; treat fits crossing b=256 with care.
  • tma_read anomaly resolved as consumer-side via the no-consume variant; hidden-gather figures are a nosink-to-copy range.
  • fault_cold is untrustworthy here — the UVM pool is reused across cells so pages stay device-resident; two fixes were attempted and cold rates still exceed the PCIe link rate. Only mapped mode feeds the fits.
  • No hardware counters. ncu exists on the box but is permission-blocked (ERR_NVGPUCTRPERM) and predates SM100, so every measurement here uses CUDA-event timing or vLLM's layerwise profile tree.
  • All three anchor checks passed, so there are no anchor misses to declare.
