§Overview in one minute

DeepSeek Sparse Attention (DSA) is usually described as “attention that stays cheap at long context”. Measured, that is only half true — and the half that is false is the half that decides how you build a serving cluster.

Plain-language thesis. DSA makes the part of attention that reads KV cheap — it attends to a fixed top-2048 no matter how long the context is. But something still has to decide which 2048, and that decision is a lightning indexer that scans every token in the cache. So a V3.2 layer is flat in the attend and linear in the scan. At short context the scan is invisible; at long context it is the whole story.
The consequence. Long context does not make V3.2 attention-cheap; it makes V3.2 attention-bound. At batch 64 the decoder layer goes from 2,974.7 µs to 5,518.8 µs, and attention overtakes the 256-expert MoE block on the way.

1What DSA changes, mechanically

Why the cost splits into a flat part and a linear part.

A V3.2 decoder layer runs two RMSNorms, one attention block and one MoE block. The attention block is classic multi-head latent attention (MLA) — one shared latent per token, kv_lora_rank 512 plus a 64-dim RoPE part — wrapped around a lightning indexer. Per token per layer the cache holds 656 B of main MLA latent plus 132 B of indexer key.

On every decode step, for every sequence in the batch, the indexer scans that sequence’s entire 132 B/token key cache to pick the top index_topk = 2048 tokens. FlashMLA then attends over exactly those 2048. So:

  • The attend is O(1) in context — fixed at 2048 selected tokens. This is the part the “sparse attention is cheap” story is about, and it is real.
  • The scan is O(batch × context) — every cached token is touched to be ranked. This part is bandwidth-bound and it is what the measurement below exposes.
A back-of-envelope that the data confirms. At batch 64 with 1M context the indexer must read 64 × 1,048,576 × 132 B ≈ 8.9 GB per layer per step. The measured excess over the short-context baseline implies an effective ≈3.5 TB/s — about 73% of the H200’s peak HBM bandwidth, which is what a well-tuned streaming scan should achieve. The model and the measurement agree.

3Where the time goes

The same layer, decomposed — batch 64, across context.

Composition of one MoE decoder layer at decode batch 64. Percentage above each bar is attention’s share.

At short context the layer is an MoE layer with some attention attached: the 256-expert block dominates and the picture matches conventional MoE intuition. At long context that inverts completely — the MoE block does not change at all (it depends on token count, not context), while attention grows without bound.

Why this matters for a cluster. The MoE block is what expert parallelism exists to spread. If long-context serving is attention-bound, adding EP ranks buys progressively less, and the binding constraint moves to KV-cache bandwidth and capacity instead.

Two things read straight off these. The MoE block (green) is nearly the same height at every batch within a panel — it saturates at batch 32 and then barely grows — while the attention block (blue) climbs steadily with batch, because the indexer scan is ∝ batch × context. So batching converts an MoE-dominated layer into an attention-dominated one, and it happens sooner at longer context: attention’s share crosses 50% only at the largest batches at 128K, but is already the majority across most of the batch range at 1M. Latency (bar height) rises with both knobs, but for different reasons — MoE height is set by context (flat) and attention height by batch×context.

The crossover is not monotonic in batch — it is U-shaped, and the shape falls straight out of how the two blocks scale.

  • Batch 1–2: attention-bound almost immediately. A single token activates only 8 of the 256 experts, so the MoE block is tiny and even a short scan outweighs it.
  • Batch 4–32: MoE-bound throughout. Here each added token still lights up more experts, so MoE cost climbs steeply with batch while the scan is still small. Attention never catches up inside a 1M context.
  • Batch ≥64: attention-bound again, and progressively sooner. Once the batch is large enough to activate all 256 experts, MoE saturates — extra tokens are nearly free for it. The indexer scan keeps growing with batch × context, so the crossover marches from 1M at batch 64 down to 64K at batch 1024.
The operating regime that matters is the third one. Any deployment serving many concurrent users at long context sits there, and in it the decoder layer is attention-bound and getting worse with both knobs at once.

6Contrast with DeepSeek-V4

The same measurement path, run against the V4 bundle from Part V.

V4’s Sparse-MLA compresses KV temporally before selection, so its indexer works over a compressed sequence and its decode attention is close to flat in context. Measured on B200 through this same lookup code, one V4 layer’s attention at batch 64 moves 203.9 → 240.8 µs from 8K to 128K — about +18%. Over a comparable span (4K → 128K) V3.2’s attention moves 287.8 → 612.6 µs — +113% — and unlike V4 it never levels off, reaching 2,816.3 µs at 1M.

The two were profiled on different hardware (V4 on B200, V3.2 on H200), so the absolute microseconds are not directly comparable. The shape is the point: V4 is asymptotically flat in context, V3.2 asymptotically linear.

Read this as a design trade, not a verdict. V4 buys flat long-context attention with a lossy temporal compression of the cache. V3.2 keeps every token addressable at full fidelity and pays a scan to rank them. Which is better depends on whether your workload can tolerate the compression — but they have genuinely different serving cost curves, and a capacity plan built on one does not transfer to the other.

The gather is a 2–4% sliver at modest batch, but climbs to 27% at batch 1024 and 4K context. That rise with batch is the surprising one, so it is worth spelling out.

Why more batch means a bigger gather share. The share is gather ÷ layer, and the two scale with batch completely differently:
  • The gather grows linearly with batch — each query gathers its own fixed 2048 latents (~1.6 µs/query, §7). From batch 64 to 1024 at 4K it grows 15× (105 → 1,597 µs).
  • The layer barely grows, because its dominant cost — the MoE block — has saturated. Past batch 32 all 256 experts are already active (§3), so more tokens add no experts and the MoE cost is nearly flat: over the same 64 → 1024 it grows just 1.2×, and the whole layer only 1.9× (2,990 → 5,827 µs).
A numerator growing 15× over a denominator growing 1.9× — the fraction has to climb. In short: batching stops making the layer’s big block (MoE) more expensive but keeps making the gather more expensive, so the gather eats an ever-larger slice.

Two footnotes to that. Below saturation (batch 1–32) the share actually dips — there the MoE is still growing faster than the gather (each token lights up more experts), so it outruns the numerator. And along every row the share falls with context: the gather is flat in context (§7), but the scan inflates the layer as context grows, shrinking the fixed gather’s slice. So the gather only matters in the high-throughput, short-context corner — and even there it is dwarfed by the scan at long context.

Does a simple a + N/b model fit?

The gather reads, per query, the 2048 selected main-MLA latents at 656 B each (the fp8_ds_mla layout) = 1.34 MB/query, and that scales with batch, not context. Fitting gather(B) = a + N/b with N = B × 1.34 MB gives a clean line (±1% in the saturated regime):

870 GB/s
fitted b — effective gather bandwidth (18% of the H200’s 4.8 TB/s peak)
10.8 µs
fitted a — the fixed intercept (see the caveat)

the scan’s bandwidth for contrast (86% of peak) — same HBM, contiguous
b makes sense — as a gather. 870 GB/s is only 18% of peak, but that is the signature of a scatter: each query pulls 2048 non-contiguous 656 B latents chosen by the indexer, and random HBM access runs far below streaming peak. The contiguous scan on the same memory reaches 4.15 TB/s (86% of peak) — a 4.8× efficiency gap between reading scattered and reading in order. (One caveat: this kernel gathers and attends, so b folds the MLA attend compute into the number — it is an effective throughput, not raw DRAM bandwidth.)
a does NOT make sense as HBM access latency. Real HBM latency is a few hundred nanoseconds; the fitted 10.8 µs is 30–100× that. It is kernel launch plus the small-batch occupancy floor, not memory latency. The batch-1 point proves it: one query gathers 1.34 MB, which at peak bandwidth is ~0.3 µs of transfer, yet the measured batch-1 gather is 11.5 µs… an order of magnitude of pure overhead, because a single query cannot fill the GPU.
Why the gather is not the story. At batch 64, 1M context the gather is 105.0 µs while the scan that finds those 2048 tokens is 2,134 µs — 20× more. DSA’s long-context cost is finding the top-2048 (a linear scan), not reading them (a bounded, flat gather). “Sparse attention is cheap” is true only of the gather.

The AI column is arithmetic intensity — FLOPs per byte of HBM traffic, computed analytically at this shape (fp8 weights, bf16 activations). It says how memory-bound each kernel is: on the H200 the roofline ridge is ~412 FLOP/byte (fp8) / ~206 (bf16) — below it a kernel is bandwidth-bound, above it compute-bound. Every kernel here is below the ridge, so the whole decode is memory-bound; the AI just says by how much. The projection GEMMs sit around 119 (weight-load bound — at decode each token reads the weight once, so AI ≈ 2×batch), the scan is ~124 but reads the KV cache at 85% of peak bandwidth, and the gather+attend is ~400 (right at the ridge, the one near-balanced kernel).

The picture in one line: the indexer scan and top-k are the two kernels that grow with context; everything else — the projections, the gather, the FlashMLA attend — is fixed. At 128K the scan is already the single largest kernel in the layer.

The routed experts are the block, and they are weight-streaming bound: AI = 4. The grouped GEMM (fused_moe_kernel, ×2 for up/down) is 2.56 ms — 95% of the block — and it moves the full 11.3 GB of all 256 experts’ fp8 weights to process only ~2 tokens each. That is an arithmetic intensity of just 4 FLOP/byte (vs the 412 ridge), and it runs at 92% of peak HBM bandwidth — the layer’s one truly bandwidth-saturating kernel. Because the weight traffic is set by the expert count, not the token count, the block barely grows once all 256 experts are active (§3): more tokens make each per-expert matmul slightly larger but add no weight to stream. That is the throughput sweet spot in §10, and it is a memory-bandwidth effect end to end.
How AI moves with batch. Arithmetic intensity is not fixed — it rises with batch, because more tokens reuse the same weights. For the dense GEMMs AI ≈ 2×batch, so they only cross the ridge into compute-bound above batch ~206. The routed experts are far worse: AI ≈ batch ÷ 16 (each expert still sees only batch×8÷256 tokens), so they stay memory-bound across the entire serving range. DeepSeek-V3.2 decode is a memory-bandwidth problem, and the MoE weights are the largest part of it.

How the lightning indexer’s scan scales

The three marked rows above are the lightning indexer — at 128K context it is 365 µs, 60% of the attention block, and the scan is the bulk of it. The scan is the one kernel whose cost grows with the serving knobs, so it is worth seeing on its own. It reads every cached token’s 132 B indexer key, for every query, to produce the index scores — so its work is batch × context.

Every long-context conclusion in this report — the crossover (§4), the throughput ceiling (§10) — traces back to this line.

Two things fall out, and the second is the one that matters for offloading:

  • The scatter penalty is small — the tier is everything. The gather runs at 71–96% of a matched sequential copy on every tier: a 656 B record is 164 contiguous words, a big enough transaction that random placement barely hurts. So the gather is not slow because it is scattered — it is exactly as fast as the memory it lands on. (This refines §7’s “18% of peak”: that gap was op-shape — a copy that also writes, vs the streaming scan — not randomness.)
  • Off-HBM is 18–44× slower. The a + N/b model from §7 holds per tier; only b changes — 929 GB/s on HBM, 51 GB/s on CPU DRAM, 21 GB/s over PCIe. The PCIe path is a flat wall (gen5 ×16 tops out ~35 GB/s of read; the gather takes 60% of that).
Offloading the latents off HBM backfires. A batch-1024 gather is 1.48 ms in HBM but 64 ms over PCIe — per layer, per decode step, so ~3.7 s across 58 MoE layers just to gather. DSA’s indexer already makes the scan the long-context cost (§7); moving the gathered latents to CPU DRAM would not relieve that, it would add a second, worse bottleneck. The 656 B main latent has to stay in HBM; only colder tiers are plausible offload candidates, and only if the scan that reads them can be pushed near the memory.

  • The MoE dead zone (batch 1–32): batching barely helps. Below 32, every added token activates more of the 256 experts (§3), so the MoE block grows nearly in proportion to batch — no economy of scale. The worst step is 16 → 32: batch doubles, throughput rises just 6% (177 → 188 tok/s at 1K).

A production TP/EP setup shifts the absolute tok/s, but the shape — the batch-32 knee and the context-dependent ceiling — is the transferable result.

Why this sets up the next section. DSA moves the dominant long-context operation off the compute roof onto the memory roof, leaving most of a datacenter GPU’s FLOP engine unused. You don’t need 1979 TFLOP/s to run a 124-intensity streaming reduction — you need bandwidth next to the KV. That is the case for near-memory processing.

12An architecture note: the indexer on an HBM base die

A forward-looking read, not a measurement. Everything above says the long-context cost is the indexer scan — a memory-bound sweep that decides which KV to read. That makes it the natural candidate for near-memory processing in a capacity-expanded HBM: run the indexer on the HBM base die, and let the base die drive the fetch from an LPDDR capacity tier over UCIe.

The proposal: indexer keys stay in HBM, the base die scans them and selects the top-2048, then fetches only those latents from LPDDR over UCIe — the index never leaves the die that uses it.

Why the indexer, and not the other blocks

Everything in decode is memory-bound (§8), so that alone does not single it out. Three properties do, and no other block has all three:

  • It is a data-reduction. The scan reads a lot (132 B × context per query) and emits almost nothing (2048 indices). Near-memory processing exists to reduce near the data and ship only the small result — exactly this shape. The MoE experts are more bandwidth-bound (AI = 4) but they read weights, need real matmul throughput, and their weights want to stay in HBM (reused every step, not a capacity problem) — a poor NMP fit.
  • It is the fetch address. The index is not an intermediate — it is the LPDDR address list. Computing it anywhere but the LPDDR-facing die means a round trip (GPU → scores → GPU → fetch). The base die is the one place with both HBM access (the keys) and the UCIe link (the latents), so index-and-fetch collapse to one hop.
  • It is the long-context bottleneck (§7–§8): 45% of the attention block at 128K, 76% at 1M. Offloading it is where the payoff is.

The refinement the data forces: tier by key vs latent

The KV splits into two halves with opposite access patterns, and they should live in different tiers:

indexer keymain latent
size132 B/token (17% of KV)656 B/token (83%)
read bythe scan — every token, every stepthe gather — 2048 selected, every step
bandwidthO(batch × context) — huge, context-scalingO(batch × 2048) — fixed, flat in context
tierHBM (hot, near the scan)LPDDR (cold bulk, sparse)

Keeping keys in HBM and latents in LPDDR offloads 83% of the KV capacity to LPDDR while keeping the bandwidth-critical half fast. The selected-latent gather is bounded and context-flat (~5 GB/step across all layers at batch 64), so LPDDR bandwidth is a manageable target there.

The wall to design around

NMP does not make the scan cheaper — it must read batch × context × 132 B every step wherever the keys live. That is the hard constraint:

The scan’s bandwidth is fundamental, so the keys must stay in HBM. At batch 64 / 1M the scan reads ~540 GB/step across layers — ~113 ms at HBM’s 4.8 TB/s, but ~1.1 s at an LPDDR-class ~500 GB/s. Putting the scan on the base die only wins if it reads the keys from HBM (or its own near-DRAM); if the keys are in LPDDR it is LPDDR-bandwidth-bound no matter where the compute sits. Keys fit in ~100 GB of HBM up to roughly batch×context ≈ 12 M token-seqs (batch 8 at 1M, batch 64 at ~190K); beyond that they spill and the scan slows. Modelling that crossover is the core of the study.
And the base die needs the compute. The scan is memory-bound on a GPU tensor core, but it still burned ~500 TFLOPS to keep pace with 85% of HBM bandwidth at 128K (AI ≈ 124 — 64 index heads × 128 dims is not free). A base die under a DRAM stack has a small fraction of that and a hard thermal budget, so the realistic failure mode is a scan that is compute-limited on the base die, not bandwidth-limited. The make-or-break number is the indexer’s FLOP/token against a realizable near-DRAM MAC array (and whether a cheaper scoring approximation gets there).

How many TOPS does the base die need?

To make the base die’s compute budget concrete: the scan does 16,384 fp8 ops per (query, token) (64 index heads × 128 dims), for a fixed arithmetic intensity of 124 FLOP/byte. On the GPU the scan is bandwidth-bound — it lands at ~496 TOPS not because it needs that much compute, but because that is the rate that keeps pace with ~4 TB/s of key streaming. So the requirement falls straight out of the roofline:

TOPS = arithmetic intensity × bandwidth =  124 × BW. To keep pace with the ~4 TB/s the scan streams, the base die needs ~496 TOPS (fp8) to match the GPU on the single-request critical path (~596 to feed the full 4.8 TB/s PHY). This is shape-independent — both the ops and the bytes scale with batch×context, so the required rate does not move with either knob.

The parallel q_b overlap barely helps. q_b is genuinely independent (both it and the indexer branch off the query latent and reconverge at the attend), but it is only ~19 µs against the indexer’s ~365 µs, so hiding it relaxes the budget ~5% — and it is the only independent work in single-stream decode, since everything after the indexer needs its indices.

The real lever: overlap the indexer with a neighbour’s MoE

The requirement collapses if the base die scans microbatch B’s keys while the GPU runs microbatch A’s MoE. It only has to finish within that MoE window, so TOPS ≈ indexer ops ÷ MoE time — and that is context-dependent, because the indexer’s share of the layer grows with context:

contextindexer % of layerbase-die TOPS to hide it
128K11%47 TOPS
512K31%187 TOPS
1M47%373 TOPS
Why the overlap is free — and the real payoff. The indexer reads keys over the internal TSVs; the MoE reads expert weights over the external PHY (it is 92%-bandwidth-bound, §8). Those are different bandwidth domains, so running them concurrently costs nothing on the bandwidth side. In the all-GPU design both contend for the one 4.8 TB/s PHY; moving the indexer to the base die partitions the two onto separate paths. So the base-die compute you buy purchases both the LPDDR capacity tier and a free indexer / MoE overlap — the point is not that the base die out-computes the GPU (it cannot), but that it moves a PHY-contending, bandwidth-bound op onto an otherwise-idle path.

Thermal reality — where the design lands

A dedicated fp8 systolic array at ~0.05 pJ/op sets the budget:

Aim for ~100–200 TOPS. A base-die thermal budget under the DRAM stack is realistically ~5–15 W, i.e. ~100–200 TOPS — not the ~496 needed for single-request latency parity at any context. But ~100–200 TOPS is enough to hide the indexer behind the MoE up to ~256–512K context, a large useful envelope. Beyond that the scan’s share outgrows what fits, and you either accept it partly on the critical path (a latency-for-capacity trade — still a win, since without LPDDR that context does not fit at all) or cut the indexer compute: fewer index heads, int4 / approximate scoring, or a coarse first-pass filter before the full 128-dim dot.
Verdict. It is the right operation to offload — the only one that is simultaneously memory-bound, a reduction, and the generator of the LPDDR access itself. The real prize is the co-location (index and fetch on the same die), which removes a control round trip, not just bandwidth. The open questions are quantitative: (1) base-die compute vs the indexer’s FLOP/token; (2) the key-capacity crossover from HBM to LPDDR; (3) UCIe bandwidth and random-access efficiency for the scattered 2048×656 B gather. All three are answerable from the profile data this report is built on.

Why the winner is who it is: S1 vs S1.5 vs S2, mechanically

All three designs run the same logical pipeline per layer — qkv_a → indexer queries → SCAN → top-2048 → GATHER → attend → o_proj — and differ only in which engine executes the scan and which engine executes the gather.

S1 → S1.5: what “base-die gather” means, and why it beats GPU-driven gather. After top-k you hold 2048 indices per query; the 656 B latent records they point to live in LPDDR, reachable only through the UCIe controller on each cube’s base die. The question is who turns indices into data. GPU-driven (S1): GPU threads issue loads to remote LPDDR addresses. Requests are cacheline-grained (128 B), so one 656 B record becomes ~5–6 transactions; remote memory is not L2-cached (the same behaviour verified on Grace C2C), so each pays the full ~500–800 ns round trip; and an SM keeps only a limited number of remote loads in flight — the link runs latency-bound at ~50% efficiency → 97 µs, while occupying GPU load/store units the whole time. Base-die (S1.5): the GPU ships the tiny thing — the index list (2048×4 B ≈ 8 KB per query) — down to the die. A DMA engine sitting next to the UCIe controller translates indices to addresses, issues native 656 B burst reads with a deep (~64-entry) outstanding queue that hides the latency, coalesces neighbours, and streams the result back up the PHY as one packed sequential buffer the attend then reads at streaming speed — ~80% efficiency → 61 µs, with the GPU’s SMs free. Ship the small descriptor to the data, stream the big payload back in bulk: the classic near-memory move, and it needs no MAC array — just a DMA block. Net: 97 → 61 µs/layer ≈ 2.2 ms/step ≈ +4% throughput for a thermally free piece of hardware (5,515 → 5,756 tok/s).

S1.5 → S2: why also moving the scan onto the NPU is slower at feasible TOPS. The scan is identical work either way — 640 MB of keys, 79.4 GFLOP per layer at b=37. Only the engine changes, and the two engines are wildly mismatched:

And there is nothing to overlap the loss against. The scan sits on the critical path in every design: the attend cannot start before top-k, the next layer’s queries do not exist until this layer finishes, and the only concurrent GPU work is the 15 µs q_b projection. Offloading the scan does free GPU HBM bandwidth — but during the attention phase nothing else wants it (the MoE runs later, sequentially), so the freed bandwidth buys zero critical-path time. S2 at 200 TOPS is therefore S1.5 plus a pure +238 µs/layer loss (397 vs 159). The crossover where the on-die scan catches the GPU is ~357 TOPS/GPU (~45 TOPS/cube, ~18 W) — above the comfortable budget. Hence adaptive placement: the gather is latency/protocol-limited, so a smart engine next to the memory always wins it; the scan is compute-hungry, so it belongs to whichever engine has both the data at hand and the most TOPS — the GPU while keys are HBM-resident, the base die once they spill (where the GPU’s alternative collapses to a 2.74 ms UCIe-streamed scan and even 200 TOPS wins).

Partial offload: split the indexer by arithmetic intensity (“S1.75”)

S2 failed because it moved the whole indexer — including the AI=124 scan — onto a compute-poor die. But the kernel table (§8) says the indexer is not one kernel; it is three, with wildly different compute-per-byte:

The top-k reads the logits array (37×131072×~4 B ≈ 19 MB/layer), does about one compare per byte, and emits 8 KB of indices — a pure data-reduction at AI≈1 that a few GOPS handle. Better: its output is the gather’s input, so top-k and gather fuse on the die and the indices never visit the GPU at all. The GPU scan writes logits to HBM as it already does; the die streams them up the TSVs (~4 µs), selects as scan tiles complete (visible tail ~5 µs vs the GPU’s 46 µs kernel). And since the 200 TOPS MAC array is now otherwise idle, a further increment — co-scan — splits the key stream ~72:28 between GPU (bandwidth-bound, 4.15 TB/s) and die (compute-bound, 200 TOPS), the two reading over different paths (PHY vs TSV), with the die merging both logit streams: scan 159 → ~111 µs.

13Method & caveats

  • Measurement. vLLM 0.25.1 layerwise profiling of a 1-layer dummy-weight DeepSeek-V3.2-Exp on one H200 (SM90), fp8_ds_mla KV cache, FlashMLA-sparse backend, enforce_eager, tp1. No checkpoint weights are downloaded — only kernel shapes and timings matter.
  • Composition. Per-layer totals are assembled from the per-category CSVs by calling LLMServingSim’s own lookup functions, so these numbers are exactly what the simulator replays, including its interpolation and its extrapolation past the profiled grid.
  • Compute-only. Tensor- and expert-parallel collectives are costed by ASTRA-Sim, not by these tables. At the tp1/ep1 configuration profiled here there are none, so the figures are complete for that case — but a tp8/ep8 deployment adds communication on top.
  • MoE backend is Triton, vLLM’s own selection on SM90. A DeepGEMM-tuned deployment would shift the MoE bars down and therefore move the crossover to shorter context, which strengthens rather than weakens the conclusion.
  • Beyond 163,840 tokens the model is not numerically V3.2. vLLM sizes the YaRN RoPE cache as original_max_position_embeddings × factor and ignores max_position_embeddings, so the profiling run raises factor to cover 1M positions. That changes the values in the cos/sin cache, not the shape or cost of any kernel — timings are unaffected, and positions past the trained range are meaningless for output quality regardless.
  • Faded table cells are interpolated, not measured. The measured KV axis is 16, 64, 256, 1,024, 4,096, 16,384, 65,536, 131,072, 262,144, 524,288, 1,048,576.
