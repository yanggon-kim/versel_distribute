DeepSeek-V3.2 Sparse Attention — Part VI

Part V measured one DeepSeek-V4 decoder layer at a single batch shape. This part asks the serving question instead: how does one V3.2 decoder layer scale with the two knobs an operator actually controls — how many users are decoding at once, and how long their conversations are? Measured on a single NVIDIA H200 via vLLM layerwise profiling, then composed through the LLMServingSim lookup path.

§Overview in one minute

DeepSeek Sparse Attention (DSA) is usually described as “attention that stays cheap at long context”. Measured, that is only half true — and the half that is false is the half that decides how you build a serving cluster.

Plain-language thesis. DSA makes the part of attention that reads KV cheap — it attends to a fixed top-2048 no matter how long the context is. But something still has to decide which 2048, and that decision is a lightning indexer that scans every token in the cache. So a V3.2 layer is flat in the attend and linear in the scan. At short context the scan is invisible; at long context it is the whole story.
The consequence. Long context does not make V3.2 attention-cheap; it makes V3.2 attention-bound. At batch 64 the decoder layer goes from 2,974.7 µs to 5,518.8 µs, and attention overtakes the 256-expert MoE block on the way.

1What DSA changes, mechanically

Why the cost splits into a flat part and a linear part.

A V3.2 decoder layer runs two RMSNorms, one attention block and one MoE block. The attention block is classic multi-head latent attention (MLA) — one shared latent per token, kv_lora_rank 512 plus a 64-dim RoPE part — wrapped around a lightning indexer. Per token per layer the cache holds 656 B of main MLA latent plus 132 B of indexer key.

On every decode step, for every sequence in the batch, the indexer scans that sequence’s entire 132 B/token key cache to pick the top index_topk = 2048 tokens. FlashMLA then attends over exactly those 2048. So:

  • The attend is O(1) in context — fixed at 2048 selected tokens. This is the part the “sparse attention is cheap” story is about, and it is real.
  • The scan is O(batch × context) — every cached token is touched to be ranked. This part is bandwidth-bound and it is what the measurement below exposes.
A back-of-envelope that the data confirms. At batch 64 with 1M context the indexer must read 64 × 1,048,576 × 132 B ≈ 8.9 GB per layer per step. The measured excess over the short-context baseline implies an effective ≈3.5 TB/s — about 73% of the H200’s peak HBM bandwidth, which is what a well-tuned streaming scan should achieve. The model and the measurement agree.

2The decode surface

One MoE decoder layer, GPU time, across batch size and context length.

One MoE decoder layer at decode — log–log. Flat left, linear right: the knee is where the indexer scan overtakes the fixed per-step cost.

Every curve has the same shape: flat while the scan is negligible, then a straight linear climb once it dominates. Increasing batch raises the floor and moves the knee left, because the scan cost is proportional to the product of the two axes.

The floors are not evenly spaced. Between batch 32 and batch 64 the curve barely moves (2,916.2 µs → 2,974.7 µs at 1K) because the MoE block has already saturated: at batch 32 a step activates all 256 experts, and beyond that point more tokens are nearly free for MoE. Everything above that batch is the indexer talking.

3Where the time goes

The same layer, decomposed — batch 64, across context.

Composition of one MoE decoder layer at decode batch 64. Percentage above each bar is attention’s share.

At short context the layer is an MoE layer with some attention attached: the 256-expert block dominates and the picture matches conventional MoE intuition. At long context that inverts completely — the MoE block does not change at all (it depends on token count, not context), while attention grows without bound.

Why this matters for a cluster. The MoE block is what expert parallelism exists to spread. If long-context serving is attention-bound, adding EP ranks buys progressively less, and the binding constraint moves to KV-cache bandwidth and capacity instead.

The crossover is not monotonic in batch — it is U-shaped, and the shape falls straight out of how the two blocks scale.

  • Batch 1–2: attention-bound almost immediately. A single token activates only 8 of the 256 experts, so the MoE block is tiny and even a short scan outweighs it.
  • Batch 4–32: MoE-bound throughout. Here each added token still lights up more experts, so MoE cost climbs steeply with batch while the scan is still small. Attention never catches up inside a 1M context.
  • Batch ≥64: attention-bound again, and progressively sooner. Once the batch is large enough to activate all 256 experts, MoE saturates — extra tokens are nearly free for it. The indexer scan keeps growing with batch × context, so the crossover marches from 1M at batch 64 down to 64K at batch 1024.
The operating regime that matters is the third one. Any deployment serving many concurrent users at long context sits there, and in it the decoder layer is attention-bound and getting worse with both knobs at once.

The first three layers are different

V3.2 sets first_k_dense_replace = 3, so layers 0–2 run a dense MLP instead of the MoE block — 58 of 61 layers are MoE. A dense layer at batch 64 / 1M context costs 2,940.9 µs, versus 5,518.8 µs for a MoE layer.

6Contrast with DeepSeek-V4

The same measurement path, run against the V4 bundle from Part V.

V4’s Sparse-MLA compresses KV temporally before selection, so its indexer works over a compressed sequence and its decode attention is close to flat in context. Measured on B200 through this same lookup code, one V4 layer’s attention at batch 64 moves 203.9 → 240.8 µs from 8K to 128K — about +18%. Over a comparable span (4K → 128K) V3.2’s attention moves 287.8 → 612.6 µs — +113% — and unlike V4 it never levels off, reaching 2,816.3 µs at 1M.

The two were profiled on different hardware (V4 on B200, V3.2 on H200), so the absolute microseconds are not directly comparable. The shape is the point: V4 is asymptotically flat in context, V3.2 asymptotically linear.

Read this as a design trade, not a verdict. V4 buys flat long-context attention with a lossy temporal compression of the cache. V3.2 keeps every token addressable at full fidelity and pays a scan to rank them. Which is better depends on whether your workload can tolerate the compression — but they have genuinely different serving cost curves, and a capacity plan built on one does not transfer to the other.

7Method & caveats

  • Measurement. vLLM 0.25.1 layerwise profiling of a 1-layer dummy-weight DeepSeek-V3.2-Exp on one H200 (SM90), fp8_ds_mla KV cache, FlashMLA-sparse backend, enforce_eager, tp1. No checkpoint weights are downloaded — only kernel shapes and timings matter.
  • Composition. Per-layer totals are assembled from the per-category CSVs by calling LLMServingSim’s own lookup functions, so these numbers are exactly what the simulator replays, including its interpolation and its extrapolation past the profiled grid.
  • Compute-only. Tensor- and expert-parallel collectives are costed by ASTRA-Sim, not by these tables. At the tp1/ep1 configuration profiled here there are none, so the figures are complete for that case — but a tp8/ep8 deployment adds communication on top.
  • MoE backend is Triton, vLLM’s own selection on SM90. A DeepGEMM-tuned deployment would shift the MoE bars down and therefore move the crossover to shorter context, which strengthens rather than weakens the conclusion.
  • Beyond 163,840 tokens the model is not numerically V3.2. vLLM sizes the YaRN RoPE cache as original_max_position_embeddings × factor and ignores max_position_embeddings, so the profiling run raises factor to cover 1M positions. That changes the values in the cos/sin cache, not the shape or cost of any kernel — timings are unaffected, and positions past the trained range are meaningless for output quality regardless.
  • Faded table cells are interpolated, not measured. The measured KV axis is 16, 64, 256, 1,024, 4,096, 16,384, 65,536, 131,072, 262,144, 524,288, 1,048,576.
