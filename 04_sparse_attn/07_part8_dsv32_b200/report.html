§Overview in one minute

DeepSeek Sparse Attention (DSA) is usually described as “attention that stays cheap at long context”. Measured, that is only half true — and the half that is false is the half that decides how you build a serving cluster.

Plain-language thesis. DSA makes the part of attention that reads KV cheap — it attends to a fixed top-2048 no matter how long the context is. But something still has to decide which 2048, and that decision is a lightning indexer that scans every token in the cache. So a V3.2 layer is flat in the attend and linear in the scan. At short context the scan is invisible; at long context it is the whole story.
The consequence. Long context does not make V3.2 attention-cheap; it makes V3.2 attention-bound. At batch 64 the decoder layer goes from 625.0 µs to 2,337.1 µs, and attention overtakes the 256-expert MoE block on the way.

1What DSA changes, mechanically

Why the cost splits into a flat part and a linear part.

A V3.2 decoder layer runs two RMSNorms, one attention block and one MoE block. The attention block is classic multi-head latent attention (MLA) — one shared latent per token, kv_lora_rank 512 plus a 64-dim RoPE part — wrapped around a lightning indexer. Per token per layer the cache holds 656 B of main MLA latent plus 132 B of indexer key.

On every decode step, for every sequence in the batch, the indexer scans that sequence’s entire 132 B/token key cache to pick the top index_topk = 2048 tokens. FlashMLA then attends over exactly those 2048. So:

  • The attend is O(1) in context — fixed at 2048 selected tokens. This is the part the “sparse attention is cheap” story is about, and it is real.
  • The scan is O(batch × context) — every cached token is touched to be ranked. This part is bandwidth-bound and it is what the measurement below exposes.
A back-of-envelope that the data confirms. At batch 64 with 1M context the indexer must read 64 × 1,048,576 × 132 B ≈ 8.9 GB per layer per step. The measured excess over the short-context baseline implies an effective ≈5.2 TB/s — about 66% of the B200’s 8 TB/s peak HBM bandwidth (rising to ≈5.9 TB/s, 74%, at batch 128). The sm100 scan streams somewhat further from peak than its sm90 counterpart did (73%) — §12 quantifies this.

3Where the time goes

The same layer, decomposed — batch 64, across context.

Composition of one MoE decoder layer at decode batch 64. Percentage above each bar is attention’s share.

At short context the layer is an MoE layer with some attention attached: the 256-expert block dominates and the picture matches conventional MoE intuition. At long context that inverts completely — the MoE block does not change at all (it depends on token count, not context), while attention grows without bound.

Why this matters for a cluster. The MoE block is what expert parallelism exists to spread. If long-context serving is attention-bound, adding EP ranks buys progressively less, and the binding constraint moves to KV-cache bandwidth and capacity instead.

Two things read straight off these. The MoE block (green) is nearly the same height at every batch within a panel — it saturates at batch 32 and then barely grows — while the attention block (blue) climbs steadily with batch, because the indexer scan is ∝ batch × context. So batching converts an MoE-dominated layer into an attention-dominated one, and it happens sooner at longer context: attention’s share crosses 50% only at the largest batches at 128K, but is already the majority across most of the batch range at 1M. Latency (bar height) rises with both knobs, but for different reasons — MoE height is set by context (flat) and attention height by batch×context.

The crossover is not monotonic in batch — it is U-shaped, and the shape falls straight out of how the two blocks scale.

  • Batch 1–2: attention-bound almost immediately. A single token activates only 8 of the 256 experts, so the MoE block is tiny and even a short scan outweighs it.
  • Batch 4–32: MoE-bound throughout. Here each added token still lights up more experts, so MoE cost climbs steeply with batch while the scan is still small. Attention never catches up inside a 1M context.
  • Batch ≥64: attention-bound again, and progressively sooner. Once the batch is large enough to activate all 256 experts, MoE saturates — extra tokens are nearly free for it. The indexer scan keeps growing with batch × context, so the crossover marches from 1M at batch 64 down to 64K at batch 1024.
The operating regime that matters is the third one. Any deployment serving many concurrent users at long context sits there, and in it the decoder layer is attention-bound and getting worse with both knobs at once.

6Contrast with DeepSeek-V4

The same measurement path, run against the V4 bundle from Part V.

V4’s Sparse-MLA compresses KV temporally before selection, so its indexer works over a compressed sequence and its decode attention is close to flat in context. Measured on B200 through this same lookup code, one V4 layer’s attention at batch 64 moves 203.9 → 240.8 µs from 8K to 128K — about +18%. Over a comparable span (4K → 128K) V3.2’s attention moves 278.8 → 501.8 µs — +80% — and unlike V4 it never levels off, reaching 1,980.3 µs at 1M.

Unlike Part VI’s cross-hardware caveat, both models here are measured on the same B200, so the absolute microseconds are directly comparable. The shape conclusion is unchanged: V4 is asymptotically flat in context, V3.2 asymptotically linear.

Read this as a design trade, not a verdict. V4 buys flat long-context attention with a lossy temporal compression of the cache. V3.2 keeps every token addressable at full fidelity and pays a scan to rank them. Which is better depends on whether your workload can tolerate the compression — but they have genuinely different serving cost curves, and a capacity plan built on one does not transfer to the other.

The gather is a 2–4% sliver at modest batch, but climbs to 19% at batch 1024 and 4K context. That rise with batch is the surprising one, so it is worth spelling out.

Why more batch means a bigger gather share. The share is gather ÷ layer, and the two scale with batch completely differently:
  • The gather grows linearly with batch — each query gathers its own fixed 2048 latents (~1.6 µs/query, §7). From batch 64 to 1024 at 4K it grows 11× (43 → 469 µs).
  • The layer barely grows, because its dominant cost — the MoE block — has saturated. Past batch 32 all 256 experts are already active (§3), so more tokens add no experts and the MoE cost is nearly flat: over the same 64 → 1024 it grows just 2.7×, and the whole layer only 3.9× (636 → 2,507 µs).
A numerator growing 11× over a denominator growing 3.9× — the fraction has to climb. In short: batching stops making the layer’s big block (MoE) more expensive but keeps making the gather more expensive, so the gather eats an ever-larger slice.

Two footnotes to that. Below saturation (batch 1–32) the share actually dips — there the MoE is still growing faster than the gather (each token lights up more experts), so it outruns the numerator. And along every row the share falls with context: the gather is flat in context (§7), but the scan inflates the layer as context grows, shrinking the fixed gather’s slice. So the gather only matters in the high-throughput, short-context corner — and even there it is dwarfed by the scan at long context.

Does a simple a + N/b model fit?

The gather reads, per query, the 2048 selected main-MLA latents at 656 B each (the fp8_ds_mla layout) = 1.34 MB/query, and that scales with batch, not context. Fitting gather(B) = a + N/b with N = B × 1.34 MB gives a clean line (±1% in the saturated regime):

3.04 TB/s
fitted b — effective gather bandwidth (38% of the H200’s 4.8 TB/s peak)
15.2 µs
fitted a — the fixed intercept (see the caveat)
6.77 TB/s
the scan’s bandwidth for contrast (85% of peak) — same HBM, contiguous
b makes sense — as a gather. 3.04 TB/s is only 38% of peak, but that is the signature of a scatter: each query pulls 2048 non-contiguous 656 B latents chosen by the indexer, and random HBM access runs far below streaming peak. The contiguous scan on the same memory reaches 6.77 TB/s (85% of peak) — a 2.2× efficiency gap between reading scattered and reading in order. (One caveat: this kernel gathers and attends, so b folds the MLA attend compute into the number — it is an effective throughput, not raw DRAM bandwidth.)
a does NOT make sense as HBM access latency. Real HBM latency is a few hundred nanoseconds; the fitted 15.2 µs is 30–100× that. It is kernel launch plus the small-batch occupancy floor, not memory latency. The batch-1 point proves it: one query gathers 1.34 MB, which at peak bandwidth is ~0.3 µs of transfer, yet the measured batch-1 gather is 12.0 µs… an order of magnitude of pure overhead, because a single query cannot fill the GPU.
Why the gather is not the story. At batch 64, 1M context the gather is 42.0 µs while the scan that finds those 2048 tokens is 1,308 µs — 20× more. DSA’s long-context cost is finding the top-2048 (a linear scan), not reading them (a bounded, flat gather). “Sparse attention is cheap” is true only of the gather.

The AI column is arithmetic intensity — FLOPs per byte of HBM traffic, computed analytically at this shape (fp8 weights, bf16 activations). It says how memory-bound each kernel is: on the H200 the roofline ridge is ~562 FLOP/byte (fp8) / ~281 (bf16) — below it a kernel is bandwidth-bound, above it compute-bound. Every kernel here is below the ridge, so the whole decode is memory-bound; the AI just says by how much. The projection GEMMs sit around 119 (weight-load bound — at decode each token reads the weight once, so AI ≈ 2×batch), the scan is ~124 but reads the KV cache at 85% of peak bandwidth, and the gather+attend is ~400 (right at the ridge, the one near-balanced kernel).

The picture in one line: the indexer scan and top-k are the two kernels that grow with context; everything else — the projections, the gather, the FlashMLA attend — is fixed. At 128K the scan is already the single largest kernel in the layer.

The routed experts are the block, and they are weight-streaming bound: AI = 4. The grouped GEMM (fused_moe_kernel, ×2 for up/down) is 0.00 ms — 0% of the block — and it moves the full 11.3 GB of all 256 experts’ fp8 weights to process only ~2 tokens each. That is an arithmetic intensity of just 4 FLOP/byte (vs the 562 ridge), and it runs at 92% of peak HBM bandwidth — the layer’s one truly bandwidth-saturating kernel. Because the weight traffic is set by the expert count, not the token count, the block barely grows once all 256 experts are active (§3): more tokens make each per-expert matmul slightly larger but add no weight to stream. That is the throughput sweet spot in §10, and it is a memory-bandwidth effect end to end.
How AI moves with batch. Arithmetic intensity is not fixed — it rises with batch, because more tokens reuse the same weights. For the dense GEMMs AI ≈ 2×batch, so they only cross the ridge into compute-bound above batch ~281. The routed experts are far worse: AI ≈ batch ÷ 16 (each expert still sees only batch×8÷256 tokens), so they stay memory-bound across the entire serving range. DeepSeek-V3.2 decode is a memory-bandwidth problem, and the MoE weights are the largest part of it.

How the lightning indexer’s scan scales

The three marked rows above are the lightning indexer — at 128K context it is 4,273 µs, 64% of the attention block, and the scan is the bulk of it. The scan is the one kernel whose cost grows with the serving knobs, so it is worth seeing on its own. It reads every cached token’s 132 B indexer key, for every query, to produce the index scores — so its work is batch × context.

This one kernel is the whole long-context story. Every long-context conclusion in this report — the crossover (§4), the throughput ceiling (§10) — traces back to this line.

Two things fall out, and the second is the one that matters for offloading:

  • The scatter penalty is small — the tier is everything. The gather runs at 71–96% of a matched sequential copy on every tier: a 656 B record is 164 contiguous words, a big enough transaction that random placement barely hurts. So the gather is not slow because it is scattered — it is exactly as fast as the memory it lands on. (This refines §7’s “18% of peak”: that gap was op-shape — a copy that also writes, vs the streaming scan — not randomness.)
  • Off-HBM is 13–27× slower. The a + N/b model from §7 holds per tier; only b changes — 986 GB/s on HBM, 76 GB/s on CPU DRAM, 36 GB/s over PCIe. The PCIe path is a flat wall (gen5 ×16 tops out ~35 GB/s of read; the gather takes 60% of that).
Offloading the latents off HBM backfires. A batch-1024 gather is 1.40 ms in HBM but 38 ms over PCIe — per layer, per decode step, so ~3.7 s across 58 MoE layers just to gather. DSA’s indexer already makes the scan the long-context cost (§7); moving the gathered latents to CPU DRAM would not relieve that, it would add a second, worse bottleneck. The 656 B main latent has to stay in HBM; only colder tiers are plausible offload candidates, and only if the scan that reads them can be pushed near the memory.

10Throughput: what batching actually buys

Everything so far measured one layer’s latency. The question an operator asks is different: as I batch more concurrent decodes, does throughput (tokens/s = batch ÷ step latency) actually go up? For DSA the answer has a sharp, non-obvious shape.

Throughput always rises with batch — it never falls — but the gains are lumpy, with a knee exactly at MoE saturation (batch 32). Two effects, both measured in the sections above, set the whole curve:

  • The MoE dead zone (batch 1–32): batching barely helps. Below 32, every added token activates more of the 256 experts (§3), so the MoE block grows nearly in proportion to batch — no economy of scale. The worst step is 16 → 32: batch doubles, throughput rises just 91% (710 → 1,355 tok/s at 1K).
  • The saturation sweet spot (batch 32 → 64): throughput nearly doubles for free. Once all 256 experts are active the MoE cost freezes (§8), so 2× the tokens cost ~2% more latency: throughput jumps 1.3× (1,355 → 1,697 tok/s). This is the single best batching decision in the range.
  • Beyond (batch ≥128): the indexer scan sets a ceiling. Past saturation the scan (∝ batch × context, §7) becomes the term that grows with batch, so throughput approaches a context-dependent wall.

Serving takeaway. Always batch past 32 — the 16–32 region is the worst efficiency in the whole range (you pay for all 256 experts but split them over few tokens), and batch 64 is the payoff. How far to push beyond depends on context: at short context keep batching hard (the ceiling is ~10,497 tok/s and every doubling still helps), but at long context the scan caps you near ~3,633 tok/s, so huge batches buy little (55% from 512→1024 at 1M) and cost KV capacity you may not have.
These are tp1 numbers — all 61 layers on one GPU, which no real deployment runs; decode-only, compute-only (kernel time includes HBM weight/KV reads but not inter-GPU collectives). A production TP/EP setup shifts the absolute tok/s, but the shape — the batch-32 knee and the context-dependent ceiling — is the transferable result.

Slope + floor vs pure slope. Dense is a big linear slope with no floor (∝ 656 B/token). The speedup is bounded (~3.5–3.8×), not unbounded: the indexer still scans every token, and top-k grows with context too.

Faster and more memory-bound — the idle compute

These aren’t in tension. “Faster” is about absolute work; “memory-bound” is about the compute-to-byte ratio. DSA does less of both — it just cuts compute harder. The tell is the achieved compute rate on the B200:

The scan runs the B200 at ~17 of its fp8 TOPS (~784 TFLOP/s of 4500) — the compute engine sits >80% idle, starved for bandwidth. On Blackwell even the dense attend cannot reach full rate (AI 425 < ridge 562), so the wider fp8 engine is underfed on both sides. The speedup still caps at the byte ratio (5×), not the FLOP ratio (17×): bandwidth throttles the scan. The two memory ops also pull opposite ways — the isolated scan kernel streams paged keys at ~80–85% of peak HBM, while the gather scatters 2048 random 656 B records at ~7% of peak (§7, §9) — on B200 the scatter gap is even wider than the H200’s 4×, because the gather is latency-bound and gained nothing from the faster HBM (§12).
Why this matters more on Blackwell, not less. Each B200 generation-over-generation buys 2.27× the FLOPs but only 1.67× the bytes, so a 124-intensity streaming reduction leaves an even larger fraction of the chip idle than on the H200. You don’t need 4500 TFLOP/s to rank KV tokens — you need bandwidth next to the KV. The near-memory case (Part VI §12) strengthens with every compute-heavy generation; §15 summarizes what changes.

Which kernels deviate, and why. GATE 0 of the B200 run established that these are not the H200 kernels recompiled: the scan is sm100_fp8_paged_mqa_logits (vs sm90_*), the gather+attend is the sm100::decode FlashMLA-sparse family, the dense GEMMs moved to DeepGEMM’s sm100_fp8_fp4 path, and MoE switched backend entirely — vLLM selects FlashInfer TRT-LLM on SM100 where it selected Triton on SM90. Four deviations stand out: (1) the isolated scan lands at 0.61–0.64×, essentially at the 0.60 bandwidth prior — the cleanest pure-scaling row in the table (the wrapper-level ratio is diluted to 0.70–0.82 by the parts that do not scale); (2) the gather+attend block does not improve at all (1.00×) — the 2048-record scatter is latency-bound, not bandwidth-bound, so 1.67× the HBM bandwidth buys it nothing; (3) single-decode (batch 1) attention is slower on B200 (1.18×) — fixed launch/setup cost of the new sm100 decode path dominates at tiny batch; (4) MoE at few-tokens × many-experts improves 7.7× (0.13×), far beyond any roofline — that is the Triton→TRT-LLM backend swap fixing a pathological H200 case, not silicon scaling, and it is why the batch-64 TPOT ratio (0.27×) beats every hardware prior. Large-token MoE (0.46×) and the wide dense GEMMs (0.38–0.46×) sit at the compute prior, confirming the fp8 engine delivers its 2.27× on well-shaped work.
How to use this table for H200→B200 scaling. Do not apply one scalar. Scale scan-dominated attention by ~0.67, compute-bound GEMM/MoE work by ~0.44, keep small-batch attention flat-to-worse (~1.0–1.2), and treat any Triton-pathological MoE shape as re-benchmarked, not scaled. TPOT-level ratios blend these per the workload’s phase mix — the per-phase rows above are the primitives.

13The five unexpected differences

§12’s table, distilled: the rows a naive “scale H200 by the spec sheet” model gets wrong, each with its evidence and its consequence.

1 · The gather+attend floor did not move: 1.00× (154.7 → 154.6 µs). The top-2048 scatter+attend is latency-bound, not bandwidth-bound — 1.67× the HBM bandwidth bought it nothing. DSA’s fixed floor is generation-invariant, with a compounding consequence quantified in §14.2.
2 · Single-user decode got slower: 1.18× (173.8 → 205.4 µs at kv=128K). The sm100 FlashMLA-sparse decode path carries a higher fixed launch/setup cost; at batch 1 that cost dominates. B200 does not pay off until batch ~16–32 (§14.1) — interactive single-stream serving is a regression, not an upgrade.
3 · MoE at (64 tok, 256 exp): 0.13× — 7.7× faster, beyond any roofline. Not silicon: vLLM swapped MoE backends (SM90 Triton → SM100 FlashInfer TRT-LLM), and Triton was pathological at few-tokens × many-experts (2,697 µs for 64 tokens). This one swap drives the batch-64 TPOT ratio to 0.27× — better than the best hardware prior (§14.4 separates backend from silicon).
4 · act_fn got slower: 1.24× (60.0 → 74.2 µs at 2048 tokens). A memory-bound elementwise SiLU×mul “should” scale by ~0.6×. Same vLLM kernel on both GPUs, consistent across the token axis. Unexplained; recorded as measured — the simulator replays the measured value.
5 · The scan streams further from peak: 66% vs 73% (wrapper-level). The isolated sm100_fp8_paged_mqa_logits kernel still scales essentially at the bandwidth prior (0.61–0.64× vs 0.60), but the non-scaling parts around it (top-k at 0.91×, fixed floor at 1.00×) dilute the wrapper. Fraction-of-peak erodes a little each generation even when the streaming kernel itself is healthy.

The batch-64, 128K decode step improved 195.0 → 52.0 ms (0.27×) — better than any hardware ratio. Splitting the win using H200’s own well-shaped MoE cell as a counterfactual (its (2048, 256) cell scaled linearly to 64 tokens ≈ 115 µs/layer vs the 2,697 µs Triton pathology):

The counterfactual is a linear lower bound (a real backend keeps some per-launch overhead at 64 tokens), so it brackets the backend effect from below; the silicon-only gap is the remaining distance to the B200 row.

Most of the 3.75× step win at batch 64 is the MoE backend, not the GPU. An H200 with a TRT-LLM-class MoE backend would already capture the bulk of it; the silicon contributes roughly the per-phase roofline ratios (0.44–0.82). 14.5 — Serving-level consequences & open questions

  • Capacity: the KV budget grew 144.4M → 194.2M tokens (+34%), yet the same six (batch × context) profiling corners stay infeasible, and end-to-end LLMServingSim runs on this bundle show DP4+EP4 capacity-dead at 128K (64-expert rank ≈ 172 GiB of 192) and a 1 TiB single GPU capping at ~61 concurrent 128K streams. Capacity, not bandwidth, still bounds long-context V3.2 serving on Blackwell — the memory-tier studies this bundle feeds.
  • Measured cluster point: DP8+EP8 at 128K, B_cluster=128: 4,749 tok/s vs 3,120 on H200 — 1.52×, i.e. the TPOT blend (0.66×) of §12, not the spec-sheet 1.67–2.27×.
  • Unprofiled by design, now worth revisiting: skew profiling was skipped on the DSA ruling (fixed top-2048 attend). The sm100 scan’s batch-1 penalty and the frozen gather floor were not visible on H200 — a small heterogeneous-decode sweep on B200 would test whether the scan stays mean-exact under skew there too.
  • The act_fn 1.24× regression (§13.4): dump the elementwise kernel’s launch config on both GPUs (grid/block/vectorization) — likely a tuning artifact, cheap to confirm, and it biases every dense-layer composition by a few percent.
  • Top-k at 0.91×: neither bandwidth- nor overhead-shaped. The cooperative_topk cs8→cs16 change suggests a different cooperative width; worth a dedicated microbench before trusting extrapolations of the top-k term past 1M context.

15Near-memory: what changes on B200

Part VI’s §12 makes the full base-die/NMP case on H200 numbers; it is deliberately not duplicated here.

Read the architecture note in Part VI §12 — the indexer on an HBM base die. What the B200 measurements change, in five lines:

  • The GPU’s 8 TB/s roughly halves the scan’s wall-clock vs H200 — but the scan stays strictly bandwidth-bound (§11), so the NMP argument is unchanged in kind.
  • Scan-parity on-die throughput doubles: matching the PHY now needs ~124 FLOP/B × 8 TB/s ≈ 1,000 aggregate TOPS across the stack’s base dies (H200-parity was ~600).
  • The fp8 ridge moves 412 → ~562 FLOP/byte, so AI-425 dense attend is itself memory-bound on B200 — every generation of compute-heavier GPUs widens the class of kernels that would rather live next to the memory.
  • The idle-compute waste grows: the scan leaves >80% of a 4,500-TFLOP/s engine unused (§11), vs ~75% of 1,979 on H200.
  • Capacity pressure is unchanged: 192 GB admits the same six infeasible (batch, context) corners as 141 GB did (§2) — the LPDDR capacity tier Part VI argues for is still the binding constraint at DP-scale batches.

16Method & caveats

  • Measurement. vLLM 0.25.1 layerwise profiling of a 1-layer dummy-weight DeepSeek-V3.2-Exp on one B200 (SM100, 192 GB HBM3e), fp8_ds_mla KV cache, FlashMLA-sparse backend, enforce_eager, tp1. No checkpoint weights are downloaded — only kernel shapes and timings matter.
  • Composition. Per-layer totals are assembled from the per-category CSVs by calling LLMServingSim’s own lookup functions, so these numbers are exactly what the simulator replays, including its interpolation and its extrapolation past the profiled grid.
  • Compute-only. Tensor- and expert-parallel collectives are costed by ASTRA-Sim, not by these tables. At the tp1/ep1 configuration profiled here there are none, so the figures are complete for that case — but a tp8/ep8 deployment adds communication on top.
  • MoE backend is FlashInfer TRT-LLM, vLLM’s own selection on SM100 (the H200 run selected Triton on SM90) — a genuinely different implementation, and one reason the H200→B200 MoE ratios in §12 are not pure hardware scaling.
  • Beyond 163,840 tokens the model is not numerically V3.2. vLLM sizes the YaRN RoPE cache as original_max_position_embeddings × factor and ignores max_position_embeddings, so the profiling run raises factor to cover 1M positions. That changes the values in the cos/sin cache, not the shape or cost of any kernel — timings are unaffected, and positions past the trained range are meaningless for output quality regardless.
  • Faded table cells are interpolated, not measured. The measured KV axis is 16, 64, 256, 1,024, 4,096, 16,384, 65,536, 131,072, 262,144, 524,288, 1,048,576.
