§Overview in one minute

DeepSeek Sparse Attention (DSA) is usually described as “attention that stays cheap at long context”. Measured, that is only half true — and the half that is false is the half that decides how you build a serving cluster.

Plain-language thesis. DSA makes the part of attention that reads KV cheap — it attends to a fixed top-2048 no matter how long the context is. But something still has to decide which 2048, and that decision is a lightning indexer that scans every token in the cache. So a V3.2 layer is flat in the attend and linear in the scan. At short context the scan is invisible; at long context it is the whole story.
The consequence. Long context does not make V3.2 attention-cheap; it makes V3.2 attention-bound. At batch 64 the decoder layer goes from 625.0 µs to 2,337.1 µs, and attention overtakes the 256-expert MoE block on the way.

1What DSA changes, mechanically

Why the cost splits into a flat part and a linear part.

A V3.2 decoder layer runs two RMSNorms, one attention block and one MoE block. The attention block is classic multi-head latent attention (MLA) — one shared latent per token, kv_lora_rank 512 plus a 64-dim RoPE part — wrapped around a lightning indexer. Per token per layer the cache holds 656 B of main MLA latent plus 132 B of indexer key.

On every decode step, for every sequence in the batch, the indexer scans that sequence’s entire 132 B/token key cache to pick the top index_topk = 2048 tokens. FlashMLA then attends over exactly those 2048. So:

  • The attend is O(1) in context — fixed at 2048 selected tokens. This is the part the “sparse attention is cheap” story is about, and it is real.
  • The scan is O(batch × context) — every cached token is touched to be ranked. This part is bandwidth-bound and it is what the measurement below exposes.
A back-of-envelope that the data confirms. At batch 64 with 1M context the indexer must read 64 × 1,048,576 × 132 B ≈ 8.9 GB per layer per step. The measured excess over the short-context baseline implies an effective ≈5.2 TB/s — about 66% of the B200’s 8 TB/s peak HBM bandwidth (rising to ≈5.9 TB/s, 74%, at batch 128). The sm100 scan streams somewhat further from peak than its sm90 counterpart did (73%) — §12 quantifies this.

3Where the time goes

The same layer, decomposed — batch 64, across context.

Composition of one MoE decoder layer at decode batch 64. Percentage above each bar is attention’s share.

At short context the layer is an MoE layer with some attention attached: the 256-expert block dominates and the picture matches conventional MoE intuition. At long context that inverts completely — the MoE block does not change at all (it depends on token count, not context), while attention grows without bound.

Why this matters for a cluster. The MoE block is what expert parallelism exists to spread. If long-context serving is attention-bound, adding EP ranks buys progressively less, and the binding constraint moves to KV-cache bandwidth and capacity instead.

The crossover is not monotonic in batch — it is U-shaped, and the shape falls straight out of how the two blocks scale.

  • Batch 1–2: attention-bound almost immediately. A single token activates only 8 of the 256 experts, so the MoE block is tiny and even a short scan outweighs it.
  • Batch 4–32: MoE-bound throughout. Here each added token still lights up more experts, so MoE cost climbs steeply with batch while the scan is still small. Attention never catches up inside a 1M context.
  • Batch ≥64: attention-bound again, and progressively sooner. Once the batch is large enough to activate all 256 experts, MoE saturates — extra tokens are nearly free for it. The indexer scan keeps growing with batch × context, so the crossover marches from 1M at batch 64 down to 64K at batch 1024.
The operating regime that matters is the third one. Any deployment serving many concurrent users at long context sits there, and in it the decoder layer is attention-bound and getting worse with both knobs at once.

6Contrast with DeepSeek-V4

The same measurement path, run against the V4 bundle from Part V.

V4’s Sparse-MLA compresses KV temporally before selection, so its indexer works over a compressed sequence and its decode attention is close to flat in context. Measured on B200 through this same lookup code, one V4 layer’s attention at batch 64 moves 203.9 → 240.8 µs from 8K to 128K — about +18%. Over a comparable span (4K → 128K) V3.2’s attention moves 278.8 → 501.8 µs — +80% — and unlike V4 it never levels off, reaching 1,980.3 µs at 1M.

Unlike Part VI’s cross-hardware caveat, both models here are measured on the same B200, so the absolute microseconds are directly comparable. The shape conclusion is unchanged: V4 is asymptotically flat in context, V3.2 asymptotically linear.

Read this as a design trade, not a verdict. V4 buys flat long-context attention with a lossy temporal compression of the cache. V3.2 keeps every token addressable at full fidelity and pays a scan to rank them. Which is better depends on whether your workload can tolerate the compression — but they have genuinely different serving cost curves, and a capacity plan built on one does not transfer to the other.

The gather is a 2–4% sliver at modest batch, but climbs to 19% at batch 1024 and 4K context. That rise with batch is the surprising one, so it is worth spelling out.

Why more batch means a bigger gather share. The share is gather ÷ layer, and the two scale with batch completely differently:
  • The gather grows linearly with batch — each query gathers its own fixed 2048 latents (~1.6 µs/query, §7). From batch 64 to 1024 at 4K it grows 11× (43 → 469 µs).
  • The layer barely grows, because its dominant cost — the MoE block — has saturated. Past batch 32 all 256 experts are already active (§3), so more tokens add no experts and the MoE cost is nearly flat: over the same 64 → 1024 it grows just 2.7×, and the whole layer only 3.9× (636 → 2,507 µs).
A numerator growing 11× over a denominator growing 3.9× — the fraction has to climb. In short: batching stops making the layer’s big block (MoE) more expensive but keeps making the gather more expensive, so the gather eats an ever-larger slice.

Two footnotes to that. Below saturation (batch 1–32) the share actually dips — there the MoE is still growing faster than the gather (each token lights up more experts), so it outruns the numerator. And along every row the share falls with context: the gather is flat in context (§7), but the scan inflates the layer as context grows, shrinking the fixed gather’s slice. So the gather only matters in the high-throughput, short-context corner — and even there it is dwarfed by the scan at long context.

Does a simple a + N/b model fit?

The gather reads, per query, the 2048 selected main-MLA latents at 656 B each (the fp8_ds_mla layout) = 1.34 MB/query, and that scales with batch, not context. Fitting gather(B) = a + N/b with N = B × 1.34 MB gives a clean line (±1% in the saturated regime):

b makes sense — as a gather. 3.04 TB/s is only 38% of peak, but that is the signature of a scatter: each query pulls 2048 non-contiguous 656 B latents chosen by the indexer, and random HBM access runs far below streaming peak. The contiguous scan on the same memory reaches 6.77 TB/s (85% of peak) — a 2.2× efficiency gap between reading scattered and reading in order. (One caveat: this kernel gathers and attends, so b folds the MLA attend compute into the number — it is an effective throughput, not raw DRAM bandwidth.)
a does NOT make sense as HBM access latency. Real HBM latency is a few hundred nanoseconds; the fitted 15.2 µs is 30–100× that. It is kernel launch plus the small-batch occupancy floor, not memory latency. The batch-1 point proves it: one query gathers 1.34 MB, which at peak bandwidth is ~0.3 µs of transfer, yet the measured batch-1 gather is 12.0 µs… an order of magnitude of pure overhead, because a single query cannot fill the GPU.
Why the gather is not the story. At batch 64, 1M context the gather is 42.0 µs while the scan that finds those 2048 tokens is 1,308 µs — 20× more. DSA’s long-context cost is finding the top-2048 (a linear scan), not reading them (a bounded, flat gather). “Sparse attention is cheap” is true only of the gather.

The picture in one line: the indexer scan and top-k are the two kernels that grow with context; everything else — the projections, the gather, the FlashMLA attend — is fixed. At 128K the scan is already the single largest kernel in the layer.

How AI moves with batch. Arithmetic intensity is not fixed — it rises with batch, because more tokens reuse the same weights. For the dense GEMMs AI ≈ 2×batch, so they only cross the ridge into compute-bound above batch ~281. The routed experts are far worse: AI ≈ batch ÷ 16 (each expert still sees only batch×8÷256 tokens), so they stay memory-bound across the entire serving range. DeepSeek-V3.2 decode is a memory-bandwidth problem, and the MoE weights are the largest part of it.

  • The scatter penalty is small — the tier is everything. So the gather is not slow because it is scattered — it is exactly as fast as the memory it lands on. (This refines §7’s “38% of peak”: that gap was op-shape — a copy that also writes, vs the streaming scan — not randomness.)
  • Off-HBM is 13–27× slower. The a + N/b model from §7 holds per tier; only b changes — 986 GB/s on HBM, 76 GB/s on CPU DRAM, 36 GB/s over PCIe. The PCIe path is a flat wall (gen5 ×16 tops out ~35 GB/s of read; the gather takes 60% of that).
Offloading the latents off HBM backfires. A batch-1024 gather is 1.40 ms in HBM but 38 ms over PCIe — per layer, per decode step, so ~3.7 s across 58 MoE layers just to gather. DSA’s indexer already makes the scan the long-context cost (§7); moving the gathered latents to CPU DRAM would not relieve that, it would add a second, worse bottleneck. The 656 B main latent has to stay in HBM; only colder tiers are plausible offload candidates, and only if the scan that reads them can be pushed near the memory.

15Near-memory on B200: the base-die case, recomputed

Part VI §12 made the full architecture argument on H200 numbers: run the lightning indexer on the HBM base die of a capacity-expanded stack, tier keys (HBM) apart from latents (LPDDR), and let the die that computes the index also drive the fetch. This section re-derives every number in that case from the B200 measurements — and the B200 data moves the conclusion in both directions at once.

The proposal, unchanged in shape: indexer keys stay in HBM, the base die scans them and selects the top-2048, then fetches only those latents from LPDDR over UCIe.

What the B200 numbers keep, and sharpen

  • The indexer still owns long-context attention. Its share of the decode attention block is 64% at 128K and 92% at 1M on B200 (H200: 71% / 94%) — a 1.49× faster scan only dips the share a few points, because the scan is the one term that scales with context. The op worth offloading is unchanged; what grew instead is the gather floor’s share of the remainder (§14.2), which reshapes the argument below.
  • The key/latent tiering split is unchanged (it is a property of the model, not the GPU): 132 B/token of scan-hot keys (17% of KV) vs 656 B/token of gather-cold latents (83%) — LPDDR takes 83% of capacity while HBM keeps the context-scaling bandwidth.
  • The scan-bandwidth wall is unchanged in kind, halved in time. At batch 64 / 1M the scan reads ~540 GB/step across layers: ~68 ms at the B200’s 8 TB/s (H200: ~113 ms) but still ~1.1 s at an LPDDR-class 500 GB/s — a 16× cliff. Keys must stay in HBM (or near-DRAM the base die can stream); only the compute placement is negotiable.
  • The key-capacity crossover grows with the 192 GB stack: the measured 142.5 GiB KV pool holds all-layer keys up to batch×context ≈ 19 M token-seqs (H200: ~12 M) — batch 64 to ~290K context, batch 128 to ~145K. Beyond that the keys themselves spill and the crossover model of Part VI §12 becomes the binding study.

(2) Top-k is six orders of magnitude cheaper (26 GOPS — effectively free comparator silicon), and since its GPU time did not improve on B200, moving it on-die saves more relative time each generation: it belongs on the die unconditionally. (3) The projections need only ~3 TOPS but belong on the GPU anyway: they are L-independent weight-GEMMs over the 4 new tokens with no memory-side data to exploit. (4) A die below the scan budget degrades gracefully via co-scan: a 25 TOPS/die array covers ~26% of the B200 scan (~40% of H200’s) with the GPU carrying the rest — a thermal dial, not a cliff.

The bandwidth-parity caveat: matching latency ≠ speedup

A die that meets the scan’s TOPS budget does not automatically speed the layer up — because the scan is bandwidth-bound and the bytes come out of the same DRAM banks whether they exit through the PHY to the GPU or stop at the base die. If the stack’s internal (bank/TSV) bandwidth equals its PHY-rated bandwidth, the die reads keys exactly as fast as the GPU does: latency-parity compute = same scan time, Δ = 0. The same logic constrains co-scan: splitting the key stream between GPU and die adds bandwidth only if the custom HBM provisions internal bandwidth above the PHY rate — both readers drain the same banks. We name that design knob h = internal BW ÷ external BW; extra bank-group/TSV parallelism buys h > 1 at silicon cost. Real latency leverage requires one of: h > 1 (a custom-HBM design choice that must be stated), the keys-spill regime (locality becomes a genuine bandwidth advantage), or larger batch/context growing the fused top-k/gather savings. Any co-scan speedup quoted on these pages implicitly assumes h > 1 — this section makes that assumption explicit.

The G-ladder: what to fuse around the gather (all latents in LPDDR)

Given the parity caveat above, the base die’s defensible latency territory is the selection chain — top-k and the gather — because both are latency/protocol-bound, not bandwidth-bound, so they need queues and proximity rather than TOPS or bandwidth headroom. Standing assumption for every row below: the 656 B latent entries live in LPDDR (the capacity design’s whole point; 167.8 GB at b=32 — 16% of the tier); only the 132 B indexer keys stay in HBM, scanned by the GPU. Operating point: b=32/GPU, L=128K, B200 measured; EP8 layer components attn 332.8 / MoE 155.8 / norms 5 µs.

Why the gather is latency-bound, in one line of evidence each: its effective bandwidth collapses with concurrency (112 GB/s at b=1 — 1.4% of peak — vs 2.0 TB/s at b=64, 3.0 at b=1024); the naive-gather microbenchmark gained only 1.05× from B200’s 1.67× bandwidth while the TMA-batched in-kernel gather gained 2.5× (concurrency engineering, not bytes); and the surrounding metadata/launch floor (95.4 µs at b=32) did not move across the generation. Requests-in-flight decide its time; bytes do not.

The baselines matter. With latents in LPDDR, the honest all-GPU baseline is GPU top-k (40.7 µs) + GPU-driven UCIe gather: 43.0 MB ÷ (1.024 TB/s × 0.5 efficiency) = 84.0 µs — cacheline-fragmented, uncached, MSHR-limited — giving a 551.1 µs layer. 16Method & caveats

  • Measurement. vLLM 0.25.1 layerwise profiling of a 1-layer dummy-weight DeepSeek-V3.2-Exp on one B200 (SM100, 192 GB HBM3e), fp8_ds_mla KV cache, FlashMLA-sparse backend, enforce_eager, tp1. No checkpoint weights are downloaded — only kernel shapes and timings matter.
  • Composition. Per-layer totals are assembled from the per-category CSVs by calling LLMServingSim’s own lookup functions, so these numbers are exactly what the simulator replays, including its interpolation and its extrapolation past the profiled grid.
  • Compute-only. Tensor- and expert-parallel collectives are costed by ASTRA-Sim, not by these tables. At the tp1/ep1 configuration profiled here there are none, so the figures are complete for that case — but a tp8/ep8 deployment adds communication on top.
  • MoE backend is FlashInfer TRT-LLM, vLLM’s own selection on SM100 (the H200 run selected Triton on SM90) — a genuinely different implementation, and one reason the H200→B200 MoE ratios in §12 are not pure hardware scaling.
  • Beyond 163,840 tokens the model is not numerically V3.2. vLLM sizes the YaRN RoPE cache as original_max_position_embeddings × factor and ignores max_position_embeddings, so the profiling run raises factor to cover 1M positions. That changes the values in the cos/sin cache, not the shape or cost of any kernel — timings are unaffected, and positions past the trained range are meaningless for output quality regardless.
  • Faded table cells are interpolated, not measured. The measured KV axis is 16, 64, 256, 1,024, 4,096, 16,384, 65,536, 131,072, 262,144, 524,288, 1,048,576.
