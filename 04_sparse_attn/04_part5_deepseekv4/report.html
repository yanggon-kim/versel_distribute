DeepSeek-V4 Sparse Attention — Part V

Parts I–IV asked which KV entries and experts a decoder layer selects. This part asks a different question: what actually runs inside one decoder layer, in order, and how many microseconds of GPU does each operation cost? Measured by vLLM layerwise profiling of DeepSeek-V4-Pro on a single NVIDIA B200 (SM100) — the same run that produced the LLMServingSim profile bundle.

§Overview in one minute

A DeepSeek-V4 decoder layer is two heavy blocks wrapped in cheap glue: a sparse-attention block and a Mixture-of-Experts block, stitched together by multi-rate hyper-connections (mHC) instead of a plain residual add. We profiled every CUDA kernel in one layer and attributed the time.

Plain-language thesis. Per layer, almost all the GPU time is in two GEMM-bound blocks: the MoE experts (a single fused fp4 kernel) and the attention projections (wq_b up-projection and wo_b output projection). The parts that make V4 sparse — the lightning indexer, the KV compressor, the FlashMLA core — are individually small (a few µs each), and their payoff shows up not in the per-op table but in §6: attention barely grows as context length goes from 0 to 128K. The hyper-connections that replace the residual stream are cheap glue (<7%).
Read the µs the right way. These are device-active CUDA times per operation. V4's attention runs its input GEMMs across four CUDA streams at once (§3), so the per-op numbers overlap and sum to more than the block's wall-clock. Use them for attribution (where the work is), not as an addition you can trust to equal the stopwatch. Where a block's own total is meaningful we quote the profiler's roll-up (Attention 217.6, MoE 235.1).

§1The layer at a glance: what runs, in what order

One DeepseekV4DecoderLayer.forward executes four stages in strict sequence. First a hyper-connection mix feeds the attention block; attention writes back; a second hyper-connection mix feeds the MoE block; the MoE writes back. There is no separate "add residual" — the mHC kernels are the residual path.

Execution order inside one decoder layer, annotated with device-active GPU time for this batch. Purple = hyper-connection glue (cheap); blue = sparse attention; green = MoE. The two coloured blocks are ~94% of the layer.

First… then… (from DeepseekV4DecoderLayer.forward):

  • 1. mHC pre (query side). One fused kernel folds the previous layer's output mix, this layer's input mix, and the attention RMSNorm together, and emits the vector the attention block reads.
  • 2. Sparse attention. Project to the compressed query/KV latent, let the lightning indexer pick the top-1024 relevant KV entries, run FlashMLA over just those, project back.
  • 3. mHC (ffn side). Same fused hyper-connection kernel again, now folding attention's output back into the stream and applying the FFN RMSNorm.
  • 4. MoE. Score 384 experts, route each token to 6 (plus 1 shared expert), run one fused fp4 grouped-GEMM, write back.
CSA vs HCA. V4 layers come in two flavours. A CSA (Compressed Sparse Attention) layer compresses KV 4× and runs the lightning indexer to select a top-k set — this is the layer we profiled. An HCA (Heavily Compressed Attention) layer compresses 128× instead, leaving so few entries that it just attends to all of them and skips the indexer entirely (−36 µs of attention). V4-Pro alternates them across its 61 layers. Everything else in this report — mHC, MoE, the projections — is identical for both.

§2mHC — multi-rate hyper-connections (the residual replacement)

Where a normal transformer does x = x + block(norm(x)), V4 replaces the residual with a small learned mixing map over a widened stream. We call it mHC (multi-rate hyper-connections); in the model it is the family of *_tilelang kernels.

The stream is widened by hc_mult = 4: instead of a single residual vector, the layer carries four "rates" and mixes them with a doubly-stochastic (Sinkhorn-normalised, 20 iters) map before and after each block. Two fused kernels do all of it:

  • mHC pre / query side (mhc_pre_big_fuse_with_norm, and the fused post+pre variant on interior layers): folds the previous block's output back into the stream, computes this block's input mix, and applies the block's RMSNorm — producing the vector the attention (or MoE) block consumes. "Query side" here just means the mix that feeds the attention query path.
  • mHC ffn side (mhc_fused): the same fused mix again between attention and MoE.
  • Model-level heads (mhc_post, hc_head_fuse, and a small hc_prenorm GEMM): run once at the top/bottom of the stack, not per block.

§3Sparse attention (CSA), operation by operation

The attention block (DeepseekV4FlashMLAAttention, 217.6 µs rolled up) is a pipeline of a dozen kernels. It projects the token into a compressed query/KV latent, uses a cheap "lightning indexer" to pick which past tokens matter, runs FlashMLA over only those, and projects back. Read the sub-ops as attribution: several of the input GEMMs run concurrently on separate CUDA streams (see the note below), so they overlap in wall-clock.

The pipeline, in order

  1. Input GEMMs (parallel). fused_wqa_wkv projects the hidden state down to the query latent (rank 1536) and the shared KV latent (512) in one GEMM; concurrently, on three auxiliary streams, the compressor and the indexer's weights_proj run.
  2. q/kv RMSNorm. One fused kernel normalises both latents.
  3. wq_b up-projection. Expands the query latent back to the 128 heads × head_dim.
  4. Lightning indexer → top-1024. Scores every compressed KV entry with a small fp4 network (64 heads) and keeps the index_topk = 1024 most relevant — this is the "selection" Parts I–III analysed.
  5. Compressor. Summarises the new token's KV into a compressed entry and inserts it into the indexer's cache.
  6. FlashMLA sparse core. Builds decode metadata, runs the sparse attention over just the selected entries, and combines split-KV partials.
  7. Inverse-RoPE + output projection. wo_a (grouped low-rank, o_groups = 16, rank 1024) then wo_b back to the 7168-wide hidden.

"~" values fold together several tiny kernels reported individually in the tree (§7). The two fp4 projection GEMMs (wq_b 23.4 + wo_b 29.0) are the largest sub-ops; the sparse machinery (indexer 36.3 + compressor 11.1 + FlashMLA ~41) is what buys the flat context scaling in §6.

Four streams at once. V4 launches the metadata-independent input GEMMs on four CUDA streams — fused_wqa_wkv on the default stream, plus the compressor kv_score, the indexer weights_proj, and the indexer's own compressor on three aux streams. That is why the sub-op µs above overlap and their naive sum exceeds the 217.6 µs block roll-up.
Why sparse attention barely grows with context. Everything above except the indexer's scoring and FlashMLA is per new token, independent of history length. The indexer scores all entries cheaply in fp4, and FlashMLA only ever attends the fixed top-1024. So doubling the context roughly doubles a small scoring term and leaves the rest flat — measured directly in §6.

§4MoE, operation by operation

The FFN is a Mixture-of-Experts (DeepseekV4MoE, 235.1 µs rolled up): a router scores 384 experts, each token is sent to 6 of them plus 1 always-on shared expert, and a single fused fp4 grouped-GEMM does all the expert math. Where Part IV studied which experts get picked and how stable that is, this is the cost side of the same block.

The first 3 layers of V4 route by a fixed token-id hash instead of this learned gate (see Part IV).

Cost rises with the token count and, more slowly, with the number of distinct experts activated across the batch — a small batch that happens to spread across many experts pays a surcharge, which is exactly why expert-selection locality (Part IV) translates into real GPU savings.

The one-time tax: LM head

Outside the layer stack, the LM head (hidden 7168 → 129,280-vocab logits) costs ~268 µs per iteration and the sampler ~37 µs. Per layer that is nothing, but against a single decode step it is comparable to a whole decoder layer — a fixed tax paid once per generated token, not once per layer.

§7Method & caveats

  • Hardware / stack. One NVIDIA B200 (SM100), CUDA 13, vLLM 0.24 with the DeepGEMM MegaMoE backend, fp8 fp8_ds_mla KV, fp4 experts, enforce_eager (no CUDA graphs, so every kernel is an independently timeable launch).
  • How measured. vLLM's layerwise_profile() over a one-decoder-layer model (num_hidden_layers=1) built with random ("dummy") weights — kernel time depends on tensor shapes, not values, so timings are representative while nothing is downloaded. The batch was prefill 8 + 2 decodes at kv 64. Scaling tables in §6 come from the full profiler grid sweep.
  • Device-active, overlapping time. Reported µs are per-op CUDA device time. V4's attention overlaps input GEMMs across four streams, so per-op numbers sum above the block wall-clock — treat them as attribution. Block roll-ups (attention 217.6, MoE 235.1) are the profiler's own per-module aggregates. A few "~" rows fold together many sub-µs kernels the tree lists individually.
  • CSA layer. We profiled a Compressed-Sparse-Attention layer (compress-ratio 4, indexer present). Heavily-Compressed-Attention layers skip the ~36 µs indexer; V4-Pro alternates the two across its 61 layers.
  • Model variant. These GPU numbers are DeepSeek-V4-Pro (hidden 7168, 61 layers, 384 experts / 6 active). Parts I–IV instrument DeepSeek-V4-Flash (256 experts, 43 layers); the operation structure is identical, the dimensions differ.
  • Not the full picture. Single-GPU numbers exclude the tensor-/expert-parallel collectives (all-reduce, all-to-all) that a multi-GPU deployment adds around these kernels — those are modelled analytically by LLMServingSim, not measured here.
